
## 1. What Is Cloud Computing?

Cloud computing is a model where **computing resources are provided by a third-party provider over the Internet and consumed on demand**.

Instead of an organization purchasing and maintaining its own:

- Physical servers
    
- Storage systems
    
- Network equipment
    
- Data centers
    
- Cooling systems
    
- Power infrastructure
    
- Hardware maintenance
    

the organization can obtain these resources from a cloud provider.

### Common cloud providers

- Amazon Web Services (AWS)
    
- Microsoft Azure
    
- Google Cloud Platform (GCP)
    

Cloud computing can also include services that users interact with every day:

- Google Drive
    
- Gmail
    
- Microsoft 365
    
- Dropbox
    
- Slack
    
- Zoom
    
- TryHackMe
    

The important point is that **"cloud" does not mean a completely different type of computer technology**.

Underneath the cloud, there are still familiar technologies:

- Servers
    
- Operating systems
    
- Networks
    
- Databases
    
- Storage
    
- Virtual machines
    
- Authentication
    
- APIs
    
- Applications
    

The difference is primarily **who owns, operates, and manages the infrastructure and how the resources are delivered**.

---

# 2. Why Organizations Use Cloud

Organizations move workloads to the cloud for several reasons.

### Scalability

A company can increase or decrease resources based on demand.

Example:

An e-commerce company normally needs:

```text
20 servers
```

During a major sale:

```text
20 servers
      ↓
200 servers
```

Cloud infrastructure can make this scaling much easier.

---

### Availability

Cloud providers operate large infrastructures designed to provide highly available services.

Instead of relying on a single physical server, workloads can potentially be distributed across:

- Multiple servers
    
- Availability zones
    
- Regions
    
- Storage systems
    

---

### Cost model

Traditional infrastructure often requires large upfront investments.

Cloud commonly uses a consumption-based model:

```text
Use resource
     ↓
Pay for resource
```

This doesn't automatically mean cloud is cheaper. Poor cloud management can create **very expensive environments**.

---

### Reduced infrastructure management

The organization doesn't necessarily need to maintain:

- Physical servers
    
- Data-center hardware
    
- Power
    
- Cooling
    
- Physical networking
    

Depending on the service model, the provider handles more of these responsibilities.

---

# 3. Cloud Service Models

There are three major service models you should know:

1. **IaaS — Infrastructure as a Service**
    
2. **PaaS — Platform as a Service**
    
3. **SaaS — Software as a Service**
    

The main difference is:

> **How much of the technology stack is managed by the customer versus the cloud provider.**

---

# 4. IaaS — Infrastructure as a Service

## Definition

IaaS provides **virtualized computing infrastructure on demand**.

The cloud provider gives you resources such as:

- Virtual machines
    
- Storage
    
- Networking
    
- Virtual networks
    
- Firewalls/security controls
    
- Compute resources
    

You then configure and manage the software running on those resources.

Examples include:

- AWS EC2
    
- Azure Virtual Machines
    
- Google Compute Engine
    

---

## IaaS Example

Suppose a company needs a Linux server.

Traditionally:

```text
Buy physical server
        ↓
Install server hardware
        ↓
Install Linux
        ↓
Configure networking
        ↓
Configure security
        ↓
Maintain hardware
```

With IaaS:

```text
Open cloud console
        ↓
Create VM
        ↓
Select Linux image
        ↓
Configure networking
        ↓
Start VM
```

The physical hardware is operated by the cloud provider.

---

## What the customer manages in IaaS

Typically, the customer is responsible for things such as:

- Operating system
    
- OS patching
    
- Applications
    
- Application configuration
    
- User accounts
    
- Credentials
    
- Data
    
- Network configuration
    
- Security configuration
    
- Access permissions
    

For example:

If your Linux VM has an unpatched SSH vulnerability, you generally cannot blame AWS for failing to patch **your operating system**.

---

## What the provider manages

The provider generally manages the underlying infrastructure, such as:

- Physical servers
    
- Data centers
    
- Physical networking
    
- Physical storage
    
- Power
    
- Cooling
    
- Underlying virtualization infrastructure
    

The exact responsibility boundary depends on the provider and service.

---

# 5. IaaS Security Example

Imagine:

```text
AWS
 │
 └── EC2 VM
      │
      ├── Ubuntu
      ├── Apache
      ├── Application
      └── Customer Data
```

Suppose Apache is vulnerable.

Who needs to fix it?

**The customer.**

Suppose the physical AWS server has a hardware failure.

Who handles that?

**AWS.**

This distinction is fundamental to cloud security.

---

# 6. PaaS — Platform as a Service

## Definition

PaaS provides a **managed platform for developing and running applications**.

The developer doesn't want to manage:

- Physical servers
    
- Operating systems
    
- Hypervisors
    
- Hardware
    
- Runtime infrastructure
    

They simply want:

> "Give me a platform where I can deploy my application."

Examples:

- Vercel
    
- Heroku
    
- Google App Engine
    

---

# 7. PaaS Example

Suppose a developer writes:

```text
app.py
```

Instead of:

```text
Buy server
 ↓
Install OS
 ↓
Install runtime
 ↓
Configure server
 ↓
Configure networking
 ↓
Deploy application
 ↓
Patch OS
 ↓
Maintain server
```

they can use a PaaS platform:

```text
Write code
   ↓
Push/deploy code
   ↓
Platform builds application
   ↓
Platform runs application
```

The provider handles much more of the underlying environment.

---

# 8. PaaS Security

The provider normally takes responsibility for more infrastructure than with IaaS.

However, the customer still needs to secure:

- Application code
    
- Application authentication
    
- Application authorization
    
- Secrets
    
- API keys
    
- Data
    
- Application configuration
    
- User access
    

### Example

A company deploys a web application to a PaaS platform.

The underlying operating system is compromised because of a platform-level vulnerability.

That is generally a provider-side concern.

But if the developer writes:

```text
/admin/delete-all-users
```

without proper authentication, that's a **customer application-security problem**.

---

# 9. SaaS — Software as a Service

## Definition

SaaS provides a **complete software application to the customer through the Internet**.

The customer doesn't need to install and maintain the underlying infrastructure.

Examples:

- Gmail
    
- Google Docs
    
- Slack
    
- Zoom
    
- Dropbox
    
- Microsoft Intune
    
- Microsoft 365
    

The customer typically interacts with the application rather than the underlying infrastructure.

---

# 10. SaaS Example

Consider Gmail.

You don't manage:

- Gmail servers
    
- Gmail operating systems
    
- Gmail database infrastructure
    
- Google's physical data centers
    
- Google's network infrastructure
    

You simply use the application.

Your responsibility is more focused around things such as:

- Your account
    
- Your password
    
- MFA
    
- Access permissions
    
- Data handling
    
- Organization configuration
    

---

# 11. Comparing IaaS, PaaS and SaaS

Think about the technology stack:

```text
                 IaaS       PaaS       SaaS

Application       YOU        YOU       PROVIDER

Data              YOU        YOU       YOU*

Runtime           YOU       PROVIDER   PROVIDER

Operating System  YOU       PROVIDER   PROVIDER

Virtualization    PROVIDER  PROVIDER   PROVIDER

Hardware          PROVIDER  PROVIDER   PROVIDER
```

`*` The customer still has responsibilities concerning the data they put into and configure within the SaaS service.

The exact responsibility boundary varies between providers.

### Simple memory method

```text
IaaS → I manage infrastructure above the provider layer

PaaS → I manage my application

SaaS → I use the software
```

---

# 12. The "As-a-Service" Concept

The phrase **"as a service"** means that some portion of the traditional management burden is abstracted away from you.

For example:

### Traditional

```text
Physical server
      ↓
Operating system
      ↓
Runtime
      ↓
Application
      ↓
User
```

You manage almost everything.

### SaaS

```text
Cloud provider
      ↓
Complete application
      ↓
User
```

The provider manages almost the entire technology stack.

Therefore:

> **The more managed the service, the less infrastructure the customer directly controls — but this can also mean less visibility.**

That last point is extremely important for security analysts.

---

# 13. Security of the Cloud

Now we move from **cloud computing** into **cloud security**.

There are two concepts you must keep separate:

### Security OF the cloud

and

### Security IN the cloud

---

# 14. Security OF the Cloud

**Security of the cloud** refers to protecting the cloud provider's underlying infrastructure.

This can include:

- Physical data centers
    
- Physical servers
    
- Physical networking
    
- Storage infrastructure
    
- Virtualization infrastructure
    
- Core cloud platform
    
- Provider infrastructure
    

The cloud provider is primarily responsible for this layer.

---

## Example

Suppose an organization uses AWS.

The organization doesn't physically control:

```text
AWS Data Center
       ↓
Physical Server
       ↓
Physical Network
       ↓
Power
       ↓
Cooling
```

AWS must protect those systems.

The customer cannot simply walk into the AWS data center and install an EDR agent on the physical server.

That's provider infrastructure.

---

# 15. Security IN the Cloud

Security **in the cloud** means protecting the resources that the customer operates inside the cloud.

Examples:

- Virtual machines
    
- Cloud storage
    
- Databases
    
- Applications
    
- IAM accounts
    
- API keys
    
- Secrets
    
- Security groups
    
- Cloud configurations
    
- Cloud workloads
    

This remains the customer's responsibility to varying degrees depending on the service model.

---

# 16. Shared Responsibility Model

The **Shared Responsibility Model** explains the division of security responsibilities between:

```text
Cloud Provider
       +
Cloud Customer
```

It is one of the most important concepts in cloud security.

---

## Provider responsibility

Generally includes things such as:

- Physical infrastructure
    
- Data center security
    
- Hardware
    
- Core cloud infrastructure
    
- Underlying virtualization/platform
    

---

## Customer responsibility

Depending on the service:

- Identity
    
- Access management
    
- Credentials
    
- Data
    
- Application security
    
- Configuration
    
- OS security
    
- Network controls
    
- Permissions
    
- Secrets
    

---

# 17. Responsibility Changes With Service Model

This is where students often get confused.

### IaaS

Customer has **more responsibility**.

```text
Provider
Hardware
Virtualization

Customer
OS
Applications
Data
IAM
Configuration
```

### PaaS

Provider manages more.

```text
Provider
Hardware
Virtualization
OS
Runtime
Platform

Customer
Application
Data
Configuration
IAM
```

### SaaS

Provider manages most infrastructure.

```text
Provider
Infrastructure
OS
Application
Platform

Customer
Users
Data
Configuration
Access
```

Therefore:

> **Moving from IaaS → PaaS → SaaS generally shifts more infrastructure responsibility to the provider.**

# 18. Cloud Does Not Mean Automatically Secure

This is one of the most important lessons.

A common misconception is:

> "AWS is secure, therefore my AWS environment is secure."

That is wrong.

The cloud provider can have extremely strong infrastructure security while the customer has:

- Public storage
    
- Weak passwords
    
- Excessive permissions
    
- Exposed APIs
    
- Leaked credentials
    
- Poor logging
    
- Insecure applications
    
- Misconfigured firewalls
    

---

# 19. Cloud Misconfiguration

Cloud misconfiguration is one of the major security risks.

Examples:

### Public storage

```text
Private bucket
      ↓
Incorrect permission
      ↓
Publicly accessible
      ↓
Sensitive data exposed
```

### Open management port

```text
Security Group
      ↓
TCP/22
      ↓
0.0.0.0/0
```

Now SSH may be exposed to the Internet.

### Excessive permissions

```text
Developer
   ↓
Administrator permissions
   ↓
Developer account compromised
   ↓
Attacker obtains administrative capabilities
```

The underlying cloud provider may be functioning correctly.

The problem is the **customer's configuration**.

---

# 20. Cloud Supply Chain Risk

Cloud providers are part of your organization's technology supply chain.

If a cloud provider or SaaS provider suffers a serious compromise, customers can potentially be affected.

This creates:

> **Third-party / supply-chain risk**

Your organization may have excellent security controls, but you still depend on:

```text
Your Organization
       ↓
Cloud Provider
       ↓
Cloud Infrastructure
       ↓
Third-party services
```

A compromise somewhere in that chain can affect you.

---

# 21. Why Cloud Visibility Is Difficult

This is especially important for SOC analysts.

In an on-prem environment, the organization might control:

- Servers
    
- Network devices
    
- Firewalls
    
- Endpoint agents
    
- Operating systems
    
- Applications
    
- Logs
    

Therefore, the SOC can potentially collect a lot of telemetry.

Cloud changes this.

You are using infrastructure operated by another organization.

You generally cannot inspect the provider's internal environment.

---

# 22. SaaS Visibility Problem

Consider a SaaS application.

Your organization might see:

```text
User login
User logout
File download
Administrative action
```

But you may **not** see:

```text
Provider server process
Provider internal network traffic
Provider hypervisor events
Provider internal authentication systems
Provider internal database activity
```

That infrastructure belongs to the SaaS provider.

This creates a major security challenge:

> **You can only investigate what the provider exposes to you.**

---

# 23. Cloud Logging

Because you cannot simply install traditional monitoring agents everywhere, you often depend on **cloud-native logging mechanisms**.

Examples include:

- Cloud audit logs
    
- Identity logs
    
- API activity logs
    
- Administrative logs
    
- Application logs
    
- Network logs
    
- Storage access logs
    

These logs can then be forwarded to a SIEM.

---

# 24. Cloud Logging Architecture

A simplified architecture:

```text
             Cloud Environment
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      IAM          API       Storage
      Logs        Logs        Logs
        │           │           │
        └───────────┼───────────┘
                    ↓
              Log Collection
                    ↓
                   SIEM
                    ↓
             Detection Rules
                    ↓
                  Alert
                    ↓
               SOC Analyst
```

This is the kind of architecture you should understand as a SOC analyst.

---

# 25. Problems With Cloud Logging

Cloud logging has several challenges.

## 25.1 Paid logging

Some cloud providers charge for:

- Log ingestion
    
- Log storage
    
- Retention
    
- SIEM integration
    
- Advanced security telemetry
    

Organizations may therefore enable only selected logging.

---

## 25.2 Poor log format

Some services may provide logs that are:

- Incomplete
    
- Difficult to interpret
    
- Inconsistent
    
- Poorly documented
    

This makes detection engineering harder.

---

## 25.3 Lack of integration

Some SaaS applications may have:

- Limited APIs
    
- Limited SIEM integrations
    
- No useful security logs
    
- Restricted audit data
    

This can create a visibility gap.

# 26. Shadow IT

**Shadow IT** means employees use technology or services that have not been formally approved or controlled by the organization.

Cloud makes shadow IT extremely easy.

Example:

```text
Employee
   ↓
Needs to share sensitive document
   ↓
Creates personal cloud account
   ↓
Uploads document
   ↓
Security team doesn't know
```

Potential consequences:

- Data leakage
    
- Regulatory violations
    
- Loss of visibility
    
- Unauthorized access
    
- Data retention problems
    
- Third-party risk
    

---

# 27. OAuth and Cloud Security

Modern SaaS applications frequently use OAuth.

OAuth allows an application to obtain authorized access to resources without necessarily receiving the user's password.

This creates another attack surface.

Example:

```text
User
 ↓
Approves malicious OAuth application
 ↓
Application receives token
 ↓
Attacker uses token
 ↓
Accesses cloud resources
```

This is why SOC teams should monitor:

- New OAuth applications
    
- Suspicious OAuth grants
    
- Unusual token activity
    
- High-risk permissions
    
- Unusual application access
    

---

# 28. Cloud Credentials

Cloud environments heavily depend on identity.

Examples:

- Username/password
    
- MFA
    
- API keys
    
- Access tokens
    
- Service accounts
    
- OAuth tokens
    
- Role credentials
    

A stolen cloud credential can be extremely dangerous.

Example:

```text
Developer
    ↓
AWS access key
    ↓
Committed to GitHub
    ↓
Attacker discovers key
    ↓
Authenticates to cloud
    ↓
Enumerates resources
    ↓
Attempts privilege escalation
    ↓
Accesses data
```

Therefore:

> **Identity is one of the most important security boundaries in cloud environments.**

---

# 29. Least Privilege

Cloud environments should follow the principle of:

> **Least privilege**

Users and applications should receive only the permissions they actually need.

Bad:

```text
Developer
   ↓
Full Administrator
```

Better:

```text
Developer
   ↓
Only permissions required
   ↓
Specific resources
```

Why?

Because if the account is compromised:

```text
More privileges
      ↓
Greater attacker capability
      ↓
Greater blast radius
```

---

# 30. Cloud Attack Surface

A cloud environment can expose several attack surfaces.

### Identity

- User accounts
    
- Service accounts
    
- API keys
    
- Tokens
    
- OAuth applications
    

### APIs

Cloud services are heavily API-driven.

Attackers may abuse APIs to:

- Enumerate resources
    
- Modify configurations
    
- Create accounts
    
- Change permissions
    
- Access data
    

### Storage

Examples:

- Object storage
    
- Cloud drives
    
- Databases
    

Misconfigured storage can expose sensitive information.

### Network

Examples:

- Public IPs
    
- Security groups
    
- Firewall rules
    
- Load balancers
    

### Applications

Cloud-hosted applications can still contain:

- SQL injection
    
- Authentication flaws
    
- Authorization flaws
    
- SSRF
    
- RCE
    
- Broken access control
    

Cloud doesn't magically eliminate traditional application vulnerabilities.

---

# 31. Cloud Migration Pitfalls

A dangerous misconception is:

> "If we move the server to the cloud, it becomes secure."

No.

Suppose you have:

```text
Old server
↓
Unpatched OS
↓
Weak credentials
↓
Vulnerable application
```

You migrate it:

```text
AWS VM
↓
Same unpatched OS
↓
Same weak credentials
↓
Same vulnerable application
```

You have simply moved the problem.

---

# 32. Cloud Requires Different Security Thinking

Traditional security controls may not be sufficient by themselves.

For example:

```text
Traditional environment
        ↓
Internal network
        ↓
Users inside network
        ↓
Perimeter security
```

Cloud environments often look more like:

```text
Internet
   ↓
Cloud identity
   ↓
API
   ↓
Cloud resource
```

The identity itself becomes a major security boundary.

This is closely related to **Zero Trust principles**.

# 33. Cloud Incident Detection

A SOC should monitor several categories.

## Authentication

Look for:

- Failed logins
    
- Successful logins
    
- Impossible travel
    
- New locations
    
- Unusual devices
    
- MFA changes
    
- Password changes
    

---

## Identity and IAM

Look for:

- New users
    
- New roles
    
- New service accounts
    
- Permission changes
    
- Privilege escalation
    
- New API keys
    

---

## Administrative actions

Look for:

- Security group modifications
    
- Firewall changes
    
- IAM policy changes
    
- Logging disabled
    
- Encryption disabled
    
- Storage permissions changed
    

---

## Data access

Look for:

- Large downloads
    
- Unusual data access
    
- Access from unusual locations
    
- Access to sensitive storage
    
- Bulk file operations

# 34. Example Detection Scenario

Imagine:

```text
01:00
User normally works in India

02:00
New login from foreign IP

02:02
MFA configuration changed

02:04
New API key created

02:06
User granted administrator privileges

02:10
Large amount of cloud storage accessed
```

A SOC analyst should immediately recognize this as highly suspicious.

The sequence is:

```text
Compromised identity
       ↓
Persistence / credential manipulation
       ↓
Privilege escalation
       ↓
Cloud resource access
       ↓
Potential data theft
```

This is much more valuable than looking at each event independently.

# 35. Cloud Incident Investigation Method

When investigating a cloud alert, think systematically.

### Step 1 — Identify the identity

Who performed the activity?

```text
Username
Account
Service account
Role
Application
```

---

### Step 2 — Identify the source

Where did the activity originate?

```text
IP address
Country
ASN
Device
Application
User agent
```

---

### Step 3 — Determine authentication method

How did they authenticate?

```text
Password
MFA
API key
OAuth token
Service account
Role
```

---

### Step 4 — Determine what changed

Look for:

- IAM changes
    
- Security-group changes
    
- Firewall changes
    
- Storage permissions
    
- Logging configuration
    
- Account changes
    

---

### Step 5 — Determine what was accessed

Ask:

> What resources did the identity access?

Examples:

- S3/object storage
    
- Database
    
- VM
    
- Secrets
    
- Files
    
- Cloud console
    

---

### Step 6 — Determine what the attacker did

Possible actions:

```text
Read
Create
Modify
Delete
Download
Upload
Execute
Privilege escalation
```

---

### Step 7 — Determine persistence

Attackers may create:

- New accounts
    
- API keys
    
- Service accounts
    
- OAuth applications
    
- Roles
    
- Backdoors
    

---

### Step 8 — Determine data exposure

Ask:

> Was sensitive data accessed or exfiltrated?

Look for:

- Large downloads
    
- Bulk queries
    
- Unusual file access
    
- External transfers

# 36. Cloud Security Incident Examples

The lesson gives several real-world examples. You don't need to memorize every date and company for SOC interviews.

Instead, memorize the **attack pattern**.

### Pattern 1 — SaaS compromise

```text
SaaS provider compromised
        ↓
Attacker gains access to customer-related information
        ↓
Customer sessions/tokens potentially exposed
        ↓
Customer tenants targeted
```

### Pattern 2 — Cloud platform vulnerability

```text
Cloud platform vulnerability
        ↓
Unauthorized access
        ↓
Restricted resources exposed
```

### Pattern 3 — Customer misconfiguration

```text
Customer misconfiguration
        ↓
Resource becomes accessible
        ↓
Attacker discovers resource
        ↓
Sensitive data accessed
```
