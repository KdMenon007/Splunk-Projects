# AWS IAM, Credentials & Cloud Identity 

This section is **one of the most important parts of AWS security for a SOC analyst**.

The central idea is:

> **In AWS, identity is a major security boundary. If an attacker obtains valid AWS credentials, they may not need malware or an exploit. They can simply use AWS legitimately from the cloud's perspective.**

That makes IAM monitoring extremely important.

---

# 1. What Is AWS IAM?

**IAM = Identity and Access Management.**

IAM is a core AWS capability used to control:

- Who can access AWS
    
- How they authenticate
    
- What they can access
    
- What actions they can perform
    
- Which AWS resources they can use
    
- Which AWS services can act on behalf of other services
    

Think of IAM as the AWS equivalent of the identity/access-control layer you might know from Active Directory.

A simplified model:

```text
                    AWS IAM
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      Users          Roles          Groups
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                    Policies
                       ↓
                 Permissions
                       ↓
                AWS Resources
```

---

# 2. The Four Important IAM Components

You need to understand four terms clearly:

1. IAM User
    
2. IAM Group
    
3. IAM Role
    
4. IAM Policy
    

---

# 3. IAM User

An **IAM User** represents an identity that requires AWS access.

It can represent:

- A human user
    
- An application identity
    
- A legacy integration
    

Example:

```text
john.doe
sarah.smith
developer01
```

A user can have credentials such as:

- Password for console access
    
- Access keys for programmatic access
    

A user can also receive permissions through:

- Directly attached policies
    
- Group membership
    

---

# 4. IAM User vs Active Directory User

If you're familiar with Windows/AD:

```text
Active Directory
       ↓
User
       ↓
Group
       ↓
Permissions
```

AWS IAM has a similar conceptual structure:

```text
AWS IAM
   ↓
IAM User
   ↓
IAM Group
   ↓
IAM Policy
   ↓
AWS Permissions
```

But don't assume IAM is simply "AWS Active Directory."

They solve similar identity/access problems but operate differently.

---

# 5. IAM Group

An IAM Group is a **collection of IAM users**.

Example:

```text
                    IT-Support
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
       John           Sarah          Mike
          │             │             │
          └─────────────┼─────────────┘
                        ↓
                  Shared Policies
```

Instead of assigning the same permissions individually to 50 users, you can place them into a group and assign appropriate permissions to that group.

Examples:

```text
EU-IT-Team
Developers
Security-Analysts
Database-Admins
Contractors
```

---

# 6. IAM Policy

An IAM policy defines:

> **What actions an identity is allowed or denied to perform.**

Policies are typically JSON documents.

Conceptually:

```text
WHO?
 ↓
Identity

WHAT?
 ↓
Action

WHERE?
 ↓
Resource

ALLOW/DENY?
 ↓
Effect
```

For example:

```text
Allow
  ↓
s3:GetObject
  ↓
specific bucket
```

means the identity can retrieve objects from that specified resource, subject to the rest of AWS authorization controls.

---

# 7. IAM Role

An **IAM Role** is different from a normal IAM user.

A role is an identity that can be **assumed** by another trusted identity or service.

Think:

```text
User / EC2 / Lambda / Federated Identity
              ↓
         AssumeRole
              ↓
          IAM Role
              ↓
       Temporary Credentials
              ↓
        AWS API Actions
```

Roles are extremely important because modern AWS environments heavily rely on them.

---

# 8. IAM User vs IAM Role

This distinction is critical.

### IAM User

Generally represents a persistent identity.

Example:

```text
john.doe
```

May have:

```text
Password
Access keys
```

### IAM Role

Represents a set of permissions that can be assumed.

Example:

```text
ProductionDatabaseReadOnly
```

The role doesn't normally function like a person permanently logging into it.

Instead:

```text
John
 ↓
AssumeRole
 ↓
ProductionDatabaseReadOnly
 ↓
Temporary credentials
```

---

# 9. Why Roles Are Preferred for Workloads

Imagine an EC2 application needs to read images from S3.

Bad architecture:

```text
EC2
 ↓
Hardcoded AWS access key
 ↓
S3
```

Example source code:

```text
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

This is dangerous.

If an attacker obtains the key:

```text
Attacker
   ↓
Stolen access key
   ↓
AWS
   ↓
Same permissions as application
```

---

# 10. Better Architecture: IAM Role

Instead:

```text
EC2
 ↓
IAM Role
 ↓
Temporary credentials
 ↓
S3
```

The EC2 instance receives permissions through the role.

No developer needs to hardcode a permanent access key into the application.

This is one of the major advantages of IAM roles.

---

# 11. Role Trust Policy vs Permission Policy

This is a subtle but **very important** concept.

An IAM role involves two separate ideas:

### Trust policy

Answers:

> **Who is allowed to assume this role?**

Example:

```text
EC2 service
       ↓
Allowed to assume
       ↓
UserAvatarsProcessor
```

### Permissions policy

Answers:

> **What can the role do after it has been assumed?**

Example:

```text
UserAvatarsProcessor
       ↓
s3:GetObject
       ↓
user-avatars bucket
```

So:

```text
Trust Policy
    ↓
WHO can assume?

Permissions Policy
    ↓
WHAT can they do?
```

Do not mix these two.

---

# 12. Temporary Credentials

When a role is assumed, AWS can provide **temporary security credentials** through AWS Security Token Service (STS).

Conceptually:

```text
Identity
   ↓
AssumeRole
   ↓
AWS STS
   ↓
Temporary credentials
   ↓
AWS API calls
```

These credentials are generally short-lived compared with long-term IAM user credentials.

---

# 13. Why Temporary Credentials Are Safer

Suppose an attacker steals a permanent access key.

If it remains valid:

```text
Day 1 → stolen
Day 2 → usable
Day 30 → usable
Day 100 → potentially usable
```

unless revoked/rotated/disabled.

Temporary credentials have an expiration time.

Conceptually:

```text
AssumeRole
    ↓
Temporary credential
    ↓
Valid for limited period
    ↓
Expires
```

This reduces the window of opportunity.

However:

> **Temporary credentials can still be stolen and abused while they are valid.**

So don't treat STS as magical armor.

---

# 14. Why Hardcoded Credentials Are Dangerous

Developers may accidentally place credentials in:

- Source code
    
- `.env` files
    
- Configuration files
    
- CI/CD systems
    
- Databases
    
- Scripts
    
- Docker images
    
- Public repositories
    
- Logs
    

Example:

```text
application.py
      ↓
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
      ↓
GitHub
      ↓
Attacker
```

This is a major cloud security risk.

---

# 15. AWS Console Authentication

The AWS Management Console is the graphical web interface.

A user can authenticate using appropriate AWS identity mechanisms.

A simplified IAM-user scenario:

```text
AWS Account
    ↓
IAM User
    ↓
Username
Password
MFA
    ↓
AWS Console
```

After authentication, the user can perform whatever actions their effective permissions allow.

---

# 16. Root User vs IAM User

AWS accounts have a **root user**.

The root identity has extremely powerful privileges.

It should not be used for normal daily administration.

Bad:

```text
Root
 ↓
Daily administration
 ↓
Create VM
 ↓
Modify IAM
 ↓
Manage S3
```

Better:

```text
Root
 ↓
Emergency / account-level tasks
```

and:

```text
IAM / federated identity
 ↓
Normal administration
```

---

# 17. Why Root User Monitoring Is Critical

Root account activity should be rare.

Therefore:

```text
Root login
    ↓
Alert
    ↓
Investigate
```

And root access-key creation is particularly concerning.

From a SOC perspective:

> **Root activity is high-value telemetry because legitimate root usage should be uncommon.**

---

# 18. MFA

**MFA = Multi-Factor Authentication.**

It adds another authentication factor beyond a password.

For example:

```text
Password
   +
MFA
   ↓
Authentication
```

MFA significantly reduces the risk of password-only account compromise.

However:

> **MFA does not eliminate phishing, token theft, session theft, or credential abuse.**

Attackers can sometimes steal valid authenticated sessions or trick users into approving malicious authentication flows.

---

# 19. IAM Access Keys

Access keys are used for **programmatic AWS access**.

Examples:

- AWS CLI
    
- AWS SDK
    
- Python/Boto3
    
- Terraform
    
- Automation scripts
    
- CI/CD systems
    

Instead of:

```text
Username
Password
```

the application uses credentials associated with API requests.

---

# 20. Access Key Components

An access key has two important components:

```text
Access Key ID
+
Secret Access Key
```

The **Access Key ID** is an identifier and isn't itself a password.

The **Secret Access Key** must be treated as confidential.

Think:

```text
Access Key ID
     ↓
Username-like identifier

Secret Access Key
     ↓
Secret credential
```

Never expose the secret publicly.

---

# 21. AWS CLI Example

A developer may configure credentials for the AWS CLI and then execute:

```text
aws s3 ls
```

The command causes AWS API requests.

For example:

```text
Developer
   ↓
AWS CLI
   ↓
AWS API
   ↓
S3
```

The SOC sees the resulting AWS API activity in CloudTrail.

---

# 22. Why Access Keys Are Dangerous

The problem isn't simply that access keys exist.

The problem is:

> **Long-lived credentials can be copied.**

For example:

```text
Developer laptop
      ↓
Access key
      ↓
Git repository
      ↓
Public exposure
      ↓
Attacker
```

Or:

```text
CI/CD server
      ↓
Access key
      ↓
Compromised CI/CD
      ↓
Attacker obtains credential
```

Once stolen, the attacker can potentially use the credential from somewhere else.

---

# 23. Access Key Attack Chain

A common attack pattern:

```text
Credential exposed
       ↓
Attacker discovers credential
       ↓
AWS authentication
       ↓
Cloud enumeration
       ↓
Permission discovery
       ↓
Privilege escalation
       ↓
Data access
       ↓
Persistence
       ↓
Exfiltration
```

This is why access-key monitoring is so important.

---

# 24. Console Login vs Access-Key Activity

This is one of the most important SOC concepts in this section.

### Console

A human logs into the AWS Management Console.

CloudTrail can record:

```text
ConsoleLogin
```

### Access key

A program makes an API request.

There isn't necessarily a separate "login" event first.

Instead:

```text
AWS CLI
 ↓
API request
 ↓
CloudTrail event
```

Therefore:

> **You should not expect `ConsoleLogin` for normal access-key API activity.**

---

# 25. Why This Matters During Investigation

Suppose you find:

```text
DeleteDBInstance
```

You need to determine:

> **How did the attacker perform it?**

Possibilities:

### Phished console session

```text
Phishing
 ↓
Victim logs into fake page
 ↓
Attacker obtains credentials/session
 ↓
AWS Console
 ↓
DeleteDBInstance
```

### Leaked access key

```text
Access key exposed
 ↓
Attacker
 ↓
AWS CLI
 ↓
DeleteDBInstance
```

The final action may be similar, but the **root cause is completely different**.

---

# 26. Console Activity Often Has More Noise

When a human uses the AWS console, the browser performs many background API requests.

You might see:

```text
ConsoleLogin
GetCallerIdentity
List...
Describe...
Get...
List...
Describe...
DeleteDBInstance
```

The console needs this information to display the AWS interface.

---

# 27. CLI Activity Can Be More Direct

With the CLI:

```text
aws rds delete-db-instance ...
```

you may see the actual operation without the large sequence of console UI discovery calls.

Conceptually:

```text
Console:

Login
 ↓
List
 ↓
Describe
 ↓
Get
 ↓
List
 ↓
Delete


CLI:

Delete
```

This distinction can help determine how an action was performed.

---

# 28. Identifying Access-Key Activity

The lesson provides this Splunk example:

```spl
index=aws userIdentity.accessKeyId=AKIA*
```

The idea is to identify events associated with long-term access-key-style identifiers.

Another approach from the lesson:

```spl
index=aws NOT userIdentity.sessionContext.attributes.creationDate=*
```

This is useful as a heuristic for filtering out certain console/session activity.

But don't treat these queries as universal AWS truth.

Your actual CloudTrail schema and ingestion pipeline matter.

---

# 29. User-Agent

The `userAgent` field is extremely useful.

It can tell you what software generated the API request.

Examples:

```text
aws-cli/...
aws-sdk-java/...
Boto3/...
```

Suppose a service normally uses:

```text
aws-sdk-java
```

and suddenly you see:

```text
aws-cli
```

That should make you ask:

> Why did the client change?

It could be:

- Legitimate migration
    
- New automation
    
- Developer troubleshooting
    
- Incident response
    

or:

- Compromised credential
    
- Attacker using CLI
    

The log doesn't tell you which one automatically.

---

# 30. User-Agent Is Context, Not Verdict

Never build a detection like:

```text
Boto3 = attacker
```

That's terrible detection logic.

Instead:

```text
Unexpected Boto3
+
Unusual IP
+
Unusual time
+
Unexpected API action
+
Service account
```

Now you have something interesting.

---

# 31. Service Accounts and Automation

This is where cloud SOC investigations become tricky.

Consider:

```text
svc-s3-backup
```

The account's job is:

> Back up S3 data.

Normally:

```text
svc-s3-backup
 ↓
S3
 ↓
Read/write backup objects
```

Suddenly:

```text
svc-s3-backup
 ↓
EC2
 ↓
RunInstances
```

That's suspicious.

Why?

Because the action doesn't match the identity's expected purpose.

---

# 32. User Purpose vs Action

This is a very powerful detection principle.

Ask:

> **Does the action make sense for this identity?**

Examples:

### Normal

```text
svc-s3-backup
 ↓
S3
 ↓
PutObject
```

### Suspicious

```text
svc-s3-backup
 ↓
IAM
 ↓
CreateAccessKey
```

### Very suspicious

```text
svc-s3-backup
 ↓
IAM
 ↓
CreateUser
 ↓
AttachAdministratorAccess
```

The identity's **business purpose** provides context.

---

# 33. Source IP Investigation

Another major signal is the source IP.

Suppose:

```text
svc-gitlab-cicd
```

has operated for years from:

```text
GitLab infrastructure
```

Suddenly:

```text
DigitalOcean IP
```

appears.

That doesn't automatically mean compromise.

But it is an anomaly worth investigating.

Ask:

- Was CI/CD infrastructure migrated?
    
- Was a new runner deployed?
    
- Is the IP legitimate?
    
- Is it a known corporate infrastructure range?
    
- Has the service account been compromised?
    

---

# 34. Role-Based Authentication

IAM roles are heavily used by AWS services.

Example:

```text
EC2
 ↓
UserAvatarsProcessor role
 ↓
S3
```

The EC2 workload assumes the role and obtains temporary credentials.

This is much better than embedding a permanent access key in application code.

---

# 35. CloudTrail Role Activity

A role-based event might look conceptually like:

```text
userIdentity.type = AssumedRole
```

Example ARN:

```text
arn:aws:sts::398985017225:assumed-role/UserAvatarsProcessor/i-123456789
```

Break this down:

```text
AWS Account
      ↓
398985017225

Role
      ↓
UserAvatarsProcessor

Session
      ↓
i-123456789
```

---

# 36. `AssumedRole`

When you see:

```text
userIdentity.type = AssumedRole
```

think:

> **"Someone or something assumed an IAM role and is now operating with that role's permissions."**

The role itself isn't necessarily the original actor.

You need to identify:

> **Who or what assumed the role?**

---

# 37. Role Session Name

The final component of an assumed-role ARN is the session name.

Example:

```text
arn:aws:sts::398985017225:assumed-role/UserAvatarsProcessor/i-123456789
```

Here:

```text
Role:
UserAvatarsProcessor

Session:
i-123456789
```

For an EC2 workload, this can often correspond to an instance identifier.

Another example:

```text
arn:aws:sts::398985017225:assumed-role/US-ITSupportRole/john.doe
```

This suggests:

```text
Role = US-ITSupportRole
Session = john.doe
```

---

# 38. Custom Session Names

Attackers or legitimate users can potentially use custom session names.

Example:

```text
arn:aws:sts::398985017225:assumed-role/SuperAdmin/MyCustomSession
```

Now:

```text
MyCustomSession
```

doesn't tell you who the real actor is.

So you must investigate the **AssumeRole event**.

---

# 39. AssumeRole Event

This is one of the most important investigation concepts.

Suppose:

```text
john.doe
   ↓
AssumeRole
   ↓
SuperAdmin
   ↓
DeleteDatabase
```

The final event might only show:

```text
AssumedRole
SuperAdmin
```

You need to go backward.

```text
DeleteDatabase
      ↑
SuperAdmin role
      ↑
AssumeRole
      ↑
john.doe
```

That process is essentially:

> **Tracing role activity back to the original identity.**

---

# 40. AssumeRole Investigation

The `AssumeRole` event can contain:

```text
eventName = AssumeRole
sourceIPAddress
userAgent
roleArn
roleSessionName
userIdentity
```

Example:

```text
roleArn = arn:aws:iam::398985017225:role/SuperAdmin

roleSessionName = MyCustomSession

userIdentity = john.doe
```

Now you know:

```text
john.doe
   ↓
assumed
   ↓
SuperAdmin
   ↓
MyCustomSession
```

That gives you **patient zero** for the role activity.

---

# 41. Why Patient Zero Matters

Suppose an alert says:

```text
SuperAdmin
 ↓
DeleteDBInstance
```

That's not enough.

You need to answer:

> Who obtained SuperAdmin?

Possible sources:

```text
Human user
EC2 instance
Lambda function
Federated user
Another role
Compromised service
```

Without identifying the source identity, your investigation is incomplete.

---

# 42. Role Chaining

Large AWS environments often have multiple roles.

Example:

```text
Sarah
  ↓
AssumeRole
  ↓
US-ITSupport
  ↓
AssumeRole
  ↓
EU-Helpdesk
  ↓
AssumeRole
  ↓
RDS-ReadOnly
  ↓
Database
```

This is called **role chaining**.

The SOC has to follow the chain backward.

```text
Database activity
       ↑
RDS-ReadOnly
       ↑
EU-Helpdesk
       ↑
US-ITSupport
       ↑
Sarah
```

The final role may not tell you the original human identity.

---

# 43. IAM Role Abuse

IAM roles can become an attack path.

Imagine:

```text
Internet
   ↓
Vulnerable EC2
   ↓
Attacker gains code execution
   ↓
EC2 has IAM role
   ↓
Role has S3 permissions
   ↓
Attacker accesses S3
```

The attacker doesn't need to steal an access key.

They can potentially inherit the permissions available to the compromised workload through its role.

This is a critical cloud attack concept.

---

# 44. Why EC2 IAM Roles Need Protection

Suppose:

```text
EC2
 ↓
AvatarProcessor role
 ↓
S3:GetObject
```

If the EC2 is compromised:

```text
Attacker
 ↓
EC2 compromise
 ↓
Access workload credentials
 ↓
Role permissions
 ↓
S3
```

Therefore:

> **Protecting the workload is also protecting the cloud identity attached to it.**

---

# 45. Least Privilege for Roles

Don't give:

```text
EC2
 ↓
AdministratorAccess
```

if it only needs:

```text
S3:GetObject
```

Better:

```text
EC2
 ↓
AvatarProcessor
 ↓
s3:GetObject
 ↓
specific bucket
```

This reduces the blast radius.

---

# 46. Monitoring IAM Role Abuse

Important signals include:

### User-agent changes

```text
Normal:
Boto3

Suddenly:
aws-cli
```

### First-seen API calls

Example:

```text
Role normally:
GetObject

Suddenly:
ListUsers
CreateAccessKey
PutRolePolicy
```

### Unexpected data access

Example:

```text
Application role
 ↓
Large S3 downloads
```

### Workload compromise

If the role belongs to EC2:

```text

+

=
Potential cloud compromise
```

# 47. Cross-Account Access

Large organizations often have multiple AWS accounts.

Example:

```text
Production Account
Development Account
Security Account
EU Account
US Account
Logging Account
```

IAM roles allow users or services to move between accounts when authorized.

Example:

```text
Sarah
 ↓
US account
 ↓
it-support role
 ↓
EU account
 ↓
eu-helpdesk role
 ↓
rds-read role
```

---

# 48. Why Cross-Account Access Is Important

Cross-account activity can be completely legitimate.

But if an attacker compromises a user who has cross-account permissions:

```text
Compromised User
       ↓
AssumeRole
       ↓
Account A
       ↓
AssumeRole
       ↓
Account B
       ↓
Sensitive resource
```

the attacker can potentially move across the organization's AWS environment.

This makes **AssumeRole monitoring** important.

---

# 49. Early Threat Detection

One of the best lessons here is:

> **Don't wait for the final attack.**

Imagine:

```text
2023
Root access key created
        ↓
2023
Key accidentally exposed
        ↓
2024
Nobody notices
        ↓
2025
Attacker discovers key
        ↓
Cloud compromise
```

The actual opportunity for prevention existed in **2023**.

Therefore SOC/security teams should monitor not only:

```text
Compromise
```

but also:

```text
Risky configuration
Credential creation
Privilege changes
MFA changes
```

---

# 50. Misconfiguration Detection

Security monitoring should detect both:

### Attack activity

```text
Stolen credentials
Suspicious login
Data exfiltration
Privilege escalation
```

and:

### Security weaknesses

```text
Unnecessary access key
Excessive permissions
MFA disabled
Root key created
Public resource
```

The second category provides **early threat detection**.

---

# 51. Important IAM Events

You should recognize these.

|Event|Meaning|Why SOC Cares|
|---|---|---|
|`CreateAccessKey`|Creates an access key|Potential persistence/credential risk|
|`UpdateAccessKey`|Changes access-key status|Could activate a key|
|`AttachUserPolicy`|Policy attached to user|Could grant excessive privileges|
|`AttachRolePolicy`|Policy attached to role|Could increase role privileges|
|`AttachGroupPolicy`|Policy attached to group|Could affect many users|
|`AddUserToGroup`|User added to group|Could inherit privileges|
|`PutUserPolicy`|Inline user policy changed|Permission modification|
|`PutRolePolicy`|Inline role policy changed|Role privilege modification|
|`PutGroupPolicy`|Inline group policy changed|Group permission modification|
|`DeleteVirtualMFADevice`|MFA device deleted|Potential account weakening|
|`DeactivateMFADevice`|MFA disabled|High-risk security change|
|`AssumeRole`|Identity assumes role|Important for attribution|
|`ConsoleLogin`|Console authentication|Identity monitoring|

---

# 52. `CreateAccessKey` Detection

This deserves special attention.

Example:

```text
CreateAccessKey
     ↓
New long-term credential
     ↓
Potential persistence
```

Suppose:

```text
john.doe
 ↓
CreateAccessKey
```

Ask:

- Does John normally use access keys?
    
- Is John a developer?
    
- Is there a change ticket?
    
- Is this a privileged account?
    
- What IP performed the action?
    
- What user agent?
    
- What happened afterward?
    

---

# 53. Access Key as Persistence

Attackers may create a second access key after gaining access.

Example:

```text
Attacker compromises account
        ↓
CreateAccessKey
        ↓
Attacker obtains new credential
        ↓
Original compromised session revoked
        ↓
Attacker still has access
```

This is why access-key creation can be a **persistence mechanism**.

---

# 54. MFA Removal

An attacker may attempt:

```text
Compromised account
       ↓
Deactivate MFA
       ↓
Account becomes easier to access
```

Therefore:

```text
DeactivateMFADevice
```

should receive attention.

But there is an important nuance.

A legitimate user may lose their phone.

They may:

```text
Deactivate old MFA
       ↓
Register new MFA
```

So:

> **A single event isn't enough. Correlate surrounding activity.**

---

# 55. Policy Modification

Suppose a policy is named:

```text
ReadOnlyAccess
```

but someone modifies it to allow:

```text
ec2:RunInstances
ec2:TerminateInstances
iam:CreateUser
iam:AttachUserPolicy
```

The name says "ReadOnly."

The actual permissions say "Administrator."

That's suspicious.

This is why SOC analysts should inspect **actual policy contents**, not blindly trust names.

---

# 56. Group Membership Abuse

Suppose:

```text
Intern
 ↓
AddUserToGroup
 ↓
Administrators
```

The user suddenly inherits powerful permissions.

This can be:

- Misconfiguration
    
- Insider activity
    
- Account compromise
    
- Privilege escalation
    

The detection should consider the user's role and expected access.

# 57. Root Access Keys

Root access keys are especially dangerous.

A mature environment should generally avoid creating root access keys.

Therefore:

```text
Root
 ↓
CreateAccessKey
 ↓
HIGH PRIORITY ALERT
```

This should be investigated immediately.

```text

 ↓

 ↓

 ↓

 ↓

AFTER:

EXPECTED:
No
```

That is a **high-confidence incident**.

# 65. The Most Important Concept in This Entire Section

If you remember only one thing, remember this:

> **AWS attacks are often identity attacks.**

An attacker doesn't always need to exploit a server.

They can simply obtain:

```text
Valid credential
       ↓
AWS authentication
       ↓
Legitimate API calls
       ↓
Cloud resources
```

And because the attacker is using valid credentials, the SOC has to distinguish:

```text
LEGITIMATE IDENTITY ACTIVITY
          vs
MALICIOUS USE OF VALID IDENTITY
```

That is why these fields matter so much:

```text
WHO?
 ↓
userIdentity

WHAT?
 ↓
eventName

WHERE FROM?
 ↓
sourceIPAddress

HOW?
 ↓
userAgent

WHAT RESOURCE?
 ↓
requestParameters

ROLE?
 ↓
AssumedRole / AssumeRole

WHEN?
 ↓
eventTime

WHAT NEXT?
 ↓
Correlated CloudTrail activity
```

That is the **core AWS IAM investigation mindset** you should carry into Splunk and cloud SOC work.
