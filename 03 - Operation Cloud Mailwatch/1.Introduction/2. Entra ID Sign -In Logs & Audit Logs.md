## 1. The investigation has two phases

The lesson is essentially teaching this workflow:

```text
          Suspicious Authentication
                    │
                    ▼
             SIGN-IN LOGS
                    │
          Who? Where? When?
          Success / Failure?
          MFA? Device? App?
                    │
                    ▼
          COMPROMISED ACCOUNT
                    │
                    ▼
              AUDIT LOGS
                    │
          What did attacker change?
          Who performed the change?
          What was modified?
                    │
                    ▼
            M365 SERVICE LOGS
                    │
          What did attacker access?
          Email? Files? Teams?
```

So remember:

> **Sign-in Logs → How did they get in?**  
> **Audit Logs → What did they change?**  
> **M365 Logs → What did they do?**

That's the core mental model.

---

# 2. Sign-in Logs

Sign-in logs are your first stop when investigating authentication attacks.

They can answer:

- Which account was targeted?
    
- Was authentication successful?
    
- Where did it originate?
    
- What IP was used?
    
- Which application was accessed?
    
- Was MFA involved?
    
- What device/browser was used?
    
- What Conditional Access decision occurred?
    

The Splunk starting point is:

```spl
index="scenario" sourcetype="azure:aad:signin"
```

This gives you the authentication universe.

Then you narrow it down.

---

# 3. Understanding the important fields

Don't try to memorize the entire JSON.

Focus on the fields that help answer investigation questions.

|Field|Meaning|Why you care|
|---|---|---|
|`userPrincipalName`|User account|Who authenticated?|
|`createdDateTime`|Event time|When?|
|`ipAddress`|Source IP|Where from?|
|`appDisplayName`|Application|What was accessed?|
|`clientAppUsed`|Client type|Browser/mobile/etc.|
|`conditionalAccessStatus`|CA result|Was policy successful?|
|`isInteractive`|Interactive login|Was a user actively authenticating?|
|`status.errorCode`|Authentication result|Why did it fail/succeed?|
|`location`|Geolocation|Is location suspicious?|
|`appliedConditionalAccessPolicies`|Applied policies|Which security controls acted?|

A useful SOC question is:

> **Does this login look like the user's normal authentication pattern?**

---

# 4. `status.errorCode` is extremely useful

This field helps distinguish successful and unsuccessful authentication.

### Successful

```text
errorCode = 0
```

### Failed

```text
errorCode != 0
```

So this query:

```spl
index="scenario" sourcetype="azure:aad:signin" "status.errorCode"!=0
```

looks for failed authentication events.

The lesson then aggregates them by user:

```spl
| stats count as event_count values(ipAddress) as ip_addresses
  values(appDisplayName) as applications
  values(status.errorCode) as errorCodes
  by userPrincipalName
| sort - event_count
| table applications, userPrincipalName, ip_addresses, errorCodes, event_count
```

This is much more useful than staring at thousands of individual events.

You're effectively asking Splunk:

> **“Show me users experiencing suspicious authentication failures and summarize the characteristics.”**

---

# 5. Error codes: don't just memorize them

The provided examples:

|Error code|Meaning|
|---|---|
|`50126`|Invalid username/password|
|`50053`|Account locked|
|`50074`|MFA required but not provided|
|`50055`|Password expired|

The **pattern** matters more than the number.

For example:

```text
10:01  50126
10:02  50126
10:03  50126
10:04  50126
10:05  50126
10:06  Success
```

That is much more interesting than:

```text
One isolated 50126
```

The first pattern could indicate password guessing or credential abuse.

The second could simply be a legitimate user typing the wrong password.

**Context beats individual events.**

# 6. The IP pivot

This is one of the most important SOC investigation techniques in the entire lesson.

Suppose your failed-login investigation reveals:

```text
User: john.doe@example.com
IP: 203.0.113.45
```

Don't stop there.

Pivot on the IP.

```spl
index="scenario" sourcetype="azure:aad:signin"
"status.errorCode"=0
ipAddress="<ADD-IP-HERE>"
```

Now you're asking:

> **“Did this same source IP successfully authenticate to anyone?”**

That's powerful.

You might discover:

```text
203.0.113.45
      │
      ├── Failed → Alice
      ├── Failed → Bob
      ├── Failed → John
      ├── Failed → Sarah
      └── SUCCESS → John
```

Now you have a much stronger hypothesis:

> The source attempted multiple accounts and eventually succeeded against John.

That's classic **credential attack behavior**.

---

# 7. Why the IP pivot works

You start with an event:

**Failed authentication**

Then extract an indicator:

**Source IP**

Then pivot:

**Source IP → successful authentication**

Then identify:

**Potentially compromised account**

This is a general SOC technique:

> **Event → Indicator → Pivot → Related events → Attack story**

You'll use this pattern constantly in SIEM work.

---

# 8. Then comes Audit Logs

Once you identify a potentially compromised account, don't immediately declare victory.

Ask:

> **What happened after the attacker got access?**

That's where Audit Logs come in.

Query:

```spl
index="scenario" sourcetype="azure:aad:audit"
```

Sign-in logs tell you about **authentication**.

Audit logs tell you about **changes/actions within the identity environment**.

---

# 9. What attackers might change

The lesson highlights several important examples:

### Password changes

An attacker may attempt to modify the password to maintain access.

### Authentication methods

Adding a new authentication method/device can potentially help maintain access.

### Privileged roles

This is extremely serious.

For example:

```text
Compromised User
      │
      ▼
Role assignment
      │
      ▼
Privileged account
      │
      ▼
Tenant-wide impact
```

### User attributes

Attackers may alter identity information.

### Malicious applications

Applications/service principals can be abused to establish access or permissions.

This is why **audit logs are critical for post-compromise investigation**.

---

# 10. Three audit fields you absolutely need to understand

### `activityDisplayName`

**What happened?**

Examples:

> Change user password  
> Disable account  
> Add member to group  
> Assign role

---

### `initiatedBy`

**Who or what performed the action?**

It could be:

```text
User
```

or:

```text
Application / Service Principal
```

This distinction matters enormously.

An action performed by:

> `john.doe@example.com`

is different from an action performed by:

> `Microsoft password reset service`

---

### `targetResources`

**What was affected?**

For example:

```text
Initiator:
attacker@example.com

Activity:
Change user password

Target:
victim@example.com
```

Now you have:

> **Who → did what → to whom**

That's an excellent investigation structure.

---

# 11. The two audit queries answer different questions

This distinction is important.

### Query 1: Changes targeting the compromised user

```spl
index="scenario" sourcetype="azure:aad:audit"
targetResources{}.userPrincipalName="<ADD-USER-EMAIL>"
| eval initiator=coalesce('initiatedBy.user.userPrincipalName',
                           'initiatedBy.app.displayName')
| sort - _time
| table _time, initiator, activityDisplayName, result,
        targetResources{}.userPrincipalName
```

Question being answered:

> **“What happened to this account?”**

---

### Query 2: Changes performed by the compromised user

```spl
index="scenario" sourcetype="azure:aad:audit"
initiatedBy.user.userPrincipalName="<ADD-USER-EMAIL>"
| sort - _time
| table _time,
        initiatedBy.user.userPrincipalName,
        activityDisplayName,
        result,
        targetResources{}.userPrincipalName
```

Question:

> **“What did this account do?”**

These are **not the same investigation**.

That's a subtle but very important point.

---

# 12. Example investigation

Imagine you identify:

```text
Compromised account:
john.doe@example.com

Suspicious IP:
203.0.113.45
```

You then examine audit logs.

You discover:

```text
10:10  john.doe@example.com
      → Add authentication method
      → john.doe@example.com

10:12  john.doe@example.com
      → Add member to privileged group
      → john.doe@example.com

10:15  john.doe@example.com
      → Modify user
      → admin@example.com
```

Now the incident is no longer simply:

> “Someone logged into John's account.”

It becomes:

> **“John's identity was potentially compromised, followed by authentication-method modification and privilege-related changes.”**

That's a materially more serious incident.

# 13. The SOC investigation methodology

For this lesson, I'd memorize this:

```text
1. Detect
   ↓
2. Examine Sign-in Logs
   ↓
3. Identify suspicious IP/account
   ↓
4. Pivot on IP
   ↓
5. Find successful authentication
   ↓
6. Identify compromised identity
   ↓
7. Pivot to Audit Logs
   ↓
8. Determine what changed
   ↓
9. Identify initiator
   ↓
10. Identify target
   ↓
11. Build timeline
   ↓
12. Investigate M365 activity
```

This is much more valuable than memorizing Splunk syntax.

# 14. Interview perspective

If an interviewer asks:

**“How would you investigate a suspected compromised Entra ID account?”**

You can answer:

> “I would begin with Entra ID Sign-in Logs to identify successful and failed authentication attempts, examining the source IP, timestamp, user, application, device, authentication method, MFA result, and Conditional Access outcome. I would correlate failed attempts with subsequent successful authentication and pivot on suspicious indicators such as the source IP. Once I identify a potentially compromised account, I would examine Entra ID Audit Logs to determine what actions were performed after compromise, including password changes, authentication-method changes, group or role assignments, and application changes. I would correlate the initiator, target resource, activity, and timestamps to build a timeline, and then investigate Microsoft 365 service logs to determine what data or services the attacker accessed.”

That's a **SOC L2-quality answer**, not merely “check the logs.”

## The three-log cheat sheet

|Log|Primary question|Key fields|
|---|---|---|
|**Sign-in Logs**|**How did they get in?**|User, IP, time, app, device, MFA, error code|
|**Audit Logs**|**What did they change?**|Initiator, activity, target, modified properties|
|**M365 Logs**|**What did they do?**|Mail, files, Teams, SharePoint activity|

### Final mental model

**Sign-in → Compromise**

**Audit → Persistence / Privilege / Configuration changes**

**M365 → Post-compromise activity / Data access**

And one golden SOC rule:

> **Never treat one authentication event as the entire incident. Build the timeline, pivot on indicators, correlate logs, and determine what happened before and after the suspicious event.**
