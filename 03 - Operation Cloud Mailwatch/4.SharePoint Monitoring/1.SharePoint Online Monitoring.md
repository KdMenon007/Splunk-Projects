
## 1. SharePoint Overview

**SharePoint Online** is Microsoft's cloud-based collaboration and document-management platform within Microsoft 365.

Organizations use it for:

- Documents
    
- Spreadsheets
    
- Contracts
    
- Reports
    
- Customer information
    
- Internal documentation
    
- Project files
    
- Source code
    
- Security documentation
    

From a SOC perspective, SharePoint is important because it contains **valuable corporate data**.

A compromised Microsoft 365 account may therefore provide an attacker with access to SharePoint without requiring the attacker to exploit SharePoint itself.

### Attacker's perspective

```text
Compromise Microsoft 365 account
            ↓
Authenticate through Entra ID
            ↓
Access SharePoint
            ↓
Search valuable files
            ↓
Read / download files
            ↓
Share externally
            ↓
Exfiltrate data
```

---

# 2. SharePoint + Entra ID

SharePoint Online uses Microsoft Entra ID for authentication.

This means you normally need **two perspectives** when investigating an incident:

```text
Entra ID
   ↓
Who authenticated?
   ↓
Microsoft 365 / SharePoint audit
   ↓
What did they do?
```

For example:

```text
10:01  Emily authenticates
10:05  Emily accesses SharePoint
10:08  Emily accesses Finance.xlsx
10:09  Emily downloads Finance.xlsx
```

The first event comes from the identity side.

The later events come from the Microsoft 365 audit side.

---

# 3. Finding SharePoint Activity

The first query you should understand is simply:

```spl
index=m365 Workload=SharePoint
```

### What does it mean?

Break it down:

```text
index=m365
```

Search the Microsoft 365 data.

```text
Workload=SharePoint
```

Only return events generated by SharePoint.

This is your basic starting point.

### Make the output readable

```spl
index=m365 Workload=SharePoint
| table _time UserId Operation SourceFileName ObjectId SiteUrl
| sort _time
```

Now you can see the basic investigation story:

```text
TIME
USER
ACTION
FILE
OBJECT
SITE
```

---

# 4. Important SharePoint Log Fields

A SharePoint event may contain fields such as:

|Field|Meaning|
|---|---|
|`CreationTime`|Time event was generated|
|`Operation`|What happened|
|`Workload`|Microsoft 365 service|
|`UserId`|Account performing action|
|`Site`|SharePoint site identifier|
|`UserAgent`|Client/application information|
|`ClientIP`|IP recorded in event|
|`SourceRelativeUrl`|File/folder location|
|`SourceFileName`|File name|
|`ApplicationDisplayName`|Application used|
|`SiteUrl`|SharePoint site|
|`ObjectId`|Object/file involved|

The most important fields to remember are:

```text
UserId
Operation
ObjectId
SourceFileName
SiteUrl
ApplicationDisplayName
UserAgent
```

---

# 5. `Operation` — What Happened?

The `Operation` field is basically the **action** performed.

Common examples:

```text
FileAccessed
FileDownloaded
FileUploaded
FileCreated
FileModified
FileDeleted
FileRecycled
SharingSet
AddedToSecureLink
AnonymousLinkCreated
SecureLinkUsed
AnonymousLinkUsed
```

You can investigate all operations with:

```spl
index=m365 Workload=SharePoint
| stats count by Operation
| sort - count
```

### Why is this useful?

It gives you an overview of what types of SharePoint activity are occurring.

For example:

```text
FileAccessed        5000
FileDownloaded       300
FileModified         120
SharingSet            30
AnonymousLinkCreated   2
```

The two anonymous links may deserve more attention than the 5,000 normal accesses.

---

# 6. `UserId` — Who Did It?

Suppose you want to understand which users are generating SharePoint activity.

```spl
index=m365 Workload=SharePoint
| stats count by UserId
| sort - count
```

This tells you:

```text
User
   ↓
Number of SharePoint events
```

But remember:

> High activity does not automatically mean malicious activity.

A SharePoint administrator may legitimately generate thousands of events.

You need to compare behavior against the user's role and baseline.

---

# 7. Investigating One User

Suppose the suspicious account is:

```text
emily.turner@tryhackme.thm
```

Search all SharePoint activity:

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
| table _time Operation SourceFileName ObjectId SiteUrl ApplicationDisplayName UserAgent
| sort _time
```

Now you can reconstruct what Emily did.

For example:

```text
09:01 FileAccessed
09:02 FileAccessed
09:03 FileDownloaded
09:04 FileDownloaded
09:05 SharingSet
```

That is already more interesting than looking at each event individually.

---

# 8. File Access

`FileAccessed` means the user accessed a file.

Query:

```spl
index=m365 Workload=SharePoint Operation=FileAccessed
| table _time UserId SourceFileName ObjectId SiteUrl
| sort _time
```

### Why monitor this?

An attacker with a compromised account may first perform **discovery**.

They aren't necessarily stealing data immediately.

They might first search for:

```text
Contracts
Finance
Passwords
Credentials
Network diagrams
Source code
Customer data
```

This makes file access potentially useful for detecting reconnaissance.

---

# 9. Investigating Sensitive File Access

You can perform a simple filename-based hunt:

```spl
index=m365 Workload=SharePoint Operation=FileAccessed
| search SourceFileName="*password*" 
    OR SourceFileName="*credential*"
    OR SourceFileName="*secret*"
    OR SourceFileName="*contract*"
    OR SourceFileName="*finance*"
| table _time UserId SourceFileName ObjectId SiteUrl
```

### Important

Filename matching is **not proof of compromise**.

For example:

```text
Password Policy.docx
```

contains the word "password" but may be completely legitimate.

Treat this as a **pivot**, not a verdict.

---

# 10. File Download

`FileDownloaded` is more important from an exfiltration perspective.

Basic query:

```spl
index=m365 Workload=SharePoint Operation=FileDownloaded
| table _time UserId SourceFileName ObjectId SiteUrl
| sort _time
```

You are asking:

> Which user downloaded which file, from which SharePoint site, and when?

---

# 11. Detecting Download Volume

One of the most useful behavioral queries:

```spl
index=m365 Workload=SharePoint Operation=FileDownloaded
| stats count as download_count by UserId
| sort - download_count
```

Example:

```text
User                     Downloads
----------------------------------
administrator             8200
backup-account             5100
emily.turner               1400
john.smith                   12
```

Emily suddenly having 1,400 downloads could be suspicious **if Emily normally downloads 10 files/day**.

This is why:

> **Behavioral baseline > arbitrary threshold.**

---

# 12. Detecting Download Spikes

You can group downloads by hour:

```spl
index=m365 Workload=SharePoint Operation=FileDownloaded
| bin _time span=1h
| stats count as downloads by _time UserId
| sort - downloads
```

This lets you identify bursts.

Example:

```text
10:00 → 5 downloads
11:00 → 8 downloads
12:00 → 7 downloads
13:00 → 900 downloads 🚨
```

That sudden change is much more interesting.

---

# 13. Why Folder Downloads Matter

Suppose a user downloads:

```text
Reports-2025/
```

containing five files.

SharePoint may generate:

```text
FileDownloaded
FileDownloaded
FileDownloaded
FileDownloaded
FileDownloaded
```

Therefore:

> A spike in download events doesn't necessarily mean the attacker manually clicked hundreds of files individually.

They may have downloaded an entire folder.

You can investigate the folder:

```spl
index=m365 Workload=SharePoint Operation=FileDownloaded
| stats count values(SourceFileName) as files by UserId SourceRelativeUrl
| sort - count
```

This shows:

```text
User
Folder
Number of downloads
Files involved
```

---

# 14. File Creation and Upload

Attackers may upload files into SharePoint.

Search:

```spl
index=m365 Workload=SharePoint Operation=FileUploaded
| table _time UserId SourceFileName ObjectId SiteUrl
```

You can also include creation:

```spl
index=m365 Workload=SharePoint Operation IN(FileUploaded, FileCreated)
| table _time UserId Operation SourceFileName ObjectId SiteUrl
| sort _time
```

### Why is this important?

An attacker could:

```text
Compromise account
      ↓
Upload malicious document
      ↓
Share document
      ↓
Victims receive notification
```

So an upload can be the beginning of a phishing campaign.

---

# 15. File Modification

Attackers don't always create new malicious files.

They may modify existing trusted files.

Search:

```spl
index=m365 Workload=SharePoint Operation=FileModified
| table _time UserId SourceFileName ObjectId SiteUrl
| sort _time
```

Imagine:

```text
Contract Template.docx
       ↓
FileModified
       ↓
SharingSet
       ↓
SecureLinkUsed
```

That is much more interesting than `FileModified` alone.

---

# 16. File Deletion

Search:

```spl
index=m365 Workload=SharePoint Operation IN(FileDeleted, FileRecycled)
| table _time UserId Operation SourceFileName ObjectId SiteUrl
| sort _time
```

Deletion may be:

- Completely legitimate
    
- Normal document management
    
- Evidence destruction
    
- Attack cleanup
    
- Destructive activity
    

Again, **timeline matters**.

---

# 17. SharePoint External Sharing

One of the most important concepts.

An attacker who compromises an account may share sensitive information with an external account.

Search:

```spl
index=m365 Workload=SharePoint Operation IN(AddedToSecureLink, AnonymousLinkCreated)
| table _time UserId Operation ObjectId TargetUserOrGroupName
| sort _time
```

Important fields:

```text
UserId
Operation
ObjectId
TargetUserOrGroupName
```

---

# 18. `AddedToSecureLink`

This indicates that a secure sharing link was added.

Example:

```text
Emily
   ↓
Contract.docx
   ↓
AddedToSecureLink
   ↓
attacker@gmail.com
```

This is potentially suspicious if the organization normally doesn't share sensitive documents externally.

---

# 19. `AnonymousLinkCreated`

Search:

```spl
index=m365 Workload=SharePoint Operation=AnonymousLinkCreated
| table _time UserId ObjectId SiteUrl
```

An anonymous sharing link deserves attention because access can potentially occur without the normal identity relationship you'd expect from authenticated sharing.

But again:

> Don't automatically label every anonymous link malicious.

Some organizations legitimately allow anonymous sharing.

The question is whether it is **expected for this user, file, and organization**.

---

# 20. Was the Link Actually Used?

Creating a link tells you the sharing action happened.

Now investigate whether somebody actually used it.

### Secure links

```spl
index=m365 Workload=SharePoint Operation=SecureLinkUsed
| table _time UserId ObjectId TargetUserOrGroupName
| sort _time
```

### Anonymous links

```spl
index=m365 Workload=SharePoint Operation=AnonymousLinkUsed
| table _time UserId ObjectId TargetUserOrGroupName
| sort _time
```

Now you can establish:

```text
Link created
      ↓
Link used
      ↓
File accessed
```

That's a much stronger investigative story.

---

# 21. Internal Sharing — `SharingSet`

Not every sharing event is external.

Search:

```spl
index=m365 Workload=SharePoint Operation=SharingSet
| table _time UserId ObjectId TargetUserOrGroupName
| sort _time
```

This is important because an attacker could use a compromised account to distribute malicious content internally.

For example:

```text
Compromised Emily account
          ↓
Malicious document
          ↓
SharingSet
          ↓
Internal employees
```

---

# 22. Connecting Sharing Events

Instead of investigating each event separately:

```spl
index=m365 Workload=SharePoint
    Operation IN(
        AddedToSecureLink,
        AnonymousLinkCreated,
        SharingSet,
        SecureLinkUsed,
        AnonymousLinkUsed
    )
| table _time UserId Operation ObjectId TargetUserOrGroupName
| sort _time
```

This gives you a **sharing timeline**.

For example:

```text
09:30 AddedToSecureLink
09:31 SecureLinkUsed
09:31 FileAccessed
```

That tells a much better story.

---

# 23. Rclone and External Applications

Attackers may use external synchronization tools to collect large amounts of SharePoint data.

Rclone is one example.

The important fields are:

```text
ApplicationDisplayName
UserAgent
```

Start by seeing which applications users are using:

```spl
index=m365 Workload=SharePoint
| stats count by UserId ApplicationDisplayName
| sort - count
```

Then inspect user agents:

```spl
index=m365 Workload=SharePoint
| stats count by UserId UserAgent
| sort - count
```

---

# 24. Hunting for Rclone

If your dataset records it explicitly:

```spl
index=m365 Workload=SharePoint
| search ApplicationDisplayName="*rclone*"
    OR UserAgent="*rclone*"
| table _time UserId Operation ApplicationDisplayName UserAgent ObjectId
| sort _time
```

But remember:

> **Rclone isn't automatically malicious.**

The useful question is:

```text
Is Rclone normal for this user?
```

For a cloud administrator, maybe.

For a sales employee who has never used command-line synchronization tools, that's much more interesting.

---

# 25. Unusual Application Per User

A stronger approach is to look at application diversity:

```spl
index=m365 Workload=SharePoint
| stats dc(ApplicationDisplayName) as app_count
        values(ApplicationDisplayName) as applications
        by UserId
| sort - app_count
```

Now you can investigate users with unexpected application behavior.

---

# 26. SharePoint as a Phishing Tool

This is a slightly different attack.

Instead of stealing information, the attacker uses SharePoint to **attack other users**.

Example:

```text
Compromised Sales account
        ↓
Find customer/partner emails
        ↓
Create malicious document
        ↓
Upload to SharePoint
        ↓
Share document
        ↓
Victim receives Microsoft notification
        ↓
Victim trusts notification
        ↓
Victim opens document
```

This is important because SharePoint is being used as **attack infrastructure**.

---

# 27. Finding the Malicious File's Origin

Suppose SOC identifies:

```text
ObjectId = BADFILE
```

Search:

```spl
index=m365 Operation IN(FileUploaded, FileCreated)
ObjectId="*BADFILE*"
| table _time UserId Operation ObjectId
| sort _time
```

Now you can identify the uploader.

This answers:

> **Who put the file into SharePoint?**

---

# 28. Who Received the File?

Next:

```spl
index=m365 Operation IN(AddedToSecureLink, SharingSet)
ObjectId="*BADFILE*"
| table _time UserId TargetUserOrGroupName ObjectId
| sort _time
```

Now you know:

> **Who was the file shared with?**

---

# 29. Who Opened the File?

Then:

```spl
index=m365 Operation IN(SecureLinkUsed, AnonymousLinkUsed, FileAccessed)
ObjectId="*BADFILE*"
| table _time UserId Operation ObjectId
| sort _time
```

Now you can identify users who interacted with the malicious file.

---

# 30. Build the Full Incident Timeline

This is the most important investigation query.

```spl
index=m365 ObjectId="*BADFILE*"
| table _time UserId Operation SourceFileName TargetUserOrGroupName ObjectId SiteUrl
| sort _time
```

You might discover:

```text
10:01 FileUploaded
10:02 AddedToSecureLink
10:03 SecureLinkUsed
10:03 FileAccessed
10:05 FileDownloaded
```

Now you have an attack narrative.

---

# 31. Complete SharePoint Investigation Example

Imagine:

> Emily's account may have been compromised.

Start with identity.

### Phase 1 — Authentication

```text
Entra ID
   ↓
Was Emily's login suspicious?
```

Look for:

- Unexpected IP
    
- Unusual location
    
- Unusual device
    
- Authentication anomalies
    
- Unusual time
    

Then move to SharePoint.

### Phase 2 — Access

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
| search Operation=FileAccessed
| table _time SourceFileName ObjectId SiteUrl
| sort _time
```

Question:

> What was Emily looking at?

---

### Phase 3 — Downloads

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
Operation=FileDownloaded
| stats count values(SourceFileName) as files by UserId
```

Question:

> Did Emily collect an unusual amount of data?

---

### Phase 4 — Sharing

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
Operation IN(AddedToSecureLink, AnonymousLinkCreated, SharingSet)
| table _time Operation ObjectId TargetUserOrGroupName
| sort _time
```

Question:

> Did Emily send corporate data somewhere?

---

### Phase 5 — External Application

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
| stats count by ApplicationDisplayName UserAgent
```

Question:

> Did an unusual application appear?

---

### Phase 6 — Timeline

Finally:

```spl
index=m365 Workload=SharePoint UserId="emily.turner@tryhackme.thm"
| table _time Operation SourceFileName ObjectId TargetUserOrGroupName ApplicationDisplayName
| sort _time
```

Now correlate the entire story.

---

# 32. The SOC Investigation Mindset

Don't think:

> "`FileDownloaded` = attacker."

Instead think:

```text
WHO?
 ↓
WHEN?
 ↓
FROM WHERE?
 ↓
WHAT FILE?
 ↓
WHAT ACTION?
 ↓
HOW MANY?
 ↓
WHO ELSE?
 ↓
WHAT APPLICATION?
 ↓
WHAT HAPPENED BEFORE/AFTER?
```

That's the difference between **searching logs** and **investigating an incident**.

# 33. The Most Important Attack Patterns

### Pattern 1 — Data Theft

```text
Suspicious login
      ↓
FileAccessed
      ↓
Many FileDownloaded
      ↓
External sharing
      ↓
Link used
```

### Pattern 2 — SharePoint Phishing

```text
Account compromise
      ↓
FileUploaded
      ↓
SharingSet
      ↓
Victim receives notification
      ↓
FileAccessed
```

### Pattern 3 — Mass Exfiltration

```text
Suspicious login
      ↓
FileAccessed
      ↓
Hundreds/thousands FileDownloaded
      ↓
Unusual application
      ↓
Possible Rclone/sync activity
```

### Pattern 4 — Existing Document Backdoor

```text
Trusted file
      ↓
FileModified
      ↓
Shared externally
      ↓
External access
```

# 34. Final Mental Model

For SharePoint SOC investigations, remember this chain:

```text
                    SHAREPOINT
                         │
                         ▼
                ┌─────────────────┐
                │ 1. AUTHENTICATE │
                │    Entra ID      │
                └────────┬────────┘
                         ↓
                ┌─────────────────┐
                │ 2. DISCOVER     │
                │ FileAccessed    │
                └────────┬────────┘
                         ↓
                ┌─────────────────┐
                │ 3. COLLECT      │
                │ FileDownloaded  │
                └────────┬────────┘
                         ↓
                ┌─────────────────┐
                │ 4. SHARE        │
                │ SharingSet      │
                │ Secure Links    │
                │ Anonymous Links │
                └────────┬────────┘
                         ↓
                ┌─────────────────┐
                │ 5. EXTERNAL     │
                │ LINK USED       │
                └────────┬────────┘
                         ↓
                ┌─────────────────┐
                │ 6. AUTOMATE     │
                │ Rclone / Apps   │
                └────────┬────────┘
                         ↓
                    EXFILTRATION
```

### The key distinction

**Entra ID logs answer:**

> **"Did this identity authenticate?"**

**SharePoint/M365 audit logs answer:**

> **"What did that identity do after authentication?"**

And your investigation connects the two into one timeline:

**Authentication → Discovery → Collection → Sharing → External Access → Exfiltration.**

That is the core SharePoint SOC skill.
