## 1. Password - Based Attacks
### 1. Password spraying vs. brute force

|Attack|What attacker varies|What stays relatively constant|Log pattern|
|---|---|---|---|
|**Password spraying**|Username|Password(s)|One IP → **many users** → failed logins|
|**Brute force**|Password|Username|One IP → **one user** → many failed passwords|
|**Slow brute force**|Password|Username|One user → failures spread over a **long period**|

The key SOC question is:

> **“Are many accounts being attacked, or is one account being attacked repeatedly?”**

That's the behavioral distinction.

---

### 2. Understand the first Splunk query

```spl
index="task-2" sourcetype="azure:aad:signin"
"status.errorCode"!=0
conditionalAccessStatus!=success
| table _time, userPrincipalName, appDisplayName, ipAddress,
        location.countryOrRegion, status.errorCode, status.failureReason
| sort - _time
```

Think of it as a pipeline:

**Entra logs → failures → remove successful Conditional Access results → display useful fields → newest first**

Important fields:

- `_time` → when authentication occurred
    
- `userPrincipalName` → account targeted
    
- `ipAddress` → source of authentication
    
- `appDisplayName` → application being accessed
    
- `location.countryOrRegion` → apparent source country
    
- `status.errorCode` → authentication result
    
- `status.failureReason` → why authentication failed
    

For SOC work, don't just stare at the error code. **Correlate the fields.**

---

### 3. The really useful query: failures by IP

```spl
index="task-2" sourcetype="azure:aad:signin"
"status.errorCode"!=0
conditionalAccessStatus!=success
| stats dc(userPrincipalName) as targeted_accounts,
        count as failures
        by ipAddress
| sort - failures
```

The important function here is:

```spl
dc(userPrincipalName)
```

`dc` = **distinct count**.

So:

```text
targeted_accounts = 25
failures = 80
ipAddress = 185.x.x.x
```

means:

> This IP generated 80 failed authentication attempts against 25 different accounts.

That's much more interesting than simply saying "80 failures."

For example:

|IP|Failures|Unique accounts|Interpretation|
|---|--:|--:|---|
|10.10.10.5|80|1|Possible brute force|
|10.10.10.6|75|38|Strong password-spray indicator|
|10.10.10.7|8|8|Possible spray / low-volume probing|
|10.10.10.8|150|1|Possible brute force|

**The ratio matters.**

A useful mental model:

> **Many users + few attempts/user = spraying**  
> **One user + many attempts = brute force**

---

### 4. Why the successful-login pivot matters

Finding failed attempts isn't enough.

The dangerous question is:

> **“Did the attacker eventually get the correct password?”**

That's why you pivot to successful authentication.

For a suspicious user:

```spl
index="task-2" sourcetype="azure:aad:signin"
"status.errorCode"=0
| where userPrincipalName="<TARGET_USER>"
| stats count by userPrincipalName, status.errorCode, ipAddress
| sort status.errorCode
```

You're asking:

**TARGET_USER → Did they successfully authenticate? → From which IP?**

Likewise, if you've identified a suspicious IP:

```spl
index="task-2" sourcetype="azure:aad:signin"
"status.errorCode"=0
| where ipAddress="<SUSPICIOUS_IP>"
| stats count by userPrincipalName, status.errorCode
| sort status.errorCode
```

Now the question becomes:

> **Did this suspicious IP successfully authenticate as anybody?**

That's the beginning of an actual incident investigation.

## 🧠 SOC investigation flow to memorize

Think of this as your interview/real-world workflow:

```text
Failed Entra Sign-ins
        ↓
Identify suspicious IPs
        ↓
Count failures
        ↓
Count unique targeted users
        ↓
     ┌───────────────┐
     │               │
Many users       One user
     │               │
Password Spray   Brute Force
     │               │
     └───────┬───────┘
             ↓
      Identify target
             ↓
   Search successful login
             ↓
   Was authentication successful?
             ↓
       YES → Escalate
             ↓
Investigate session/activity
```

### Interview answer

If an interviewer asks:

**“How would you detect password spraying in Entra ID?”**

A strong answer would be:

> “I would analyze Entra ID sign-in failures and group them by source IP. I would look at both the total number of failures and the distinct number of user accounts targeted. A single IP generating failures against many different accounts within a short period is a strong password-spraying indicator. I would then pivot on the suspicious IP and targeted accounts to determine whether any authentication subsequently succeeded. If successful authentication occurred, I would investigate the account, source IP, location, application, authentication method, and subsequent activity to determine whether the account was compromised.”

That's **SOC analyst thinking**, rather than merely knowing Splunk syntax.

### One thing to be careful about

Don't treat:

> **“Many failed logins = attack.”**

as a conclusion.

Legitimate causes can produce similar patterns: misconfigured applications, VPNs, mobile clients, password managers, automated services, users repeatedly entering stale credentials, etc.

The stronger detection is:

**volume + unique users + time window + source + success/failure + context.**

That's where the signal starts separating itself from the noise.

## 2. Conditional Access Policies & Identity Protection

The key idea is:

> **Password spraying tells you someone may have obtained a valid credential. Conditional Access and Identity Protection help determine whether that credential can actually be used successfully.**

## 1. Conditional Access vs Identity Protection

A very useful mental model:

```text
                  ENTRA ID SIGN-IN
                         │
                         ▼
              Identity Protection
             "Does this look risky?"
                         │
                         ▼
              Conditional Access
             "What should we do?"
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
           Allow        MFA         Block
```

### Identity Protection

**Detects risk.**

Examples:

- Suspicious IP
    
- Impossible travel
    
- Unfamiliar sign-in properties
    
- Leaked credentials
    
- Other suspicious activity
    

### Conditional Access

**Enforces a decision.**

Examples:

- Require MFA
    
- Block access
    
- Require compliant device
    
- Block legacy authentication
    
- Apply controls to high-risk sign-ins
    

So in an interview:

> **Identity Protection identifies risk; Conditional Access uses policy to respond to that risk.**

That's the clean answer.

---

# 2. Conditional Access is basically an IF/THEN engine

Think:

```text
IF
    user = employee
AND
    location = outside trusted region
THEN
    require MFA
```

Or:

```text
IF
    sign-in risk = HIGH
THEN
    BLOCK
```

Or:

```text
IF
    device = unmanaged
THEN
    BLOCK
```

The important SOC point is **scope**.

A beautifully designed policy that excludes the wrong account is basically security theater.

For example:

```text
Require MFA
   │
   ├── Employee A → MFA
   ├── Employee B → MFA
   ├── Employee C → MFA
   └── Service Account → EXCLUDED
                              │
                              ▼
                       Password spray
                              │
                              ▼
                    Valid credentials
                              │
                              ▼
                         No MFA
```

That's a potential attack path.

---

# 3. `appliedConditionalAccessPolicies` is extremely important

This field tells you what happened with the policies associated with the sign-in.

For example:

```text
Require MFA
     │
     └── result = notApplied
```

Don't immediately interpret `notApplied` as:

> "MFA failed."

That's incorrect.

It means the policy **didn't apply** to that sign-in.

The four states are worth memorizing:

|Result|SOC interpretation|
|---|---|
|`success`|Policy applied and required controls were satisfied|
|`failure`|Policy enforcement failed / blocked the request|
|`notApplied`|Policy wasn't applicable to that sign-in|
|`reportOnly`|Policy would apply, but isn't enforcing|

### The important distinction

```text
failure
   ≠
notApplied
```

**Failure** means enforcement encountered a problem/block.

**NotApplied** means the policy wasn't applicable in the first place.

That distinction can completely change your investigation.

---

# 4. Understanding the CAP Splunk query

The query:

```spl
index="task-3" sourcetype="azure:aad:signin" conditionalAccessStatus=failure
| spath output=policies path=appliedConditionalAccessPolicies{}
| mvexpand policies
| spath input=policies output=policy_result path=result
| spath input=policies output=policy_name path=displayName
| where policy_result="failure"
| stats values(policy_name) as FailedPolicies by _time, appDisplayName, userDisplayName, ipAddress, conditionalAccessStatus
| eval FailedPolicies=mvjoin(FailedPolicies, ", ")
| table _time, appDisplayName, userDisplayName, ipAddress, conditionalAccessStatus, FailedPolicies
| sort - _time
```

The interesting part is that `appliedConditionalAccessPolicies` is a **nested/multivalue structure**.

So the query essentially does:

```text
Raw sign-in
     ↓
Extract policy objects
     ↓
Expand individual policies
     ↓
Extract policy result
     ↓
Extract policy name
     ↓
Keep failures
     ↓
Summarize
```

### `spath`

Used to extract fields from structured JSON-like data.

### `mvexpand`

Takes multiple values and turns them into individual events/rows.

Conceptually:

```text
Policy A
Policy B
Policy C
```

becomes:

```text
Row 1 → Policy A
Row 2 → Policy B
Row 3 → Policy C
```

This makes the individual policy outcomes searchable.

# 5. Identity Protection: two risk concepts

This is another thing I'd memorize.

## Sign-in Risk

> **"How suspicious is this particular login?"**

Example:

```text
User: alice@company.com

09:00 → London → normal
09:05 → New York → suspicious
```

The second authentication could receive elevated sign-in risk.

It is evaluated around the **individual authentication event**.

---

## User Risk

> **"How likely is this account to be compromised?"**

This is broader.

Imagine:

```text
Alice
 │
 ├── leaked credential detected
 ├── suspicious sign-in
 ├── another high-risk sign-in
 └── suspicious M365 activity
              │
              ▼
         User Risk ↑
```

So:

|Concept|Think|
|---|---|
|**Sign-in Risk**|"Is THIS login suspicious?"|
|**User Risk**|"Is THIS USER potentially compromised?"|

That's a very interview-friendly distinction.

---

# 6. The three Identity Protection log sources

This section gives you three different investigation angles.

### `azure:aad:signin`

Think:

> **What happened during authentication?**

Useful fields:

```text
riskLevelDuringSignIn
riskLevelAggregated
userPrincipalName
ipAddress
location
appDisplayName
```

Example:

```spl
index="task-3" sourcetype="azure:aad:signin"
| where riskLevelDuringSignIn="high"
| table _time, userPrincipalName, appDisplayName, ipAddress,
        location.countryOrRegion, riskLevelDuringSignIn,
        riskLevelAggregated
| sort - _time
```

This is excellent for finding **high-risk authentication events**.

---

### `azure:aad:identity_protection:riskdetection`

Think:

> **Why did Microsoft consider something risky?**

Important fields:

```text
riskEventType
riskLevel
activity
ipAddress
userPrincipalName
```

For example:

```text
riskEventType = anonymizedIPAddress
```

means the detection relates to an anonymized source.

Your query:

```spl
index="task-3" sourcetype="azure:aad:identity_protection:riskdetection"
| where riskEventType="anonymizedIPAddress"
| table _time, userPrincipalName, activity, ipAddress,
        location.countryOrRegion, riskLevel, riskEventType
| sort - _time
```

Now you're investigating the **reason behind the risk detection**, rather than merely seeing that risk exists.

---

### `azure:aad:identity_protection:risky_user`

Think:

> **Which users currently need attention?**

```spl
index="task-3" sourcetype="azure:aad:identity_protection:risky_user"
| table _time, userPrincipalName, riskLevel, riskState, riskDetail
| sort - _time
```

This is useful for building a list of potentially compromised identities.

# 7. The biggest lesson: don't blindly trust Identity Protection

This paragraph is particularly important for a SOC analyst.

Suppose:

```text
User logs in from London
        ↓
User logs in from New York 5 minutes later
        ↓
No impossible-travel alert
```

You **cannot conclude**:

> "Therefore impossible travel didn't happen."

Instead:

```text
Identity Protection detection
          +
Entra sign-in logs
          +
User/context information
          ↓
       Investigation
```

Detection systems are **signals**, not absolute truth.

A mature SOC doesn't ask:

> "Did Microsoft alert?"

It asks:

> **"What does the underlying telemetry show?"**

That's a much stronger mindset.

## 3. MFA Bypass Techniques

The big SOC lesson is:

> **MFA dramatically reduces credential attacks, but the authentication event and the session are two different things.**

## 1. MFA flow in Entra ID

The simplified model is:

```text
Username + Password
        │
        ▼
   Credential valid?
        │
       YES
        │
        ▼
 Conditional Access
        │
        ▼
      MFA
        │
       YES
        │
        ▼
   Session / Token
        │
        ▼
      Access
```

So if an attacker has only:

```text
username + password
```

MFA should stop them.

But attackers have learned to attack **the user** or **the authenticated session**, rather than trying to defeat the cryptography itself.

---

# 2. MFA Fatigue / Prompt Bombing

This is probably the easiest MFA attack to understand.

The attacker already knows:

```text
username + password
```

They repeatedly initiate authentication:

```text
Login attempt
    ↓
MFA prompt
    ↓
Login attempt
    ↓
MFA prompt
    ↓
Login attempt
    ↓
MFA prompt
    ↓
Victim: "OMG, stop this."
    ↓
Approve
```

The attacker doesn't necessarily "hack MFA."

They **social-engineer the user into approving it**.

### What does it look like?

You might see:

```text
User A
 ├── MFA failure
 ├── MFA failure
 ├── MFA failure
 ├── MFA failure
 ├── MFA failure
 └── MFA success
```

within a short period.

The error codes mentioned in your material:

- `50074`
    
- `50076`
    
- `500121`
    

are useful indicators to investigate.

The query:

```spl
index="task-4" sourcetype="azure:aad:signin" \
(status.errorCode=50074 OR status.errorCode=50076 OR status.errorCode=500121)
| stats count as mfa_failures
        values(status.errorCode) as errorCodes
        values(status.failureReason) as failureReasons
        by userPrincipalName, ipAddress
| sort - mfa_failures
```

The important aggregation is:

```spl
stats ... by userPrincipalName, ipAddress
```

You're asking:

> **Which user is receiving lots of MFA-related failures, and where are those requests coming from?**

---

# 3. Number matching matters

Traditional push MFA:

> **Approve / Deny**

is vulnerable to fatigue because the user can accidentally or impatiently press **Approve**.

Number matching changes the interaction:

```text
Login screen:
Enter number → 42

Authenticator:
[ 42 ]
```

The user must demonstrate that they're actually looking at the authentication request.

It's not magic, but it significantly raises the attacker's social-engineering burden.

---

# 4. SIM swapping

SIM swapping attacks a different part of the authentication chain.

```text
Victim's phone number
        │
        ▼
Mobile carrier
        │
   attacker convinces
   carrier to transfer
   number
        │
        ▼
Attacker's SIM
        │
        ▼
SMS MFA codes
```

The important SOC lesson is:

> **SMS is possession of a phone number, not necessarily possession of the legitimate device.**

So organizations should generally prefer stronger phishing-resistant authentication methods over SMS where practical.

### Detection

The interesting indicators aren't necessarily explicit "SIM swap detected" events.

Instead, you may see:

```text
Normal user
    ↓
Suddenly unusual device
    +
Unusual browser
    +
Unusual location
    +
Successful authentication
```

That's why **baseline behavior** matters.

---

# 5. AiTM is the big one

**Adversary-in-the-Middle (AiTM)** is conceptually different from MFA fatigue.

The attacker doesn't necessarily convince the user to approve a fake MFA request.

Instead:

```text
Victim
  │
  │ legitimate authentication
  ▼
Attacker-controlled proxy
  │
  │ forwards traffic
  ▼
Microsoft
  │
  │ MFA challenge
  ▼
Victim completes MFA
  │
  ▼
Microsoft issues session
  │
  ▼
Attacker proxy captures session material
```

The crucial concept:

> **The attacker steals the authenticated session rather than stealing the MFA factor.**

That's why saying:

> "MFA was bypassed"

can be slightly misleading.

A better explanation is:

> **The attacker obtained a session that had already passed MFA.**

---

# 6. Why AiTM is difficult for a SOC

Imagine:

```text
09:00
User → Microsoft
IP: India
MFA completed
SUCCESS
```

Then:

```text
09:03
Same user/session
IP: Another country
SUCCESS
MFA: not requested
```

From Entra's perspective, the second event may contain a valid authentication context.

So you have to correlate:

```text
User
  +
Time
  +
IP
  +
Location
  +
Authentication result
  +
MFA behavior
  +
Conditional Access
```

This is why **individual log events aren't enough**.

You need the timeline.

# 7. Impossible Travel

This is where the previous concepts connect.

Example:

```text
09:00 → São Paulo
09:45 → Moscow
```

The account supposedly moved thousands of kilometers in 45 minutes.

That's suspicious.

Identity Protection may generate:

```text
riskEventType = impossibleTravel
```

You can search for it:

```spl
index="task-4" sourcetype="azure:aad:identity_protection:riskdetection"
| where riskEventType="impossibleTravel"
| table _time, userPrincipalName, activity, ipAddress,
        location.countryOrRegion, riskLevel, riskEventType
| sort - _time
```

But the more important hunting query is the underlying sign-in data:

```spl
index="task-4" sourcetype="azure:aad:signin" status.errorCode=0
| table _time, userPrincipalName, ipAddress,
        location.countryOrRegion, conditionalAccessStatus
| sort - _time
```

Why?

Because **Identity Protection can miss things or produce false positives**.

---

# 8. Don't blindly believe "Impossible Travel"

This is an important SOC habit.

Suppose:

```text
User → India
      ↓
User → United States
```

It doesn't automatically mean:

> COMPROMISED!

Investigate the network architecture first.

### Common false positives

**Corporate VPN**

```text
User physically in India
       ↓
Corporate VPN
       ↓
US exit node
       ↓
Entra sees US
```

**Split tunneling**

Some traffic:

```text
User → VPN → corporate network
```

Other traffic:

```text
User → Internet directly
```

Entra can therefore see different apparent source locations.

**Cloud services / integrations**

Automated services may authenticate from infrastructure that doesn't correspond to the user's physical location.

So the SOC question isn't:

> "Are there two countries?"

It's:

> **"Can I explain why there are two countries?"**

That's a much better investigation mindset.

# 🔥 Put all four attacks together

This is the mental model I'd memorize:

|Attack|What attacker has/uses|Main weakness attacked|Useful signal|
|---|---|---|---|
|**MFA Fatigue**|Valid password|Human approval|Many MFA prompts → eventual success|
|**SIM Swap**|Valid password + hijacked phone number|SMS factor|Unusual device/location + successful login|
|**AiTM**|Valid credentials + stolen session|Authenticated session|Successful login without expected new MFA + IP/location changes|
|**Impossible Travel**|Usually evidence of suspicious account use|Identity/session anomaly|Geographically impossible successful sign-ins|

## Interview answer

If asked:

**"How would you investigate a suspicious successful Entra ID login?"**

I'd answer:

That answer shows you're thinking like an analyst rather than just running Splunk queries.

That's the core of this task.

## 4. Priv Escalation and Persistence

Up to now, you were mostly asking:

> **“Did someone successfully authenticate?”**

Now the question becomes:

> **“What did they do after getting in?”**

And that's where **Entra Audit Logs** become critical.

---

# 1. Sign-in Logs vs Audit Logs

This distinction is fundamental.

|Log type|Main question|Examples|
|---|---|---|
|**Sign-in logs**|Who tried to authenticate?|Password spray, brute force, MFA, suspicious IP|
|**Audit logs**|What did an authenticated identity change/do?|Role assignment, user creation, MFA registration, policy changes|

Think of it like this:

```text
              ATTACK LIFECYCLE
                    │
                    ▼
             Credential attack
                    │
                    ▼
              Successful login
                    │
             ┌──────┴──────┐
             │             │
             ▼             ▼
        Sign-in Logs   Audit Logs
             │             │
      "How did they    "What did they
        get in?"          do?"
                           │
                           ▼
                    Post-compromise
```

That's a very important mental separation.

---

# 2. The three Audit Log fields you need to know

The room gives you three fields:

### `activityDisplayName`

**What happened?**

Examples:

```text
Add member to role
Add user
User started security info registration
```

---

### `initiatedBy`

**Who performed the action?**

Could be:

```text
user
```

or an application/service:

```text
app
```

This is extremely important because not every action is directly initiated by a human user.

---

### `targetResources`

**What was affected?**

For example:

```text
initiatedBy:
    attacker@company.com

activityDisplayName:
    Add member to role

targetResources:
    victim@company.com
    Global Administrator
```

Together:

```text
WHAT?       → activityDisplayName
WHO?        → initiatedBy
TARGET?     → targetResources
```

### Memorize this:

> **Activity = what. Initiator = who. Target = what was changed.**

---

# 3. Role Assignment — privilege escalation

This is one of the highest-value things to hunt.

Imagine:

```text
Compromised user
      │
      ▼
Add member to role
      │
      ▼
Global Administrator
      │
      ▼
Massive tenant control
```

That's privilege escalation.

The query:

```spl
index="task-5" sourcetype="azure:aad:audit"
activityDisplayName="Add member to role"
| table _time,
        activityDisplayName,
        initiatedBy.user.userPrincipalName,
        targetResources{}.userPrincipalName,
        targetResources{}.modifiedProperties{}.newValue
| sort - _time
```

The particularly interesting field is:

```spl
targetResources{}.modifiedProperties{}.newValue
```

That's where you investigate **what role was actually assigned**.

Don't stop at:

> "A role assignment occurred."

Ask:

> **Which role? To whom? Who assigned it? When?**

---

# 4. Not every role assignment is malicious

This is where analysts need to avoid tunnel vision.

For example:

```text
09:00
IT admin → User A → User Administrator
```

could be completely normal.

But:

```text
02:37 AM
Recently compromised user
      ↓
assigns themselves
      ↓
Global Administrator
```

is considerably more suspicious.

So your investigation should correlate:

```text
Role assignment
      +
Initiator
      +
Target
      +
Time
      +
Recent sign-in activity
      +
Normal provisioning workflow
```

The **context** turns an ordinary audit event into a potential incident.

# 5. Backdoor accounts

This is persistence.

Suppose:

```text
Attacker compromises Alice
        │
        ▼
Creates attacker2@company.com
        │
        ▼
Assigns privileged role
        │
        ▼
Alice gets disabled
        │
        ▼
Attacker still has attacker2
```

That's why account creation after compromise is important.

The query:

```spl
index="task-5" sourcetype="azure:aad:audit"
activityDisplayName="Add user"
| eval initiator=coalesce(
    'initiatedBy.user.userPrincipalName',
    'initiatedBy.app.displayName'
)
| eval userCreated='targetResources{}.userPrincipalName'
| table _time, activityDisplayName, initiator, userCreated
```

The clever part is:

```spl
coalesce(...)
```

It says, effectively:

> If a user initiated it, show the user; otherwise show the application.

So you don't accidentally miss app-initiated activity.

---

# 6. Why account creation alone isn't enough

Again, avoid:

> "New account = attacker."

Instead ask:

```text
Who created it?
       ↓
Who was created?
       ↓
When?
       ↓
Was this expected?
       ↓
Was the new account privileged?
       ↓
Was the creator recently compromised?
```

For example:

```text
HR onboarding
   ↓
Normal account creation
   ↓
Expected
```

versus:

```text
Compromised user
   ↓
Creates unknown account
   ↓
Assigns admin role
   ↓
Suspicious
```

The second chain is where things get spicy.

# 7. Alternate MFA registration = persistence

This is arguably one of the most important ideas in this task.

Imagine an attacker compromises:

```text
victim@company.com
```

They add their own authentication method:

```text
victim account
      │
      ▼
Attacker registers
Authenticator / phone
      │
      ▼
Attacker-controlled MFA factor
```

Now the victim changes their password.

You might think:

> "Problem solved."

Not necessarily.

If the attacker has established their own authentication method, they've potentially created a **persistent authentication path**.

Conceptually:

```text
Password compromised
       │
       ▼
Attacker gains access
       │
       ▼
Registers own MFA
       │
       ▼
Password reset
       │
       ▼
Attacker may still have access
```

That's why MFA registration changes deserve serious attention during incident response.

# 🧠 SOC investigation cheat sheet

When you suspect an Entra account has been compromised, pivot like this:

|Question|Log/Field|
|---|---|
|How did they get in?|Sign-in logs|
|Was MFA involved?|Sign-in/authentication data|
|Was the login risky?|Identity Protection|
|What did they change?|`activityDisplayName`|
|Who performed it?|`initiatedBy`|
|What was affected?|`targetResources`|
|Did they gain privileges?|`Add member to role`|
|Did they create persistence?|`Add user`|
|Did they register their own MFA?|Security info registration|

And the **golden triad** for Audit Logs:

> **WHAT → `activityDisplayName`**  
> **WHO → `initiatedBy`**  
> **TARGET → `targetResources`**

If you can reliably answer those three questions, you're already doing substantially better than an analyst who just searches for "suspicious."

---

## Interview scenario

**Question:** _“A user is confirmed compromised. What would you investigate next in Entra Audit Logs?”_

A strong answer:

> “I would look for post-compromise actions performed by the account, particularly privileged role assignments, creation of new accounts, authentication-method or MFA registration changes, and security-policy modifications. I would use `activityDisplayName` to identify the action, `initiatedBy` to determine who or what performed it, and `targetResources` to determine what was modified. I would then correlate the timestamps and source IPs with the user's sign-in and Identity Protection data to determine whether the activity was legitimate or part of the compromise.”

That's the answer I'd want from a junior SOC analyst.

**Core concept:** authentication logs tell you **how the attacker entered**; audit logs tell you **what they did once inside**.

## 5. OAuth Application Abuse

This is the **persistence layer** of the attack chain, and OAuth abuse is a big deal because it changes the question from:

> “Does the attacker still know the password?”

to:

> **“Does an application still have permission to access the tenant?”**

A password reset can kill stolen credentials. It **doesn't automatically revoke an OAuth grant**.

---

# 1. Why OAuth persistence is different

Normal credential compromise:

```text
Attacker
   ↓
Username + Password
   ↓
MFA / authentication
   ↓
Account access
```

Reset the password:

```text
Password reset
      ↓
Old credential useless
      ↓
Attacker loses that access path
```

OAuth compromise is different:

```text
Attacker
   ↓
Malicious / compromised application
   ↓
User/Admin grants consent
   ↓
OAuth permissions
   ↓
Access token / refresh capability
   ↓
Application accesses resources
```

Now:

```text
Password reset       ❌ Doesn't necessarily remove grant
MFA reset            ❌ Doesn't necessarily remove grant
Account lockout      ❌ Doesn't necessarily remove grant
OAuth revocation     ✅ Removes the application authorization
```

That's the key concept.

---

# 2. OAuth in one picture

Think of OAuth as:

> **“I don't want to give this application my password. I'll give Microsoft permission to let the application access specific resources instead.”**

Conceptually:

```text
User
 │
 │ "I approve this app"
 ▼
Microsoft Entra ID
 │
 │ Authorization grant
 ▼
Application
 │
 │ Access token
 ▼
M365 resources
```

The application doesn't need to know the user's password.

That's great for legitimate applications.

It is also exactly why attackers like abusing it.

---

# 3. Delegated vs Application permissions

This distinction is **very important for interviews**.

||Delegated|Application|
|---|---|---|
|Acts as|User|Application itself|
|Requires user|Yes|No|
|Scope|User's accessible resources|Potentially tenant-wide|
|Typical consent|User/admin depending on permission|Admin|
|Risk|Usually lower|Potentially very high|

### Delegated

Example:

```text
Mail.Read
```

The application effectively says:

> "Let me read the mail that this user is allowed to access."

So:

```text
User
  ↓
App
  ↓
User's mailbox
```

---

### Application

Example:

```text
Mail.Read.All
```

Now you're talking about:

```text
Application
     ↓
Tenant
 ┌───┼────┐
 ▼   ▼    ▼
A    B    C
mail mail mail
```

There isn't necessarily an interactive user session involved.

That's why application permissions deserve much more scrutiny.

---

# 4. High-risk permissions

These are worth recognizing immediately:

### `Mail.Read.All`

Potentially allows an application to read mail across the tenant.

### `Mail.ReadWrite.All`

Even more dangerous because the application can potentially modify mail as well.

### `Files.ReadWrite.All`

Potential access to files across SharePoint/OneDrive.

### `Directory.ReadWrite.All`

Potentially massive directory-level access.

Think:

```text
Users
Groups
Directory objects
```

### `RoleManagement.ReadWrite.Directory`

This one should make your SOC eyebrows go up.

It can enable management of directory roles.

Conceptually:

```text
OAuth app
    ↓
RoleManagement.ReadWrite.Directory
    ↓
Role assignment capability
    ↓
Potential privilege escalation
```

### `offline_access`

This is important because it relates to **long-lived access through refresh tokens**.

The key idea isn't simply:

> "offline_access = attacker."

Instead:

> **offline_access can allow an application to maintain access without requiring the user to be actively signing in.**

---

# 5. Why admin consent is especially dangerous

Imagine an attacker convinces a Global Administrator:

```text
"Please approve this productivity application."
```

The admin clicks:

> **Accept**

And grants something like:

```text
Mail.Read.All
Directory.ReadWrite.All
```

Now the attacker potentially has an application-level access path.

The attack chain becomes:

```text
Phishing / social engineering
          ↓
Administrator authenticates
          ↓
OAuth consent
          ↓
Powerful permissions granted
          ↓
Application receives authorization
          ↓
Persistent access
```

The scary part is that the attacker may no longer need to repeatedly authenticate as that administrator.

---

# 6. Audit Logs become your friend

The key event is:

```text
activityDisplayName="Consent to application"
```

That's your starting point.

The query:

```spl
index="main" sourcetype="azure:aad:audit"
activityDisplayName="Consent to application"
| eval initiator=coalesce(
    'initiatedBy.user.userPrincipalName',
    'initiatedBy.app.displayName'
)
| eval appName='targetResources{}.displayName'
| eval permissionsGranted='targetResources{}.modifiedProperties{}.newValue'
| table _time, initiator, appName, permissionsGranted
| sort - _time
```

You're extracting three things:

```text
WHO?
 ↓
initiator

WHAT APP?
 ↓
appName

WHAT PERMISSIONS?
 ↓
permissionsGranted
```

That's basically the OAuth equivalent of the earlier Audit Log triad.

---

# 7. Your investigation workflow

Suppose you find:

```text
Time: 03:15
Initiator: user@company.com
Application: "Microsoft Productivity Helper"
Permissions: Mail.Read.All
```

Don't immediately declare compromise.

Investigate:

### Step 1 — Who granted consent?

```text
initiator
```

Was it:

- Normal user?
    
- Helpdesk?
    
- Global Administrator?
    
- Compromised account?
    

---

### Step 2 — What application?

```text
appName
```

Ask:

- Is this an approved application?
    
- Is it known to the organization?
    
- Is the publisher legitimate?
    
- Was it recently introduced?
    
- Does its name imitate a trusted application?
    

---

### Step 3 — What permissions?

This is the biggest risk factor.

For example:

```text
Mail.Read
```

is very different from:

```text
Mail.Read.All
Directory.ReadWrite.All
RoleManagement.ReadWrite.Directory
```

---

### Step 4 — When did consent occur?

Timing matters enormously.

Suppose:

```text
02:10 → Password spray
02:14 → Successful login
02:18 → MFA anomaly
02:22 → OAuth consent
```

Now you have a coherent attack story.

Compare that with:

```text
Monday → normal admin approves legitimate SaaS app
```

Context changes everything.

# 🧠 Interview answer

If they ask:

**“Why is malicious OAuth consent dangerous even after a password reset?”**

Answer:

> “Because OAuth authorization is an application-level access mechanism rather than a direct credential-based authentication path. A consented application can retain delegated or application permissions even after the user's password is changed. Therefore, remediation requires identifying and revoking the malicious application consent or tokens, not just resetting the user's credentials.”

If they ask:

**“How would you hunt for OAuth abuse?”**

Say:

> “I would search Entra Audit Logs for `Consent to application`, identify the initiator and application, and inspect the permissions granted in `targetResources`. I'd prioritize high-impact permissions such as `Mail.Read.All`, `Directory.ReadWrite.All`, `RoleManagement.ReadWrite.Directory`, and broad file access. I'd then correlate the consent event with the initiator's sign-in and Identity Protection activity to determine whether the consent occurred during or immediately after a suspected compromise.”

---

## The one thing to burn into memory

> **Credentials authenticate a user. OAuth grants authorize an application.**

Therefore:

**Password reset ≠ OAuth revocation.**

That single distinction explains why OAuth consent is such a nasty persistence mechanism in Entra ID.
