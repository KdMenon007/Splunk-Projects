
This section is **very important for a SOC analyst** because it answers a practical question:

> **"What exactly do I monitor in a cloud environment?"**

A common beginner mistake is thinking:

> Cloud monitoring = CloudTrail.

That's **not enough**.

CloudTrail is extremely important, but a real cloud environment contains **identities, APIs, VMs, containers, databases, storage, networks, web applications, and managed services**. Each can require different telemetry.

The core idea is:

```text
                         CLOUD ENVIRONMENT
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
          ↓                     ↓                     ↓
    CONTROL PLANE          WORKLOADS           MANAGED SERVICES
          │                     │                     │
      CloudTrail          EC2 / VM            RDS / S3
      IAM activity        Processes            Database activity
      API activity        Files                Object activity
      Config changes      Endpoint logs        Service logs
          │                     │                     │
          └─────────────────────┼─────────────────────┘
                                ↓
                               SIEM
                                ↓
                         Detection / Hunting
                                ↓
                            SOC Analyst
```

---

# 1. The Three Main Cloud Security Areas

For a simple AWS environment, imagine:

```text
                         AWS CLOUD
                             │
             ┌───────────────┼───────────────┐
             │               │               │
             ↓               ↓               ↓
        Control Plane     Workloads     Managed Services
             │               │               │
          AWS IAM          EC2 VM          RDS
          Console          Website         S3
          APIs             Processes       Database
          Config           Files           Objects
```

A SOC needs visibility into **all three**.

---

# 2. Area 1 — Control Plane

## What is the Control Plane?

The **control plane** is where users and administrators perform actions that create, modify, configure, or manage cloud resources.

Think:

> **"Who is changing the cloud?"**

Examples:

- Creating an EC2 instance
    
- Deleting an EC2 instance
    
- Creating an S3 bucket
    
- Changing IAM permissions
    
- Creating access keys
    
- Modifying security groups
    
- Changing network configuration
    
- Logging into the AWS console
    
- Changing cloud configurations
    

---

## Example

An administrator logs into AWS and performs:

```text
Login
  ↓
Create EC2
  ↓
Modify security group
  ↓
Create IAM user
  ↓
Grant AdministratorAccess
```

These are **control-plane activities**.

For SOC monitoring, these actions are extremely important because attackers who compromise a cloud identity frequently use the control plane to:

- Establish persistence
    
- Escalate privileges
    
- Disable security controls
    
- Modify network access
    
- Access data
    
- Create resources
    
- Destroy evidence
    

---

# 3. Control Plane Monitoring

The primary AWS service used here is:

> **AWS CloudTrail**

CloudTrail records AWS API activity.

This includes activity generated through:

- AWS Management Console
    
- AWS CLI
    
- AWS SDKs
    
- AWS APIs
    
- Other AWS services
    

This means CloudTrail isn't simply:

> "A log of people clicking around the AWS console."

It is much broader.

---

# 4. Why CloudTrail Matters to a SOC

Suppose an attacker compromises:

```text
john.doe
```

The attacker doesn't necessarily need to log into a server.

They can use AWS APIs.

For example:

```text
Compromised credentials
        ↓
AWS API authentication
        ↓
Enumerate resources
        ↓
Modify IAM
        ↓
Create access key
        ↓
Modify security group
        ↓
Access S3
```

CloudTrail gives the SOC visibility into those API operations.

Therefore:

> **CloudTrail is one of the fundamental log sources for AWS security monitoring.**

---

# 5. CloudTrail

CloudTrail records AWS API events.

Examples:

```text
ConsoleLogin
RunInstances
CreateBucket
CreateUser
CreateAccessKey
PutBucketPolicy
ModifySecurityGroupRules
```

Think of:

```text
eventName
```

as:

> **"What AWS action happened?"**

# 6. CloudTrail Event History

AWS provides CloudTrail event history that allows analysts to inspect recent events.

The important point from the lesson is that CloudTrail provides a period of event history without requiring you to build your own long-term SIEM storage.

However, organizations generally need **longer retention** for security investigations and compliance.

Therefore, CloudTrail logs are commonly delivered to centralized storage and/or security monitoring platforms.

# 8. CloudTrail Event Structure

A CloudTrail event is normally JSON.

Example:

```json
{
  "eventTime": "2025-12-10T17:54:44Z",
  "eventSource": "signin.amazonaws.com",
  "eventName": "ConsoleLogin",
  "awsRegion": "us-east-1",
  "sourceIPAddress": "72.44.21.87",
  "userAgent": "Mozilla/5.0",
  "requestParameters": null,
  "readOnly": false,
  "recipientAccountId": "398985017225",
  "userIdentity": {
    "type": "IAMUser",
    "arn": "arn:aws:iam::398985017225:user/john.doe",
    "accountId": "398985017225",
    "userName": "john.doe"
  }
}
```

You don't need to memorize the entire JSON.

You need to understand the **important fields**.

---

# 9. `eventSource`

Example:

```text
eventSource = ec2.amazonaws.com
```

This tells you:

> **Which AWS service handled the request?**

Examples:

```text
ec2.amazonaws.com
s3.amazonaws.com
iam.amazonaws.com
signin.amazonaws.com
```

SOC analogy:

You can think of this somewhat like identifying the relevant Windows event channel or application source.

---

# 10. `eventName`

This tells you:

> **What action was performed?**

Examples:

```text
ConsoleLogin
RunInstances
CreateBucket
CreateUser
CreateAccessKey
ModifySecurityGroupRules
```

This is one of the most important fields for detection engineering.

Example:

```text
eventName = CreateAccessKey
```

means someone created an AWS access key.

That could be legitimate.

Or it could be:

```text
Compromised account
       ↓
Attacker
       ↓
CreateAccessKey
       ↓
Persistence
```

Context matters.

---

# 11. `recipientAccountId`

This identifies the AWS account where the activity occurred.

Example:

```text
recipientAccountId = 398985017225
```

This is useful in environments with:

- Multiple AWS accounts
    
- Production account
    
- Development account
    
- Security account
    
- Logging account
    

The SOC needs to know:

> **Which cloud account was affected?**

---

# 12. `sourceIPAddress`

This tells you where the API request originated.

Example:

```text
sourceIPAddress = 72.44.21.87
```

This can help answer:

- Is the source IP expected?
    
- Is it from the corporate network?
    
- Is it from a VPN?
    
- Is it from an unusual country?
    
- Is it a known malicious IP?
    
- Has this IP appeared in previous incidents?
    

---

# 13. `userIdentity`

This tells you about the identity behind the action.

Important fields include:

```text
userIdentity.type
userIdentity.arn
userIdentity.accountId
userIdentity.userName
```

For example:

```text
userName = john.doe
```

Now the SOC can ask:

> "Why did John create this access key at 03:00 from a foreign IP?"

That's where logs become useful.

---

# 14. ARN

ARN means:

> **Amazon Resource Name**

It provides a structured identifier for AWS resources.

Example:

```text
arn:aws:iam::398985017225:user/john.doe
```

This gives you information about:

- AWS service
    
- Account
    
- Resource type
    
- Resource identity
    

For SOC investigations, ARN can help uniquely identify the actor/resource involved.

---

# 15. `requestParameters`

This is extremely important.

It contains details specific to the API request.

For example:

```text
eventName = CreateBucket
```

The request parameters may tell you:

```text
bucketName = sensitive-data-prod
```

Another event might contain:

```text
SecurityGroupRule
CIDR = 0.0.0.0/0
Port = 22
```

Therefore:

> **`eventName` tells you what happened; `requestParameters` can tell you the details of what was changed.**

---

# 16. `readOnly`

This indicates whether the event is a read-only operation.

Conceptually:

```text
readOnly = true
```

means the operation is generally retrieving/reading information.

While:

```text
readOnly = false
```

indicates a state-changing operation.

Examples:

```text
GetObject
```

may represent reading.

Whereas:

```text
PutObject
CreateUser
CreateAccessKey
ModifySecurityGroupRules
```

represent changes or writes.

---

# 17. Why `readOnly=false` Is Interesting

The lesson recommends starting detection analysis with:

```text
readOnly = false
```

because these events often represent **changes to the environment**.

For example:

```text
IAM permission changed
Security group modified
S3 bucket policy changed
New access key created
Logging configuration changed
```

These events can have major security consequences.

But remember:

> **`readOnly=false` does NOT automatically mean malicious.**

A legitimate administrator may need to change a security group.

The SOC must evaluate:

```text
Who?
What?
When?
Where?
Why?
Was it authorized?
```

---

# 18. Practical CloudTrail Investigation

Imagine this event:

```text
eventName:
ModifySecurityGroupRules
```

The SOC sees:

```text
CidrIpv4 = 0.0.0.0/0
FromPort = 22
ToPort = 22
Protocol = TCP
```

This means:

```text
Internet
   │
   │ TCP/22
   ↓
AWS Security Group
   ↓
EC2
```

SSH has effectively been exposed to the Internet.

---

# 19. Why `0.0.0.0/0` Matters

IPv4:

```text
0.0.0.0/0
```

represents:

> **Any IPv4 source address**

Therefore:

```text
TCP/22
+
0.0.0.0/0
```

means SSH access is allowed from anywhere, subject to the rest of the environment's controls.

This can be legitimate in some architectures, but it is often a **high-risk configuration**.

# 21. Control Plane Threats

There are hundreds of possible cloud detections.

You don't need to memorize every AWS API.

Instead, organize detections into categories.

---

## Category 1 — IAM

Monitor for:

- New users
    
- New roles
    
- Permission changes
    
- Administrator privileges
    
- Access-key creation
    
- Access-key deletion
    
- MFA changes
    
- Unusual logins
    

Example attack:

```text
Compromised IAM account
       ↓
Create access key
       ↓
Create persistence
       ↓
Use key later
```

---

# 22. IAM Privilege Escalation

Example:

```text
Normal user
    ↓
Modify IAM policy
    ↓
Administrator privileges
    ↓
Cloud takeover
```

A SOC should pay close attention to unexpected privilege changes.

---

# 23. Category 2 — EC2

EC2 is AWS's virtual machine service.

Monitor:

- Instance creation
    
- Instance termination
    
- Security-group changes
    
- Public exposure
    
- Suspicious instance launches
    
- Unusual instance types
    
- Unexpected regions
    

Example:

```text
Compromised account
       ↓
Launch EC2
       ↓
Install cryptominer
       ↓
Generate cloud bill
```

This is both a security and financial risk.

---

# 24. Category 3 — S3

S3 is object storage.

Important events include:

- Bucket creation
    
- Bucket deletion
    
- Bucket policy changes
    
- Public access changes
    
- Object access
    
- Object uploads
    
- Object deletion
    

One major detection:

> **S3 bucket unexpectedly made public.**

Example:

```text
Private bucket
      ↓
Bucket policy changed
      ↓
Anonymous access granted
      ↓
Internet
      ↓
Sensitive data exposed
```

---

# 25. Detection Engineering Principle

A good detection should not simply ask:

> "Did event X happen?"

It should ask:

> **"Did event X happen under suspicious circumstances?"**

For example:

```text
CreateAccessKey
```

isn't automatically malicious.

But:

```text
CreateAccessKey
+
User rarely creates keys
+
Outside business hours
+
Unusual IP
+
Immediately followed by S3 downloads
```

is much more suspicious.

This is **correlation**.

# 26. GuardDuty

AWS also provides:

> **Amazon GuardDuty**

GuardDuty is a managed threat-detection service.

It analyzes different AWS telemetry sources and generates **findings** when it identifies suspicious activity.

It can analyze areas such as:

- Control-plane activity
    
- Network activity
    
- DNS-related activity
    
- Certain workload/endpoint signals
    

---

# 27. CloudTrail vs GuardDuty

This distinction is **very important for interviews**.

### CloudTrail

CloudTrail is primarily:

> **Raw audit/activity telemetry**

It tells you:

```text
Who performed an AWS API action?
What action?
When?
From where?
Against which account/resource?
```

### GuardDuty

GuardDuty is:

> **Managed threat detection**

It analyzes telemetry and produces findings.

Think:

```text
CloudTrail
    ↓
Raw evidence
    ↓
SOC detection / investigation
```

versus:

```text
AWS telemetry
     ↓
GuardDuty analytics
     ↓
Finding
     ↓
SOC
```

---

# 28. Why GuardDuty Isn't Enough

A mature SOC should not necessarily say:

> "We have GuardDuty, so we don't need CloudTrail."

That's poor security architecture.

GuardDuty has limitations.

### 1. Insufficient context

A GuardDuty finding may tell you:

> "Suspicious activity detected."

But the SOC may need the underlying events to understand the complete attack chain.

---

### 2. Generic detection

GuardDuty provides AWS-managed detection logic.

Your company may have unique requirements.

Example:

Your organization says:

> Developers must never create IAM access keys.

A generic cloud detection may not represent that exact business policy.

Raw logs allow you to build custom detections.

---

### 3. Advanced attacks

Attackers can behave slowly and carefully.

Example:

```text
Day 1 → Login
Day 3 → Enumerate
Day 5 → Create role
Day 7 → Access storage
```

Custom threat hunting and correlation may detect behavior that a generic managed rule misses.

---

### 4. Logging tampering

If an attacker compromises a highly privileged account, they may attempt to:

```text
Disable logging
Change logging configuration
Alter monitoring settings
```

The SOC needs independent monitoring and controls to detect such activity.

---

# 29. CloudTrail vs GuardDuty — Mental Model

Remember:

```text
CloudTrail = "What happened?"

GuardDuty = "This looks suspicious."
```

CloudTrail provides evidence.

GuardDuty provides managed detection.

A mature SOC can use **both**.

# 30. Managed Services

Cloud environments contain services where the provider manages much of the infrastructure.

Examples:

- Amazon RDS
    
- Amazon S3
    
- CloudFront
    
- DynamoDB
    
- Managed Kubernetes
    
- Other AWS managed services
    

The challenge is:

> **CloudTrail doesn't necessarily provide detailed visibility into everything happening inside every managed service.**

---

# 31. Why CloudTrail Has a Blind Spot

Suppose you have:

```text
Application
    ↓
RDS Database
```

CloudTrail can tell you about certain AWS control-plane operations around RDS.

But that doesn't necessarily mean CloudTrail records every SQL query executed inside the database.

For example:

```sql
SELECT * FROM customers;
```

You need **database-specific logging** for that kind of visibility.

This is the difference between:

```text
Managing the service
```

and

```text
Using the service
```

---

# 32. Managed Service Monitoring

Each major cloud service can have its own logging mechanisms.

Therefore:

```text
CloudTrail
+
Service-specific logs
+
Network logs
+
Application logs
```

may all be necessary.

# 33. CloudFront

CloudFront is AWS's CDN service.

A CDN sits in front of web applications and helps deliver content to users.

Simplified:

```text
User
 ↓
CloudFront
 ↓
Application
 ↓
Backend
```

Because CloudFront can sit in front of web applications, its logs can be valuable for detecting web attacks.

---

# 34. What CloudFront Logs Can Show

Typical information can include:

- Client IP
    
- HTTP method
    
- Requested host
    
- URI
    
- HTTP status
    
- User agent
    
- Bytes transferred
    
- Request timing
    

Example:

```text
80.42.89.4
POST
tryhackme.com
/login
200
Mozilla/5.0
```

---

# 35. Why CloudFront Logs Matter to a SOC

They can help investigate:

- Web scanning
    
- Brute-force attacks
    
- Exploitation attempts
    
- Malicious requests
    
- Web-shell activity
    
- Suspicious uploads
    
- SQL injection attempts
    
- Other application-layer attacks
    

The important concept:

> **CloudTrail tells you about AWS control-plane activity; CloudFront logs tell you about web traffic passing through CloudFront.**

Different telemetry, different visibility.

# 36. VPC Flow Logs

Now we move to **network visibility**.

On-premises environments commonly use:

- Firewalls
    
- Routers
    
- Network sensors
    
- IDS/IPS
    
- NetFlow-like telemetry
    

In AWS, one important source is:

> **VPC Flow Logs**

---

# 37. What Are VPC Flow Logs?

VPC Flow Logs record information about network traffic flows involving cloud network interfaces/resources, depending on how logging is configured.

They can help answer:

> **Who communicated with whom, over which port/protocol, and was the traffic accepted or rejected?**

---

# 38. Important VPC Flow Log Fields

## `srcaddr`

Source IP.

Example:

```text
172.31.16.4
```

---

## `dstaddr`

Destination IP.

Example:

```text
172.31.16.7
```

---

## `srcport`

Source port.

Example:

```text
20641
```

---

## `dstport`

Destination port.

Example:

```text
80
```

---

## `protocol`

Network protocol.

Common values:

```text
TCP = 6
UDP = 17
ICMP = 1
```

---

## `action`

Whether the traffic was:

```text
ACCEPT
```

or

```text
REJECT
```

This can help determine whether AWS network controls permitted the flow.

---

# 39. Example VPC Flow Log

```text
srcaddr       dstaddr       srcport  dstport  protocol  action

172.31.16.4   172.31.16.7   20641    80       6         ACCEPT

172.31.9.69   172.31.9.12   49761    22       6         REJECT
```

Interpretation:

### Event 1

```text
172.31.16.4
     ↓
172.31.16.7:80
     ↓
TCP
     ↓
ACCEPT
```

HTTP traffic was accepted.

### Event 2

```text
172.31.9.69
     ↓
172.31.9.12:22
     ↓
TCP
     ↓
REJECT
```

SSH traffic was rejected.

---

# 40. VPC Flow Logs Limitations

This is an important SOC lesson.

Flow logs can generate **huge volumes of data**.

In large environments:

```text
Millions
   ↓
Billions
   ↓
Potentially enormous log volume
```

A single application request may produce multiple network-flow records because traffic crosses multiple network interfaces/hops.

Therefore:

> **More logs does not automatically mean better security.**

You want:

> **High signal-to-noise ratio.**

---

For example:

### DNS logs

Can help detect:

- Command-and-control

# 42. S3 Data Events

This is another **very important distinction**.

CloudTrail normally gives you control-plane activity.

But S3 can also generate **data events**.

These can show operations involving individual objects.

Examples:

```text
GetObject
PutObject
DeleteObject
```

---

# 43. Control Plane vs Data Plane

This distinction is worth memorizing.

### Control Plane

Think:

> **"Manage the cloud resource."**

Examples:

```text
CreateBucket
DeleteBucket
ModifySecurityGroupRules
CreateUser
RunInstances
```

---

### Data Plane / Data Events

Think:

> **"Use the resource."**

For S3:

```text
GetObject
PutObject
DeleteObject
```

Example:

```text
CreateBucket
```

means someone created the bucket.

Whereas:

```text
GetObject
```

means someone accessed an object inside the bucket.

---

# 44. Why S3 Data Events Matter

Imagine an attacker compromises an AWS account.

They don't modify the bucket.

Instead they do:

```text
GetObject
GetObject
GetObject
GetObject
...
```

They are stealing data.

If you're only monitoring control-plane changes, you may miss the actual data theft.

Therefore:

> **Data access monitoring is essential for sensitive cloud storage.**

> **Amazon CloudWatch**

CloudWatch provides monitoring and logging capabilities across AWS services.

- Applications

# 46. CloudWatch vs SIEM

Don't confuse them.

CloudWatch is an AWS-native monitoring/logging platform.

A SIEM is designed for broader:

- Security monitoring
    
- Correlation
    
- Detection
    
- Investigation
    
- Alerting
    

A possible architecture:

```text

     ↓

     ↓
SIEM
     ↓

     ↓

```

CloudWatch and a SIEM can therefore complement each other.

# 51. Containers

As organizations mature, they may move from traditional VMs to containers.

Example:

```text
Traditional:

EC2
 └── OS
      └── Application
```

Containerized:

```text
Container Platform
 ├── Container A
 ├── Container B
 ├── Container C
 └── Container D
```

This changes the security monitoring model.

---

# 52. Why Containers Are Different

Traditional endpoint tools were designed around operating systems and processes running directly on those systems.

Containers introduce:

- Short-lived workloads
    
- Ephemeral containers
    
- Container images
    
- Orchestration
    
- Shared kernels
    
- Dynamic environments
    

A container might exist for only a few minutes.

Therefore:

```text
Traditional endpoint
     ↓
Long-lived machine
     ↓
Install agent
```

versus:

```text
Container
     ↓
Starts
     ↓
Runs
     ↓
Disappears
```

Monitoring needs to account for this lifecycle.

---

# 53. Container Security Monitoring

Traditional tools may not provide sufficient visibility in every containerized environment.

Cloud-native/container security solutions can provide visibility into:

- Container processes
    
- Container behavior
    
- Image vulnerabilities
    
- Runtime activity
    
- Suspicious system calls
    
- Network activity
    

Tools and approaches include technologies such as:

- Falco
    
- Cloud workload protection platforms
    
- Container security platforms
    

The important concept is not memorizing a particular product.

# 60. Key Difference: CloudTrail vs VPC Flow Logs vs Workload Logs

This is worth knowing cold.

|Log Source|Main Question|
|---|---|
|**CloudTrail**|What AWS API/control-plane action happened?|
|**S3 Data Events**|What happened to individual S3 objects?|
|**VPC Flow Logs**|Who communicated with whom and over what network flow?|
|**CloudFront logs**|What HTTP/web requests reached the CDN?|
|**EDR/Sysmon/Auditd**|What happened inside the workload?|
|**RDS/database logs**|What happened inside the database/service?|
|**GuardDuty**|Does AWS telemetry indicate suspicious behavior?|
|**CloudWatch**|Operational/service/application logs and monitoring|

# 61. The Most Important SOC Concept

Don't think:

> **"Which AWS logging product should I use?"**

Think:

> **"What activity do I need visibility into?"**

Then choose the appropriate telemetry.

For example:

### Question:

**Who changed an IAM policy?**

→ CloudTrail

### Question:

**Who downloaded this S3 object?**

→ S3 Data Events

### Question:

**Did this EC2 communicate with an external IP?**

→ VPC Flow Logs / endpoint telemetry

### Question:

**What process executed on the EC2 machine?**

→ EDR/Sysmon/Auditd

### Question:

**What HTTP requests hit my web application?**

→ CloudFront/application logs

### Question:

**Did AWS detect suspicious behavior?**

→ GuardDuty

That's the mindset you want to develop.

## The 5 things I would memorize from this section

1. **Cloud monitoring has three areas:** Control Plane, Workloads, Managed Services.
    
2. **CloudTrail = AWS API/control-plane visibility.**
    
3. **GuardDuty = managed threat detection, not a replacement for raw logs.**
    
4. **VPC Flow Logs = network-flow visibility; S3 Data Events = individual object activity.**
    
5. **Your monitoring strategy must follow the architecture:** VMs need endpoint telemetry, managed services need service-specific logs, and containers/serverless require cloud-native monitoring.
    

The deeper SOC lesson is simple:

> **You cannot detect what you cannot see. Cloud security is therefore largely an exercise in understanding the architecture first, then collecting the right telemetry for each layer.**
