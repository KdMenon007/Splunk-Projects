# AWS S3, EC2, RDS, Discovery & Denial-of-Wallet 

This section moves from **IAM/identity monitoring** into **resource-level attacks**.

The core SOC idea is:

> **Cloud attacks are often caused by either exposed resources, abused permissions, excessive discovery, or unexpected resource consumption.**

For SOC work, think in this chain:

```text
Misconfiguration
      ↓
Internet Exposure
      ↓
Attacker Discovery
      ↓
Initial Access
      ↓
Resource Abuse
      ↓
Data Exfiltration / Persistence / Impact
      ↓
Financial Impact
```

---

# 1. Amazon S3 Security

## What is S3?

**Amazon S3 (Simple Storage Service)** is AWS's object-storage service.

Organizations commonly use S3 for:

- Backups
    
- Application files
    
- Images
    
- Videos
    
- Configuration files
    
- Logs
    
- Database backups
    
- Static website content
    
- Security telemetry
    

Example:

```text
Application
    ↓
S3 Bucket
    ├── images/
    ├── backups/
    ├── logs/
    └── configuration/
```

S3 is extremely useful, but it has historically been a major source of cloud data-exposure incidents.

---

# 2. Why S3 Is Dangerous

The basic problem is simple:

```text
Sensitive Data
      ↓
S3 Bucket
      ↓
Incorrect Access Policy
      ↓
Internet
      ↓
Anyone
```

A single incorrect permission can expose millions of objects.

Potentially exposed information includes:

- Customer information
    
- Employee information
    
- Screenshots
    
- Source code
    
- Credentials
    
- Backups
    
- Logs
    
- Documents
    
- Financial information
    

---

# 3. S3 Bucket vs Object

You need to distinguish these.

### Bucket

The container.

```text
company-backups
```

### Object

The actual file.

```text
company-backups/
    database.sql
    backup.tar.gz
    passwords.txt
```

Think:

```text
Bucket
  ↓
Folder-like namespace
  ↓
Objects
```

---

# 4. Public S3 Exposure

An S3 bucket can become publicly accessible due to incorrect access controls.

The important security controls include:

- S3 Block Public Access
    
- Bucket policy
    
- IAM permissions
    
- Resource policies
    
- ACLs
    

For modern environments, **S3 ACLs are considered legacy**, so bucket policies and Block Public Access are particularly important.

---

# 5. The Basic Public-Bucket Attack

Conceptually:

```text
Private Bucket
     ↓
Disable public-access protection
     ↓
Modify bucket policy
     ↓
Allow anonymous access
     ↓
Bucket becomes publicly accessible
     ↓
Internet scanners discover it
     ↓
Objects accessed
     ↓
Data exfiltration
```

This is why the **configuration change itself** is an important detection opportunity.

Don't wait for the data to disappear.

---

# 6. Early Detection vs Late Detection

This is a major SOC concept.

## Early detection

Detect:

> "The bucket is becoming public."

Example:

```text
PutBucketPublicAccessBlock
        ↓
PutBucketPolicy
        ↓
Public exposure
```

This is ideal.

---

## Late detection

You missed the configuration change.

Now detect:

> "Someone from the Internet is accessing the bucket."

Example:

```text
HeadObject
GetObject
     ↓
External IP
     ↓
Anonymous access
```

This is already potentially an active attack.

---

# 7. S3 Public Access Block

S3 has a **Block Public Access** security feature.

Its purpose is essentially to prevent public access configurations from accidentally exposing data.

Therefore, a suspicious sequence is:

```text
PutBucketPublicAccessBlock
        ↓
Public access protections disabled
        ↓
PutBucketPolicy
        ↓
Public access granted
```

The first event is an important early warning.

---

# 8. `PutBucketPolicy`

This event indicates that an S3 bucket policy was modified/applied.

For example:

```text
eventName = PutBucketPolicy
```

SOC analysts should inspect:

```text
requestParameters.bucketPolicy
```

particularly:

```text
Effect
Principal
Action
Resource
Condition
```

---

# 9. The Dangerous Combination

A classic suspicious policy contains:

```json
"Effect": "Allow",
"Principal": "*"
```

Interpretation:

```text
Effect:
Allow

Principal:
Everyone
```

That is potentially public access.

But don't immediately declare:

> "Bucket compromised!"

You need to examine the entire policy.

---

# 10. Why `Principal: "*"` Is Not Always Malicious

Consider:

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Condition": {
    "IpAddress": {
      "aws:SourceIp": [
        "67.55.61.83/32"
      ]
    }
  }
}
```

At first glance:

```text
Principal = *
```

looks scary.

But:

```text
Condition
   ↓
Only specific IP
```

may restrict the actual exposure.

Therefore:

> **Never detect public S3 access by looking at `Principal: "*"` alone.**

Inspect the complete policy.

---

# 11. Important S3 Policy Fields

When investigating `PutBucketPolicy`, understand:

### `Effect`

Usually:

```text
Allow
Deny
```

---

### `Principal`

Who can access the resource?

```text
*
```

can mean everyone, depending on policy context.

---

### `Action`

What can they do?

Examples:

```text
s3:GetObject
s3:PutObject
s3:DeleteObject
```

---

### `Resource`

Which bucket/object does the rule apply to?

Example:

```text
arn:aws:s3:::company-data/*
```

---

### `Condition`

Additional restrictions.

Examples:

```text
Source IP
VPC
identity
encryption requirements
```

---

# 12. Public Read vs Public Write

These are very different.

### Public read

```text
s3:GetObject
```

Potential impact:

```text
Data exposure
```

But it may be legitimate.

For example:

```text
Public website
 ↓
Images
 ↓
S3
```

---

### Public write

```text
s3:PutObject
```

Potential impact:

```text
Attacker
 ↓
Upload malicious files
 ↓
S3
```

This is usually far more dangerous.

Public delete permissions can also be highly destructive.

---

# 13. Legitimate Public Buckets

Not every public bucket is an incident.

Some applications intentionally serve public content.

Examples:

```text
user-avatars
website-assets
public-media
static-content
```

Suppose:

```text
user-avatars
 ↓
s3:GetObject
 ↓
Everyone
```

That might be legitimate.

SOC should ask:

- What is the bucket's purpose?
    
- What type of data is stored?
    
- Is public access documented?
    
- Who owns the bucket?
    
- Is only read access allowed?
    
- Are there restrictions?
    
- Does the policy match the business requirement?
    

---

# 14. Bucket Name as Context

Bucket naming can help investigation.

Examples:

```text
public-website-assets
```

versus:

```text
prod-customer-backups
```

The second being public would be much more concerning.

But:

> **Bucket name is context, not proof.**

A bucket named `public-assets` can still contain secrets.

---

# 15. S3 Late Detection

Suppose your early detection failed.

The attacker may begin scanning.

Typical object-level events include:

```text
HeadObject
GetObject
```

The attacker may be attempting to determine:

> Does this file exist?

or:

> Can I download this file?

---

# 16. `HeadObject`

`HeadObject` retrieves metadata about an object without downloading its contents.

Conceptually:

```text
Attacker
   ↓
"Does this object exist?"
   ↓
HeadObject
```

Large numbers of these requests can indicate automated enumeration.

---

# 17. `GetObject`

`GetObject` retrieves the actual object.

Conceptually:

```text
Attacker
   ↓
GetObject
   ↓
Sensitive file
   ↓
Downloaded
```

A successful `GetObject` from an unexpected external source is therefore important.

---

# 18. S3 Object Brute Force

Suppose object listing isn't allowed.

The attacker may not know filenames.

They can guess:

```text
backup.zip
backup.tar.gz
prod-backup.tar.gz
database.sql
credentials.txt
config.json
```

The result may be:

```text
GetObject → AccessDenied
GetObject → AccessDenied
GetObject → AccessDenied
GetObject → AccessDenied
GetObject → Success
```

That pattern is interesting.

---

# 19. Detecting Object Enumeration

Look for:

```text
Many GetObject/HeadObject
+
Same external IP
+
Same bucket
+
Many failures
+
Occasional success
```

Conceptually:

```text
        Object guessing
              ↓
       ┌──────┴──────┐
       ↓             ↓
   AccessDenied    Success
       ↓             ↓
     many          target
```

This can indicate automated discovery.

---

# 20. GuardDuty and S3

Amazon GuardDuty can provide managed detection for S3-related threats.

Important findings include:

### `Policy:S3/BucketBlockPublicAccessDisabled`

Public-access blocking was disabled.

---

### `Policy:S3/BucketAnonymousAccessGranted`

Anonymous/public access was granted.

---

### `Impact:S3/MaliciousIPCaller`

A known malicious IP accessed an exposed S3 bucket.

---

# 21. Why GuardDuty Helps

Manually interpreting every S3 policy can become complicated.

For example:

```text
Principal = *
      +
Condition
      +
Deny
      +
Resource restrictions
      +
Identity context
```

GuardDuty can reason about the effective exposure more effectively than a simplistic SIEM rule.

Still:

> **GuardDuty complements CloudTrail; it doesn't replace raw telemetry.**

---

# 22. S3 SOC Detection Strategy

Think in three layers:

```text
LAYER 1 — CONFIGURATION
       ↓
Bucket becoming public

LAYER 2 — ACCESS
       ↓
External/anonymous object access

LAYER 3 — IMPACT
       ↓
Large-scale downloads / exfiltration
```

This is defense in depth.

# 23. EC2 Internet Exposure

Now move from storage to compute.

**Amazon EC2** provides virtual machines in AWS.

An EC2 instance may expose services such as:

```text
SSH   → 22
HTTP  → 80
HTTPS → 443
RDP   → 3389
VNC   → 5900
```

The exposure is controlled by multiple network/security mechanisms.

One major control is the **Security Group**.

---

# 24. Security Groups

Think of a security group as a cloud-level virtual firewall associated with resources.

Example:

```text
Internet
    ↓
Security Group
    ↓
EC2
```

An inbound rule might be:

```text
TCP
Port 22
Source: 0.0.0.0/0
```

Meaning:

> SSH is allowed from anywhere on the IPv4 Internet.

---

# 25. Why `0.0.0.0/0` Matters

This means:

```text
Any IPv4 source
```

Therefore:

```text
0.0.0.0/0 → 22
```

means:

```text
Internet
 ↓
SSH
 ↓
EC2
```

This isn't automatically malicious.

A public SSH server may be intentional.

But it significantly increases exposure.

---

# 26. Dangerous EC2 Exposure

Typical risky services include:

```text
22    SSH
3389  RDP
5900  VNC
```

especially when:

```text
Source = 0.0.0.0/0
```

A vulnerable or poorly configured service can become an entry point.

---

# 27. Typical EC2 Attack Chain

```text
Security Group modified
        ↓
SSH/RDP exposed
        ↓
Internet scanning
        ↓
Attacker finds EC2
        ↓
Brute force / exploit
        ↓
Initial Access
        ↓
Execution
        ↓
Credential theft
        ↓
IAM role abuse
        ↓
Cloud resource access
```

This connects your previous IAM notes directly to EC2 security.

---

# 28. Early EC2 Detection

The ideal detection is:

```text
Security Group change
        ↓
Public SSH/RDP
        ↓
SOC alert
        ↓
Remediation
```

Don't wait for:

```text
SSH brute force
```

or:

```text
Malware
```

---

# 29. Security Group Attack Scenario

Suppose Alice changes:

```text
Security Group sg-1234
```

and adds:

```text
TCP 3389
0.0.0.0/0
```

Then Bob launches an EC2 instance using that group.

You now have:

```text
Alice
 ↓
Security Group modification
 ↓
Public RDP
 ↓
Bob
 ↓
EC2 launched
 ↓
Internet exposure
```

These events should be correlated.

---

# 30. Hunt 1 — New Security Group

The first hunt is:

> **A new security group was created.**

### Step 1 — Find creation

```spl
index=* eventName=CreateSecurityGroup
```

Record:

- Group ID
    
- Group name
    
- Creator
    
- Description
    

---

### Step 2 — Find inbound rules

```spl
index=* eventName=AuthorizeSecurityGroupIngress sg-xxxxxx
```

Look for:

```text
0.0.0.0/0
```

and risky ports:

```text
22
3389
5900
```

---

### Step 3 — Find resources using the group

```spl
index=* eventName IN(RunInstances, ModifyInstanceAttribute) sg-xxxxxx
```

Now you can determine:

```text
Security Group
      ↓
EC2 instance
```

---

# 31. Hunt 2 — Existing Security Group Modified

Suppose a security group already existed.

Someone changes its rules.

### Step 1

```spl
index=* eventName IN(*SecurityGroupIngress, ModifySecurityGroupRules)
```

Identify:

- Group ID
    
- New rule
    
- Source
    
- Port
    
- Protocol
    
- Actor
    

---

### Step 2 — Find original group creation

```spl
index=* earliest=-1y eventName=CreateSecurityGroup sg-xxxxxx
```

This can help determine:

- Who created it?
    
- Why?
    
- What was its intended purpose?
    

---

### Step 3 — Find resources using it

```spl
index=* eventName IN(RunInstances, ModifyInstanceAttribute) sg-xxxxxx
```

Remember:

> Security groups aren't necessarily used only by EC2. Other AWS services can depend on them too.

---

# 32. Security Groups Are Not the Entire Network Security Model

This is important.

AWS network exposure can involve:

- Security Groups
    
- Network ACLs
    
- VPC routing
    
- Subnets
    
- Internet gateways
    
- Load balancers
    
- Host-based firewalls
    
- Application controls
    

Therefore:

```text
Security Group says "ALLOW"
```

doesn't always mean:

```text
Internet definitely reaches application
```

There may be other controls.

---

# 33. SOC Verification

If possible:

```text
CloudTrail evidence
      +
AWS configuration
      +
Network validation
```

You can validate actual exposure with authorized security testing or AWS configuration data.

Don't raise a critical incident solely because you saw:

```text
0.0.0.0/0
```

without understanding how the resource is actually exposed.

# 35. EC2 + IAM Role = Important Combination

# 38. RDS Example

RDS is a managed relational database service.

Common database engines include:

- MySQL
    
- PostgreSQL
    
- MariaDB
    
- SQL Server
    
- Oracle
    

Sensitive data may reside there:

```text

Passwords
Emails

```

Therefore exposing RDS can have serious consequences.

# 39. RDS Internet Exposure

A dangerous configuration can involve:

```text
RDS
 ↓
Public Access = enabled
 +
Security Group
 ↓
Database port
 ↓
0.0.0.0/0
```

For MySQL, for example:

```text
TCP 3306
```

could become reachable from the Internet.

---

# 40. RDS Exposure at Creation

Exposure can occur during creation.

Example:

```text
CreateDBInstance
      ↓
Public access enabled
      ↓
Existing permissive SG attached
      ↓
Database exposed
```

So don't only monitor:

```text
ModifyDBInstance
```

Also inspect:

```text

```

---

# 41. RDS Exposure After Deployment

A database can be secure for years and then become exposed.

For example:

```text
2024
RDS private

2025
Security group changed

2026
Public access enabled
```

Relevant events include:

```text
ModifyDBInstance
*SecurityGroupIngress
ModifySecurityGroupRules
```

Therefore:

> **A secure resource today isn't necessarily secure tomorrow.**

Continuous monitoring matters.

---

# 42. Why Database Exposure Is Difficult

Different AWS services expose resources differently.

For example:

```text
RDS
 ↓
Public Access + Security Group

DynamoDB
 ↓
Resource policy

OpenSearch
 ↓
Policy + potentially Security Group
```

Therefore:

> **There is no universal "public database" detection rule.**

Your SOC needs service-specific knowledge.

# 46. Cloud Discovery

Not every attack immediately results in data theft.

Attackers often first ask:

> **What do I have access to?**

This is **Discovery**.

Think of it as:

```text
Initial Access
      ↓
"Who am I?"
      ↓
"What permissions do I have?"
      ↓
"What resources exist?"
      ↓
"Which resource is valuable?"
      ↓
"How do I reach it?"
```

---

# 47. `GetCallerIdentity`

This is essentially the AWS equivalent of:

```text
whoami
```

An attacker can use:

```bash
aws sts get-caller-identity
```

to determine the identity associated with their current credentials.

Conceptually:

```text
Credential
    ↓
GetCallerIdentity
    ↓
Who am I?
Which account?
Which ARN?
```

This is extremely useful to attackers.

---

# 48. IAM Discovery

After determining identity, attackers may enumerate permissions.

Examples include:

```text
GetUser
GetCallerIdentity
ListAttachedUserPolicies
ListGroupsForUser
GetAccountSummary
```

The attacker is answering:

```text
Who am I?
   ↓
What permissions do I have?
   ↓
What account am I in?
```

---

# 49. Why `GetCallerIdentity` Isn't Automatically Malicious

This is important for SOC analysts.

Legitimate tools and applications also call identity APIs.

Therefore:

```text
GetCallerIdentity
```

alone is weak evidence.

Better:

```text
GetCallerIdentity
+
aws-cli
+
new source IP
+
many List/Describe calls
```

Now the activity becomes more interesting.

---

# 50. Broad Cloud Discovery

Once attackers understand their identity, they may enumerate the environment.

Examples:

```text
ListBuckets
DescribeInstances
ListFunctions
ListUsers
```

This is essentially:

```text
"What exists in this AWS account?"
```

---

# 51. Cross-Service Enumeration

One particularly useful SOC signal is a single identity making many different discovery calls.

Example:

```text
IAM
 ↓
ListUsers
 ↓
EC2
 ↓
DescribeInstances
 ↓
S3
 ↓
ListBuckets
 ↓
Lambda
 ↓
ListFunctions
 ↓
RDS
 ↓
DescribeDBInstances
```

That looks like broad reconnaissance.

---

# 52. Why Spikes Matter

One discovery API call isn't necessarily suspicious.

But:

```text
Normal:
5 API calls/hour

Suddenly:
300 distinct API calls
across 8 AWS services
in 3 minutes
```

is much more interesting.

Therefore detection can focus on:

```text
Distinct API calls
+
Distinct AWS services
+
Identity
+
Time window
```

---

# 53. Deeper Discovery

After broad enumeration, attackers may focus on interesting targets.

Example:

```text

 ↓

 ↓

 ↓

```

Or:

```text

 ↓

 ↓

```

# 54. Searching for Interesting Resources

Attackers may use filters.

For example:

```text
tag:Name
```

with values such as:

```text

vault
backup
database
prod
admin
password
```

This is valuable from a SOC perspective because the attacker is telling you what they are looking for.

---

# 55. Example Discovery Event

Suppose you see:

```text
eventName:
DescribeInstances

sourceIPAddress:
167.99.40.20

userAgent:
aws-cli/...kali...

requestParameters:
tag:Name = *vault*
tag:Name = *secret*
```

There are multiple signals:

### Signal 1 — Source IP

Potentially malicious infrastructure.

### Signal 2 — User-agent

AWS CLI running from Kali-like environment.

### Signal 3 — Search terms

Searching for:

```text
vault
secret
```

The combination is much stronger than any individual indicator.

---

# 56. Discovery Detection Philosophy

Don't create:

```text
ALERT = DescribeInstances
```

That's noisy.

Instead:

```text
ALERT =
unusual identity
+
unusual source
+
CLI/SDK
+
rapid enumeration
+
sensitive search terms
```

This is much closer to real SOC detection engineering.

# 57. Denial of Wallet

Now we reach a very cloud-specific attack.

Traditional:

```text
DDoS
 ↓
Service unavailable
```

Cloud environments can create a different problem:

```text
Attack
 ↓
Cloud automatically scales
 ↓
Resources increase
 ↓
AWS bill increases
```

This is called:

> **Denial of Wallet (DoW).**

---

# 58. DoS vs DoW

### Denial of Service

Goal:

```text
Make service unavailable
```

### Denial of Wallet

Goal/effect:

```text
Make victim spend excessive money
```

The attack may even leave the application available.

That's the nasty part.

---

# 59. S3 Denial of Wallet

S3 costs can depend on:

- Request volume
    
- Data transfer
    
- Object operations
    

An attacker could repeatedly request objects.

Example:

```text
Attacker
 ↓
GetObject
 ↓
Large video
 ↓
Repeat 1,000,000 times
 ↓
Request/data-transfer costs
```

The service may continue working perfectly.

The victim's billing system, however:

```text
💀
```

---

# 60. S3 DoW Example

Suppose an S3 bucket contains:

```text
10 GB videos
```

An attacker repeatedly downloads them.

Conceptually:

```text
10 GB
 ×
many requests
 =
massive outbound traffic
```

Depending on the architecture and pricing model, this can create significant cost.

---

# 61. Compute DoW

Autoscaling can make the situation worse.

Example:

```text
Attacker
 ↓
HTTP flood
 ↓
Application receives huge traffic
 ↓
Auto Scaling detects load
 ↓
Launches more EC2 instances
 ↓
Attack continues
 ↓
More EC2 instances
 ↓
Higher bill
```

The attacker may not successfully take the application offline.

But they may still cause financial damage.

---

# 62. Cloud DoW Attack Chain

```text
Attacker
   ↓
High-volume requests
   ↓
WAF/CDN/application
   ↓
Autoscaling
   ↓
More compute
   ↓
More processing
   ↓
More network traffic
   ↓
Higher cloud bill
```

This is why cloud security isn't only:

```text
CIA Triad
```

It also involves:

```text
Financial resilience
```

---

# 63. Detecting Denial of Wallet

SOC should watch for:

### Request spikes

```text
Normal:
```

# 64. SOC Response to DoW

SOC generally doesn't own the complete remediation.

SOC can:

1. Detect traffic spike
    
2. Validate whether traffic is malicious
    
3. Identify source IPs
    
4. Identify attack pattern
    
5. Coordinate blocking
    
6. Notify IT/cloud engineering
    
7. Monitor whether the attack stops
    
8. Monitor resource scaling
    
9. Escalate financial risk

# 66. WAF

A **Web Application Firewall (WAF)** can help block:

- Known malicious IPs
    
- Exploit attempts
    
- Suspicious patterns
    
- Excessive requests
    
- Automated attacks
    

For DoW:

```text
Internet
   ↓
WAF
   ↓
Application
```

is generally preferable to:

```text
Internet
   ↓
Application
```

because unwanted traffic can be filtered earlier.

# 67. CDN and Caching

A CDN can cache frequently requested content.

```text
 ↓
Origin
 ↓
S3/application
```

With caching:

```text
Attacker
 ↓
CDN cache
 ↓
Cached object
```

This can reduce repeated origin processing and help control load.

# 68. Rate Limiting

Rate limiting prevents one client or group of clients from generating unlimited requests.

Conceptually:

```text
User
 ↓
100 requests/sec
 ↓
Allowed

User
 ↓
1,000,000 requests/sec
 ↓
Rate limited
```

This can reduce both DoS and DoW impact.

# 75. Interview-Level Explanation

If an interviewer asks:

### "How would you detect a public S3 bucket?"

A strong answer:

> "I would first monitor CloudTrail for changes to S3 public-access controls and bucket policies. In particular, I would investigate `PutBucketPublicAccessBlock`, `PutBucketPolicy`, and potentially `PutBucketAcl`. For bucket policies, I would inspect `Effect`, `Principal`, `Action`, `Resource`, and `Condition` rather than simply flagging every `Principal: "*"` rule. I would then validate whether the bucket is intentionally public based on its business purpose. As a second layer, I would monitor S3 object access such as `GetObject` and `HeadObject` for anonymous or unusual external access, especially high volumes of failed requests that could indicate object-name enumeration. GuardDuty and CSPM can provide additional posture and threat context."

That's a much stronger answer than:

> "I will search for public S3."

---

# 76. Another Interview Question

### "How would you detect an exposed EC2 instance?"

Answer structure:

```text
1. Detect SG changes
2. Identify risky ports
3. Check source CIDR
4. Identify affected EC2 instances
5. Validate other network controls
6. Check GuardDuty
7. Check endpoint authentication logs
8. Look for exploitation
```

Example:

> "I'd monitor CloudTrail for security-group ingress changes, particularly rules exposing SSH, RDP, or other sensitive services to `0.0.0.0/0`. I'd correlate the security-group ID with `RunInstances` or `ModifyInstanceAttribute` events to identify affected workloads. Then I'd validate whether other VPC controls actually expose the instance and check GuardDuty, authentication logs, and EDR for evidence of exploitation."

---

# 77. Another Interview Question

### "How would you detect AWS reconnaissance?"

Don't say:

> "Alert on `GetCallerIdentity`."

Instead:

> "I'd look for behavioral patterns. After initial access, an attacker may call `GetCallerIdentity`, enumerate IAM permissions, query account information, and then enumerate resources such as S3 buckets, EC2 instances, Lambda functions, and IAM users. I'd look for unusual spikes in distinct API calls across multiple services, especially when combined with a new source IP, unusual CLI/SDK user-agent, or suspicious resource-search terms."

That's the SOC mindset.

## The key rule

**Cloud SOC monitoring should not only ask "Was the attacker successful?"**

It should ask:

> **"Did the environment become dangerous before the attacker had a chance to exploit it?"**

That means detecting:

```text
                    PREVENTIVE
                        ↓
              Misconfiguration
                        ↓
                  EARLY ALERT
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
          No attacker          Attacker
                                  ↓
                              Discovery
                                  ↓
                              Initial Access
                                  ↓
                              Exploitation
                                  ↓
                        Exfiltration / Impact
```

That distinction—**early posture detection + behavioral detection + late-stage impact detection**—is the core of mature cloud SOC monitoring.
