
This section is important because AWS attacks aren't limited to IAM, S3, EC2, or RDS. **Management services themselves can become attack paths.**

The big picture:

```text
IAM / Credentials
       ↓
AWS Management Service
       ↓
EC2 / Containers / Lambda
       ↓
Execution
       ↓
Persistence / Privilege Escalation / Impact
```

The four areas you should lock in are:

1. **SSM / Session Manager**
    
2. **Auto Scaling**
    
3. **Falco + Containers**
    
4. **Lambda**
    

---

# 1. AWS Systems Manager — SSM

AWS Systems Manager allows administrators to manage EC2 machines remotely.

Typical legitimate uses:

```text
Install software
Patch systems
Run scripts
Restart services
Collect information
Execute commands
Manage fleets
```

The important SOC question is:

> **"Can an attacker use SSM as a legitimate-looking remote execution mechanism?"**

Yes.

That's what makes it dangerous.

---

# 2. SSM Architecture

Think:

```text
AWS Console / API
       ↓
Systems Manager
       ↓
SSM Agent
       ↓
EC2
       ↓
Command execution
```

The EC2 instance runs the SSM Agent.

The agent maintains communication with AWS and receives commands.

---

# 3. SSM Run Command

An administrator can send a command to one or many EC2 instances.

Example:

```text
Administrator
      ↓
SendCommand
      ↓
SSM
      ↓
EC2 #1
EC2 #2
EC2 #3
...
```

This is incredibly useful operationally.

But from a security perspective:

> **SSM is remote code execution with a legitimate AWS control plane.**

That's the important takeaway.

---

# 4. The Critical Event: `SendCommand`

CloudTrail records the management action:

```text
eventName=SendCommand
```

This should be one of your **high-value AWS monitoring events**.

Example:

```text
User
 ↓
SendCommand
 ↓
EC2
 ↓
Shell script
```

---

# 5. Why `SendCommand` Can Be Dangerous

Imagine an attacker compromises an IAM user with sufficient SSM permissions.

Instead of:

```text
SSH brute force
```

they can potentially do:

```text
AWS credentials
      ↓
SSM
      ↓
SendCommand
      ↓
EC2
      ↓
malicious command
```

No SSH port required.

No password guessing.

No traditional remote-login event.

That's why this is an important cloud attack path.

---

# 6. SSM as Command & Control

This is the key concept:

> **SSM can be abused as a cloud-native Command and Control mechanism.**

Example attack:

```text
Compromised IAM credential
          ↓
SSM SendCommand
          ↓
Download payload
          ↓
Execute payload
          ↓
Persistence / credential theft
          ↓
Lateral movement
```

The attacker is abusing a legitimate AWS administrative channel.

---

# 7. Process Tree During SSM Execution

This process tree is extremely useful for investigations:

```text
systemd
  ↓
amazon-ssm-agent
  ↓
ssm-agent-worker
  ↓
ssm-document-worker
  ↓
sh -c script
  ↓
sh script
  ├── command
  └── command
```

So if you find:

```text
amazon-ssm-agent
       ↓
shell
       ↓
suspicious command
```

you should investigate the associated `SendCommand`.

---

# 8. Correlating SSM Events

A good investigation looks like:

```text

    ↓

    ↓

    ↓
Command/document ID
    ↓
Host runtime logs
    ↓

    ↓
```

This is much stronger than looking at `SendCommand` alone.

# 10. SSM vs SSH

This distinction is interview gold.

|SSH|SSM Session / Run Command|
|---|---|
|Network connection to SSH|AWS management plane|
|Usually TCP/22|Doesn't require TCP/22|
|SSH authentication|IAM/AWS authentication|
|`auth.log` useful|`auth.log` may not show session|
|Network exposure required|Can work without public SSH|
|Traditional remote access|Cloud-native remote access|

So:

```text
No port 22
```

does **not** mean:

```text
No remote access.
```

SSM can provide remote management without opening SSH.

# 17. Auto Scaling

Now another challenge:

**EC2 Auto Scaling.**

Instead of one server:

```text
EC2
```

you may have:

```text
Auto Scaling Group
       ↓
EC2
EC2
EC2
EC2
EC2
...
```

Instances are automatically created and destroyed based on demand.

---

# 18. Why SOC Cares About Auto Scaling

Suppose an application normally has:

```text
10 EC2 instances
```

During peak demand:

```text
10 → 100 → 500 instances
```

Later:

```text
500 → 10
```

The instances may exist for only minutes.

That creates three major SOC problems:

```text
1. Agent deployment
2. Asset inventory
3. Evidence preservation
```

---

# 19. Problem #1 — EDR

Traditional EDR installation can take time.

If an EC2 instance lives for:

```text
10 minutes
```

but the security agent needs:

```text
reboot / installation / policy sync
```

you may lose visibility before the agent becomes operational.

---

# 20. Problem #2 — Asset Inventory

Traditional inventory:

```text
Server-01
Server-02
Server-03
```

Auto Scaling:

```text
Instance A
 ↓
terminated

Instance B
 ↓
terminated

Instance C
 ↓
terminated

Instance D
 ↓
new
```

The fleet constantly changes.

Therefore asset inventory needs automation.

---

# 21. Problem #3 — Evidence Preservation

Suppose:

```text
Attacker
 ↓
Compromised EC2
 ↓
Malicious process
```

Then Auto Scaling terminates the instance.

Evidence disappears.

Potentially lost:

- Process state
    
- Files
    
- Memory
    
- Local logs
    
- Malware
    
- Runtime artifacts
    

Therefore:

> **Short-lived infrastructure requires automated evidence collection.**

---

# 22. Auto Scaling Attack Scenario

An attacker exploits a vulnerable application running on an autoscaled EC2.

```text
Internet
   ↓
Vulnerable application
   ↓
Worker EC2
   ↓
Attacker shell
   ↓
Instance terminates
```

The attacker can simply repeat the exploit against another worker.

So short lifespan does **not** eliminate risk.

Example:

```text

open

open

```

For a large cloud environment, this can become painful.

# 25. Falco

**Falco** is a runtime threat-detection engine designed particularly for cloud-native and container environments.

Think:

```text
Linux / Container
      ↓
Runtime events
      ↓
Falco
      ↓
Detection rules
      ↓
Alert
      ↓
SIEM
```

---

# 26. Why Falco Is Interesting

Falco can provide useful process context.

Example:

```text
Process:
whoami

Parent:
bash

User:
root

Container:
mywebsite

Image:
wordpress:php8.2-apache
```

That context is extremely valuable.

---

# 27. Falco vs Auditd

|Auditd|Falco|
|---|---|
|Low-level auditing|Runtime threat detection|
|Large event volume|Can produce focused alerts|
|Raw system events|Rich contextual events|
|General Linux auditing|Strong cloud/container use case|
|More SIEM processing|Can detect locally|
|Container context can be awkward|Container-aware|

The important point isn't:

> "Falco replaces Auditd everywhere."

It's:

> **Falco can provide more useful runtime context for cloud/container workloads.**

---


That's excellent investigation data.

---

# 29. Example

Suppose Falco detects:

```text

proc.pcmdline = bash
container.name = mywebsite
```

That's more useful than:

```text

```

because you immediately have context.

# 30. Falco Rule Types

Two broad approaches:

### Raw event collection

Similar to Auditd:

```text
Process execution
File access
Network activity
```

High volume.

---

### Detection rules

Instead of logging everything:

```text
Suspicious shell
+
Sensitive file search
+
Container context
```

generate an alert.

Much lower volume.

---

# 31. SIEM-Style Falco

For example:

```text
Web server
   ↓
spawns shell
   ↓
shell runs wget
   ↓
downloads suspicious payload
```

A high-level Falco rule can turn that behavior into an alert.

This is generally more useful to a SOC than shipping every low-level syscall into Splunk.

---

# 32. Falco Splunk Query

The provided raw-event query:

```spl
index=task3
| rename output_fields.* as *
| rename proc.tty as logon.session, evt.rawres as exit.code
| table _time user.name logon.session proc.pid proc.cmdline proc.ppid proc.pexepath exit.code
```

### What it does

First:

```spl
index=task3
```

Search the Falco dataset.

Then:

```spl
| rename output_fields.* as *
```

Flattens the nested Falco fields.

Then:

```spl
| rename proc.tty as logon.session
```

Makes the field easier to interpret.

Then:

```spl
| table ...
```

displays the important investigation fields.

# 40. Why `ps` Is Interesting

Inside a container:

```bash

```

generally shows the container's process namespace.

From the host:

```bash

```

can reveal host and container processes.

So:

```text
Container view
    ↓
limited visibility

Host view
    ↓
broader visibility
```

This is why host-based monitoring is important.


# 52. Lambda Security Has Three Major Components

Memorize:

```text
Lambda Security
       │
 ┌─────┼─────┐
 ↓     ↓     ↓
Code  Trust  Execution
      Policy Role
```

### 1. Function code

Can contain vulnerabilities or malicious functionality.

### 2. Trust policy

Controls who/what can invoke or assume related roles.

### 3. Execution role

Determines what AWS actions the Lambda function can perform.

---

# 53. Lambda Execution Role

Example:

```text
Lambda
 ↓
ImageProcessorRole
 ↓
S3 permissions
```

The function inherits the permissions of its execution role when it calls AWS services.

Therefore:

> **A vulnerable Lambda + powerful execution role = potentially severe cloud compromise.**

---

# 54. Lambda Initial Access

A vulnerable Lambda can potentially become an attack vector.

Conceptually:

```text
Internet/event
      ↓
Vulnerable Lambda
      ↓
Code execution
      ↓
AWS credentials/context
      ↓
AWS API access
```

The exact attack depends on the function and architecture.

---

# 55. Lambda Persistence

Attackers may modify existing Lambda functions.

For example:

```text
Existing Lambda
      ↓
Attacker modifies code
      ↓
Backdoor added
      ↓
Function invoked later
      ↓
Malicious action
```

This is particularly nasty because the function can still look like a legitimate business workload.

---

# 56. Lambda Privilege Escalation

This is one of the most important concepts.

Suppose:

```text
Developer IAM user
        ↓
Can modify Lambda
        ↓
Cannot directly launch EC2
```

But:

```text
Lambda execution role
        ↓
EC2FullAccess
SSMFullAccess
```

Then:

```text
Developer
    ↓
Modify Lambda code
    ↓
Lambda executes
    ↓
Uses powerful role
    ↓
EC2/SSM capabilities
```

That's a **privilege-escalation path**.

---

# 57. Why This Works

The developer doesn't need direct:

```text
ec2:RunInstances
```

permission.

They only need enough permission to modify/execute the Lambda, while the Lambda itself possesses the privileged execution role.

This is a classic **indirect privilege escalation** pattern.

---

# 58. Lambda Backdoor Attack Chain

The provided scenario can be represented as:

```text
Compromised IAM User
        ↓

        ↓
Create/modify execution role
        ↓

        ↓
UpdateFunctionCode
        ↓
Malicious functionality
        ↓

        ↓

        ↓

        ↓

```

This is exactly the kind of multi-event correlation SOC L2 should understand.

# 59. Critical Lambda Events

Memorize these:


---

# 60. `AddPermission*`

This modifies the Lambda's resource-based permissions/trust behavior.

Pay special attention to:

```text
Principal = *
```

because it can indicate public/anonymous invocation depending on the configuration.

Conceptually:

```text
Lambda
 ↓
Public permission
 ↓
Internet
 ↓
Function invocation
```

---

# 61. `UpdateFunctionCode*`

This changes the actual Lambda code.

Potential implications:

```text
Legitimate deployment
       OR
Backdoor
       OR
Malicious functionality
```

Therefore investigate:

- Who changed it?
    
- From where?
    
- What changed?
    
- Was there a deployment?
    
- Was there a corresponding CI/CD event?
    
- Did the function's behavior change?
    

---

# 62. `PublishLayerVersion*`

Lambda layers can contain shared libraries/dependencies.

Changing a layer can therefore alter what code executes.

Think:

```text
Lambda
 ↓
Layer
 ↓
Dependency
```

A malicious layer can become a supply-chain/persistence mechanism.

# 67. Lambda Role Investigation

Suppose:


```text

```

Trace the role backward.


Then determine the role's **effective permissions**.

Because the role name alone can be misleading.

# 70. Lambda Invoke Caveat

The material highlights an important logging consideration:

> `Invoke*` may not appear in CloudTrail in the same way as management-plane configuration events unless the relevant invocation/data-event logging is enabled.

So don't assume:


Understand what telemetry your environment actually collects.

This is a very important SOC lesson:

> **Absence of evidence is not automatically evidence of absence.**

# 75. Interview Questions You Should Be Able to Answer

### Q1. Why is `SendCommand` important?

> SSM Run Command provides legitimate remote command execution on EC2. If an attacker compromises an identity with SSM permissions, they can potentially execute commands without using SSH. Therefore I would correlate `SendCommand` with the initiating identity, target instance, command/document, source IP, and host runtime telemetry.

---

### Q2. How do you distinguish SSM from SSH?

```text
SSH:
sshd → shell
auth.log

SSM:
amazon-ssm-agent
 → session/command worker
 → shell
CloudTrail:
StartSession / SendCommand
```

---

### Q3. Why is Auto Scaling difficult for SOC?

> Instances can be created and destroyed rapidly, making asset inventory, EDR deployment, telemetry collection, and forensic evidence preservation difficult. Security controls therefore need to be automated through the instance provisioning lifecycle.

---

### Q4. Why is Falco useful?

> Falco provides runtime detection with process and container context. Instead of receiving only a raw syscall, the SOC can identify the command, parent process, user, container ID, container name, and image, making investigation and detection more effective.

---

### Q5. How can Lambda become a privilege-escalation path?

> If a low-privileged user can modify a Lambda function but the Lambda's execution role has powerful permissions, the attacker can alter the function to perform actions the user cannot perform directly. This creates an indirect privilege-escalation path.

---

### Q6. Which Lambda events are high priority?

Memorize:

```text
CreateFunction*
UpdateFunctionCode*
UpdateFunctionConfiguration*
AddPermission*
PublishLayerVersion*
```

And investigate:

```text
Invoke*
```

with the caveat that invocation visibility depends on the telemetry/logging configuration.

### The five things I'd memorize from this section:

