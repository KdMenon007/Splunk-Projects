
### 1. Why companies moved identity to the cloud

The old model was fragmented:

> Employee → Email account → HR account → Project-management account → File-sharing account

Each application had its own authentication and security controls. That creates several problems:

- Different password policies
    
- MFA unavailable on some applications
    
- Authentication logs scattered across systems
    
- Difficult employee onboarding/offboarding
    
- Inconsistent access controls
    
- Harder investigation of suspicious logins
    

A cloud IdP such as **Microsoft Entra ID** provides a centralized identity control plane:

> **User → Entra ID → Authentication → Authorization → Application**

So instead of every application independently deciding _"Who is this person?"_, the IdP can establish the user's identity and provide that information to the application.

---

### 2. The important distinction: Authentication vs Authorization

This is **very interview-important**.

|Concept|Question|Example|
|---|---|---|
|**Authentication (AuthN)**|Who are you?|Prove you're Alice using password + MFA|
|**Authorization (AuthZ)**|What can you access?|Alice can read Finance files|
|**Auditing**|What happened?|Alice logged in from India at 09:32|

Think:

**AuthN → Who are you?**  
**AuthZ → What are you allowed to do?**  
**Audit → What did you do?**

### 3. What exactly is an identity?

An identity is a **digital representation of an entity** that allows systems to recognize and control that entity.

There are three major categories:

|Identity|Represents|Examples|
|---|---|---|
|**Human identity**|Person|Employee, contractor, customer, vendor|
|**Workload identity**|Software|Application, service, script, container, VM|
|**Device identity**|Hardware/device|Laptop, phone, IoT/OT device|

This is where many beginners get caught.

**Identity ≠ user.**

A server can have an identity.

An application can have an identity.

A container can have an identity.

A laptop can have an identity.

A human can have an identity.

```text
Digital Identities

│   ├── Employees
│   ├── Contractors
│   ├── Customers
│   ├── Partners
│   └── Vendors
│
└── Machine Identities
    │
    ├── Workload Identities
    │   ├── Applications

    │
```

**Security implication:** machine identities are extremely important because they can possess privileges just like humans.

For example:

> `backup-service` → authenticate → access production database

There may be no human sitting behind that login.

### 5. What is an Identity Provider?

An **Identity Provider (IdP)** is the trusted system responsible for managing identities and authentication.

Examples include:

- Microsoft Entra ID
    
- Google Identity
    
- Apple
    
- Amazon
    
- Other enterprise identity platforms
    

A simplified flow:

```text
             ┌──────────────┐
             │    Alice     │
             └──────┬───────┘
                    │ Login
                    ▼
             ┌──────────────┐
             │     IdP      │
             │  Entra ID    │
             └──────┬───────┘
                    │
          Authentication
                    │
                    ▼
             ┌──────────────┐
             │ Application  │
             │   / Service  │
             └──────────────┘
```

Your Google example works the same way:

> Google = **Identity Provider**  
> Spotify = **Service Provider**

You authenticate with Google, and Spotify trusts the authentication assertion/token issued through that identity relationship.

### 6. Why SSO is such a big deal

Without SSO:

```text
Email      → password
HR         → password
Jira       → password
GitHub     → password
Cloud      → password
```

That's **password sprawl**.

With SSO:

```text
                 ┌── Email
                 ├── HR
User → IdP ──────┼── Jira
                 ├── GitHub
                 └── Cloud
```

The user authenticates centrally, and applications trust the IdP.

This also gives security teams a central place to enforce controls such as:

- MFA
    
- Conditional Access
    
- Risk-based authentication
    
- Device compliance
    
- Sign-in restrictions
    
- Session controls

### 7. Why GRC people should care

This isn't merely an IAM technical topic.

From a **GRC perspective**, centralized identity enables governance and control.

For example:

**Governance**

> Every employee must have an individually assigned corporate identity.

**Risk**

> Excessive privileges could allow an attacker to compromise critical systems.

**Control**

> MFA is required for privileged accounts.

**Compliance**

> Access must be reviewed periodically.

**Assurance**

> Internal audit verifies that access reviews occurred and evidence exists.

So you can connect the entire thing:

> **Identity → Access → Risk → Control → Evidence → Audit**

That's exactly the bridge between **IAM and GRC**.

### 8. Interview answer

If an interviewer asks:

**"Why did organizations move identities to cloud identity providers?"**

A strong answer would be:

> Organizations moved toward centralized cloud identity providers because managing authentication separately across every application created fragmented security controls, inconsistent authentication policies, poor visibility, and difficult user lifecycle management. A cloud IdP centralizes identity management and enables capabilities such as SSO, MFA, Conditional Access, centralized logging, and consistent access policies across applications. It also improves governance because organizations can establish common identity controls and generate centralized evidence for monitoring, compliance, and audits.

And if they ask:

**"Are identities only user credentials?"**

Answer:

> No. A digital identity represents an entity in a computing environment. That can be a human, a device, or a workload such as an application, service, container, or virtual machine. Each identity can authenticate and potentially receive authorization to access resources.

### The one sentence to remember

**Identity answers "who or what is this entity?", authentication proves it, authorization determines what it can do, and auditing records what happened.**

That sentence is basically the whole lesson compressed into one neat little cyber burrito.

## 1. The core idea

Think of Entra ID as the **front door to the organization's cloud environment**.

```text
                    INTERNET
                       │
                       ▼
                ┌─────────────┐
                │  Entra ID   │
                │ Identity     │
                │ Control Plane│
                └──────┬──────┘
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
    Outlook          Teams          SharePoint
       │               │                │
       └───────────────┼────────────────┘
                       ▼
                Internal Apps
```

If an attacker compromises an ordinary employee account, they may gain access to email, files, Teams, applications, etc.

If they compromise a **privileged identity**, the impact can become dramatically worse.

So the attacker's objective isn't necessarily:

> “Break into the network.”

It can simply be:

> **“Become a legitimate identity.”**

That's a major mindset shift in modern cloud security.

---

# 2. Why stolen cloud credentials are dangerous

Traditional attack thinking often looks like:

**Internet → Firewall → Internal Network → Endpoint → Server**

Cloud identity attacks can look more like:

**Attacker → Internet → Valid credentials → IdP → Cloud resources**

The attacker may never need to touch the organization's internal network.

This is why **identity has become a primary security perimeter**.

---

# 3. Why SSO increases both security and impact

SSO is great for usability and security, but it also creates concentration of privilege.

Suppose Alice's identity provides access to:

```text
Alice
 │
 ├── Outlook
 ├── Teams
 ├── SharePoint
 ├── HR application
 ├── Internal applications
 └── Cloud resources
```

If Alice's credentials are stolen, the attacker potentially gets access to **multiple services**.

So:

> **SSO reduces password sprawl, but a compromised identity can have a larger blast radius.**

That's why SSO must be combined with strong authentication and access controls.

---

# 4. “If Entra ID is secure, why do attacks still happen?”

This is probably the most important question in the section.

Because:

> **A security platform can provide controls without an organization actually configuring and enforcing them correctly.**

Think of it like a bank vault.

The vault may be extremely secure.

But if someone leaves the door unlocked, the vault's engineering doesn't matter much.

Same principle here.

### Security capability ≠ security configuration

|Capability|Security failure|
|---|---|
|MFA|MFA not enforced|
|Conditional Access|Overly broad exclusions|
|Risk detection|Risk policies disabled|
|Privileged access controls|Too many standing admins|
|Password protection|Weak password configuration|
|Logging|Logs not monitored|
|Access controls|Excessive permissions|

This is a **GRC goldmine** because these are essentially control-design and control-operating questions.

# 5. The major identity security gaps

![[Pasted image 20260821073934.png]]

### MFA not enforced

Without MFA:

```text
Username + Password
       ↓
     Access
```

A stolen password may be enough.

With MFA:

```text
Username + Password
       ↓
     MFA
       ↓
     Access
```

MFA isn't magic—attackers can use phishing, session/token theft, MFA fatigue, and other techniques—but it raises the bar significantly.

---

### Overly permissive policies

Imagine:

> “Allow everyone to sign in from anywhere.”

That's convenient.

It's also a security team's headache waiting to happen.

Better policies can consider signals such as:

- User
    
- Location
    
- IP reputation
    
- Device
    
- Application
    
- Authentication method
    
- Risk
    
- Session context
    

The system can then:

**Allow / Block / Require additional verification**

---

### Excessive administrative privileges

This is particularly dangerous.

Suppose an organization has:

```text
100 users
20 global administrators
```

That's a huge privileged attack surface.

If one administrator is compromised:

> **User compromise → Tenant compromise**

Good security architecture follows **least privilege** and minimizes standing administrative access.

---

### Weak passwords

Password security still matters.

An attacker may obtain credentials through:

- Phishing
    
- Credential stuffing
    
- Password reuse
    
- Data breaches
    
- Infostealers
    
- Social engineering
    

The important point is that the attacker doesn't necessarily need to exploit Entra ID itself.

They can simply obtain a **valid credential**.

---

### Disabled risk policies

Modern identity systems can evaluate signals indicating that authentication may be suspicious.

For example:

```text
User: Alice
Normal location: India
Normal device: Corporate laptop

        ↓

Sudden authentication
Location: Unusual country
Device: Unknown
IP: Suspicious
Behavior: Abnormal

        ↓

Risk evaluation

        ↓

Require MFA / Block / Investigate
```

If those protections aren't properly configured, the suspicious login may succeed.

# 6. Identity logs are where the investigation begins

This is where your **SOC Level 1/2 knowledge** starts connecting directly to cloud identity.

An authentication event can tell you:

|Signal|Investigation question|
|---|---|
|Username|Who was targeted?|
|Timestamp|When did it happen?|
|Source IP|Where did it originate?|
|Location|Is the geography unusual?|
|Device|Is this a known device?|
|Browser|Is the client normal?|
|Application|What was accessed?|
|Authentication method|Password? MFA? SSO?|
|MFA result|Did MFA succeed/fail?|
|Conditional Access|Allowed or blocked?|
|Result|Successful or failed?|

Don't just look at:

> **Login = Successful**

That's beginner-level analysis.

You want to ask:

> **Who + when + where + from what device + using what method + accessing what + under what policy + what happened afterward?**

That's SOC analysis.

# 7. The timeline mindset

The section makes an excellent point here.

A single event can be misleading.

Suppose you see:

```text
09:01  Failed login
09:02  Failed login
09:03  Successful login
09:04  MFA completed
09:07  Mailbox accessed
09:12  Large number of emails accessed
09:18  Files downloaded
```

Looking at only the successful login:

> “Authentication successful.”

Looking at the **timeline**:

> “Potential account compromise followed by cloud resource access and possible data theft.”

Huge difference.

# 8. Identity logs + M365 logs = stronger investigation

This is one of the most important concepts to remember.

### Identity logs tell you:

> **How did the account authenticate?**

### Service logs tell you:

> **What did the account do afterward?**

For example:

```text
Entra ID
   │
   ├── Successful login
   ├── IP address
   ├── Device
   └── MFA result
          │
          ▼
       M365
          │
          ├── Mailbox accessed
          ├── Emails read
          ├── Files downloaded
          ├── SharePoint accessed
          └── Teams activity
```

This correlation gives you the **attack story**, rather than isolated events.

# 9. A practical SOC investigation example

Imagine:

> User: `alice@company.com`

You observe:

```text
10:01 — Failed authentication
10:02 — Failed authentication
10:03 — Successful authentication
10:03 — New IP address
10:03 — Unknown device
10:04 — MFA successful
10:06 — Outlook accessed
10:10 — Hundreds of emails accessed
10:15 — SharePoint files downloaded
```

A weak analyst says:

> “MFA succeeded, therefore everything is fine.”

A better analyst says:

> “The successful MFA event does not automatically prove the activity is legitimate. The unusual IP, unfamiliar device, authentication history, and subsequent high-volume mailbox and file activity warrant investigation.”

That's the kind of reasoning you want.

# 10. Interview framework: Cloud identity attack

If an interviewer gives you a suspicious Entra ID login, use this structure:

### **1. Identify**

Who is the account?

### **2. Authenticate**

How did authentication occur?

### **3. Locate**

Where did the authentication originate?

### **4. Device**

Was the device known and compliant?

### **5. Policy**

What did Conditional Access do?

### **6. Timeline**

What happened before and after the login?

### **7. Activity**

What resources did the identity access?

### **8. Impact**

Was data accessed, modified, or exfiltrated?

### **9. Containment**

Should the account/session/token be revoked or access restricted?

### **10. Root cause**

How did the attacker obtain or abuse the identity?

## The mental model to lock in

Remember this chain:

**Identity → Authentication → Authorization → Cloud Resource → Activity → Logs → Investigation**

And from an attacker's perspective:

**Credential → Authentication → Valid Identity → Access → Persistence/Discovery → Data Access**

The key SOC lesson is:

> **Don't investigate the login in isolation. Investigate the identity's entire timeline and what happened after authentication.**

And the key GRC lesson is:

> **Most identity breaches aren't necessarily failures of the identity platform itself; they can be failures of configuration, governance, least privilege, monitoring, or control enforcement.**
