## 1. The attack chain — remember this

```text
Credential Theft
      ↓
Initial Access
      ↓
Mailbox Discovery
      ↓
Persistence
 ┌────┼───────────────┐
 ↓    ↓               ↓
Inbox  Mailbox       Delegate
Rules  Forwarding    Access
 └────┼───────────────┘
      ↓
Email Reconnaissance
      ↓
Phishing from trusted account
      ↓
Lateral Movement
```

A good SOC analyst asks:

> **"What did the attacker do after they got in?"**

Not merely:

> "Was there a successful login?"

---

# 2. The three log sources

|Log source|Main question it answers|
|---|---|
|**Entra/Exchange Sign-in**|Who authenticated, from where, and did it succeed?|
|**M365 Unified Audit**|What did the user actually do inside Exchange?|
|**Message Trace**|Which emails were sent, to whom, and were they delivered?|

Think of them as:

```text
SIGN-IN LOG
    ↓
"How did they get in?"

AUDIT LOG
    ↓
"What did they do?"

MESSAGE TRACE
    ↓
"Who did they affect?"
```

That mental model is gold for interviews.

---

# 3. Sign-in logs — Initial Access

The query:

```spl
index=* sourcetype="azure:aad:signin" appDisplayName="One Outlook Web"
| table _time userPrincipalName appDisplayName ipAddress location.city status.errorCode
| sort - _time
```

Important fields:

|Field|Meaning|
|---|---|
|`_time`|When authentication occurred|
|`userPrincipalName`|Account being accessed|
|`ipAddress`|Source IP|
|`location.city`|Approximate login location|
|`status.errorCode`|Authentication result|

### SOC thinking

Suppose you normally see:

```text
user: alice@company.com
location: Bengaluru
IP: 103.x.x.x
```

Then suddenly:

```text
user: alice@company.com
location: Moscow
IP: 185.x.x.x
successful login
```

That is **not automatically malicious**.

You investigate:

- Is the user travelling?
    
- Is the IP associated with corporate infrastructure/VPN?
    
- Is the device familiar?
    
- Was MFA satisfied?
    
- Were there previous failed attempts?
    
- What happened immediately after the login?
    

The last question is particularly important.

# 4. Audit logs — the attacker's activity

Query:

```spl
index=* sourcetype="o365:management:activity" Workload=Exchange
| table _time UserId Operation Workload
```

The key operations form a very useful investigation vocabulary:

|Operation|SOC interpretation|
|---|---|
|`MailItemsAccessed`|Attacker/user accessed mailbox contents|
|`Send`|Email sent from mailbox|
|`New-InboxRule`|New rule created|
|`Set-InboxRule`|Existing rule modified|
|`Set-Mailbox`|Mailbox configuration changed|
|`Add-MailboxPermission`|Delegate access granted|

You should be able to see these and immediately think:

```text
MailItemsAccessed → Recon / data exposure
New-InboxRule     → Persistence / concealment
Set-InboxRule     → Persistence / concealment
Set-Mailbox       → Forwarding / persistence
Add-MailboxPermission → Persistent mailbox access
Send              → Phishing / lateral movement
```

---

# 5. Inbox-rule abuse

This is one of the most important parts.

### Creation

```spl
index=* Workload=Exchange Operation=New-InboxRule 
| table _time UserId Name DeleteMessage ForwardTo SubjectContainsWords
```

The interesting fields are:

```text
Name
SubjectContainsWords
DeleteMessage
ForwardTo
```

### Why attackers use rules

Imagine the attacker sends:

```text
"URGENT: Invoice Payment Required"
```

to 20 employees.

One employee replies:

> "Hey Alice, did you actually send this?"

If the attacker has created:

```text
SubjectContainsWords = "Invoice"
DeleteMessage = True
```

the reply can disappear before Alice sees it.

So the attacker gets:

```text
Compromise
   ↓
Send phishing
   ↓
Victim receives it
   ↓
Victim replies
   ↓
Rule deletes reply
   ↓
Account owner remains unaware
```

That's **concealment**, not merely persistence.

---

# 6. Forwarding rules

A forwarding rule can be even more interesting.

Example conceptually:

```text
IF subject contains "invoice"
THEN forward to attacker@example.com
```

The attacker doesn't necessarily want every email.

They want valuable information:

- invoices
    
- payments
    
- credentials
    
- contracts
    
- MFA-related messages
    
- password-reset notifications
    

So:

```text
ForwardTo = external address
```

is a major investigation point.

### Strong red flags

```text
ForwardTo → external domain
DeleteMessage = True
Created outside normal hours
Created immediately after suspicious login
Generic/suspicious rule name
```

---

# 7. Mailbox-level forwarding

This is different from an inbox rule.

### Inbox rule

```text
Specific conditions
        ↓
Forward matching messages
```

### Mailbox forwarding

```text
EVERY incoming email
        ↓
External destination
```

Query:

```spl
index=* Workload=Exchange Operation=Set-Mailbox
| table _time UserId ForwardingSmtpAddress DeliverToMailboxAndForward
```

The big red flag:

```text
DeliverToMailboxAndForward = False
```

That means the mailbox owner may **not receive the message themselves**.

Conceptually:

```text
Incoming email
      ↓
   Mailbox
      ↓
 Attacker's external address

Victim may never see it
```

That's a very nasty persistence/exfiltration mechanism.

---

# 8. Delegate access

Query conceptually:

```text
Operation = Add-MailboxPermission
```

Look at:

```text
Trustee
```

The attacker could grant another account access to the mailbox.

Why is that dangerous?

Because changing Alice's password doesn't necessarily solve the entire problem if:

```text
Attacker account
      ↓
Delegate permission
      ↓
Alice's mailbox
```

still exists.

Therefore remediation must include **permission review**, not just password reset.

# 9. MailItemsAccessed — reconnaissance

Query:

```spl
index=* Workload=Exchange Operation=MailItemsAccessed
| table _time UserId ClientIPAddress OperationCount
```

This answers:

> **"Was someone actually accessing mailbox contents?"**

Imagine:

```text
09:02  Successful login
09:05  MailItemsAccessed
09:08  MailItemsAccessed
09:15  MailItemsAccessed
09:30  New-InboxRule
09:42  Send
```

Now you've got a story.

The attacker didn't simply log in.

They:

1. authenticated
    
2. explored the mailbox
    
3. established persistence
    
4. weaponised the account
    

That's much stronger evidence.

---

# 10. Send operation — lateral movement

Query:

```spl
index=* Workload=Exchange Operation=Send
| table _time UserId Item.Subject ClientIP SaveToSentItems
```

Important fields:

```text
UserId
Item.Subject
ClientIP
SaveToSentItems
```

### `SaveToSentItems=False`

This is interesting because the attacker may be trying to avoid leaving an obvious copy in Sent Items.

So:

```text
Compromised mailbox
       ↓
Send phishing email
       ↓
SaveToSentItems=False
       ↓
Victim sees less evidence
```

Combine that with:

```text
High-volume sends
+
Unusual IP
+
Suspicious subject
```

and the case gets considerably stronger.

# 11. Message Trace — scope the campaign

This is where the investigation gets really useful.

```spl
index=* sourcetype="o365:reporting:messagetrace"
| table Received SenderAddress RecipientAddress Subject Status FromIP
```

Audit logs tell you:

> Alice sent an email.

Message trace tells you:

> Alice sent this particular email to Bob, Carol, Dave, and Eve, and it was delivered.

That's the difference.

### Example

Audit:

```text
Send
UserId = alice@company.com
Subject = Urgent Invoice Update
```

Message trace:

```text
Alice → Bob     Delivered
Alice → Carol   Delivered
Alice → Dave    Delivered
Alice → Eve     Failed
```

Now your SOC team knows exactly who needs investigation.

# 12. The investigation timeline

This is probably the **most important thing to learn from this entire section**.

Imagine your logs produce:

```text
08:41
Successful Exchange login
        ↓
09:02
MailItemsAccessed
        ↓
09:17
MailItemsAccessed
        ↓
09:31
New-InboxRule
DeleteMessage=True
        ↓
09:35
Set-Mailbox
ForwardingSmtpAddress=external address
        ↓
09:47
Send
Subject="Urgent Invoice Update"
SaveToSentItems=False
        ↓
09:48
Message Trace
25 recipients
        ↓
10:05
More suspicious activity
```

Your conclusion becomes:

> The account was likely compromised at 08:41. The actor subsequently accessed mailbox contents, established persistence through mailbox/rule manipulation, and then used the compromised account to conduct an internal phishing campaign.

That's **SOC analyst language**.

Notice we're not saying:

> "The IP looks weird so it's hacked."

We're building an evidence-backed narrative.

# 13. What each technique accomplishes

|Attacker action|Purpose|
|---|---|
|Steal credentials|Obtain valid identity|
|Successful sign-in|Initial access|
|`MailItemsAccessed`|Reconnaissance / information gathering|
|`New-InboxRule`|Persistence / concealment|
|`Set-InboxRule`|Modify concealment/persistence|
|`Set-Mailbox`|Mailbox forwarding / persistence / exfiltration|
|`Add-MailboxPermission`|Persistent delegated access|
|`Send`|Internal phishing|
|Message Trace|Campaign propagation / victim identification|

A useful way to remember it:

```text
GET IN
  ↓
LOOK AROUND
  ↓
STAY HIDDEN
  ↓
STEAL MAIL
  ↓
ABUSE TRUST
  ↓
SPREAD
```

# 14. The SOC investigation workflow

When you get an Exchange compromise alert, don't randomly search logs.

Use a structured workflow:

```text
                 ALERT
                   │
                   ▼
        ┌─────────────────────┐
        │ 1. Validate Login   │
        └──────────┬──────────┘
                   ↓
          Who / IP / Location
                   ↓
        ┌─────────────────────┐
        │ 2. Build Timeline   │
        └──────────┬──────────┘
                   ↓
        What happened after
              login?
                   ↓
        ┌─────────────────────┐
        │ 3. Check Mailbox    │
        └──────────┬──────────┘
                   ↓
     MailItemsAccessed / Rules /
       Forwarding / Delegates
                   ↓
        ┌─────────────────────┐
        │ 4. Check Sending    │
        └──────────┬──────────┘
                   ↓
              Send events
                   ↓
        ┌─────────────────────┐
        │ 5. Scope Campaign   │
        └──────────┬──────────┘
                   ↓
            Message Trace
                   ↓
        ┌─────────────────────┐
        │ 6. Contain          │
        └──────────┬──────────┘
                   ↓
     Reset / revoke / remove /
       notify / investigate
```

# 15. Interview-ready explanation

If an interviewer asks:

**"How would you investigate a compromised Exchange Online account?"**

A strong answer would be:

> "I'd start with the Entra ID sign-in logs to establish the initial access, looking at the account, source IP, location, authentication result and timing. Then I'd pivot into the Microsoft 365 unified audit logs to determine what the account did after authentication. I'd specifically investigate MailItemsAccessed, inbox-rule creation or modification, mailbox forwarding changes, delegate permissions and Send operations. If I identify suspicious outbound mail, I'd pivot to message trace to determine the recipients, delivery status and scope of the phishing campaign. Finally, I'd build a timeline correlating authentication, mailbox access, persistence and outbound activity, then contain the account by revoking sessions/tokens, resetting credentials, removing malicious rules or forwarding, removing unauthorized delegates, and investigating potentially affected recipients."

That's the kind of answer that demonstrates **investigation methodology**, not just memorised terminology.

---

## 16. The biggest SOC lesson

Don't investigate these events independently.

Bad investigation:

```text
Successful login → suspicious
```

Better:

```text
Successful login
      +
Unusual source
      +
Mailbox access
      +
Inbox rule creation
      +
External forwarding
      +
Suspicious Send
      +
Multiple delivered recipients
      =
Strong compromise narrative
```

**Correlation is the superpower.**

One event can be benign. A sequence of related events can tell you the entire attack story.
