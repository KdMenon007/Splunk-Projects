The key mental model is:

> **Entra ID authenticates → Intune manages → Endpoint executes → SIEM detects**

### 1. What Intune is

|Area|SOC L2 relevance|
|---|---|
|MDM|Manages corporate devices|
|Asset inventory|Identify device/user ownership|
|Configuration|Push security settings|
|Application deployment|Install software remotely|
|Compliance|Determine whether device is trusted|
|Conditional Access|Control access based on device state|
|Remote wipe|Potential destructive action|
|Platform scripts|Potential remote code execution mechanism|
|App deployment|Potential malware deployment mechanism|

## 2. The most important attack chain

Think about Intune abuse like this:

```text
Compromised Admin Account
        ↓
Login to Intune
        ↓
Suspicious Device / Location
        ↓
Intune Administrative Action
        ↓
 ┌──────────────┬───────────────┬───────────────┐
 ↓              ↓               ↓
Wipe           Script           App Deployment
 ↓              ↓               ↓
Destroy        Execute         Deploy Malware
Data           Code            at Scale
```

The **login is your early warning**.

The actual destructive action may happen later.

# 3. Intune + Entra ID relationship

This distinction is crucial.

### Entra ID

Primarily gives you:

- Identity
    
- Authentication
    
- Device identity
    
- Sign-in logs
    
- Conditional Access
    
- Audit activity
    

### Intune

Primarily gives you:

- Device management
    
- Compliance
    
- Configuration
    
- Applications
    
- Scripts
    
- Remote actions
    

So when investigating an Intune incident, don't investigate Intune in isolation.

Correlate:

```text
Entra Sign-in
      +
Entra Audit
      +
Intune Audit
      +
Endpoint/Sysmon
      +
EDR
```

# 4. Device context — VERY important

When a user signs into a cloud application, Entra can provide device information.

Important fields:

```text
deviceDetail
deviceDetail.displayName
deviceDetail.isManaged
deviceDetail.isCompliant
deviceDetail.trustType
```

### Example

```text
isManaged = false
isCompliant = false
displayName = empty
```

This is suspicious when the account is an **Intune administrator**.

Compare:

|Device state|Interpretation|
|---|---|
|Unknown/unmanaged|Higher risk|
|Entra joined|Known identity|
|Intune managed|Organization-controlled device|
|Intune managed + compliant|Stronger trust signal|

**Important:** unmanaged ≠ automatically malicious.

It's a **risk indicator**, not proof of compromise.

# 5. Splunk Query — Intune login from unmanaged device

```spl
index=intune sourcetype=azure:aad:signin appDisplayName=*Intune* deviceDetail.displayName=""
| rename deviceDetail.* as dvc.*
| table _time appDisplayName ipAddress dvc.isManaged dvc.isCompliant dvc.displayName user
```

### What this does

```text
index=intune
```

Search Intune-related data.

```text
sourcetype=azure:aad:signin
```

Only Entra sign-in events.

```text
appDisplayName=*Intune*
```

Find Intune application access.

```text
deviceDetail.displayName=""
```

Look for missing device name.

Then:

```spl
rename deviceDetail.* as dvc.*
```

Makes fields easier to work with.

Finally:

```spl
table ...
```

Shows the important investigation fields.

### SOC interpretation

Ask:

1. Who logged in?
    
2. Is the user an Intune admin?
    
3. What IP was used?
    
4. Is the device managed?
    
5. Is it compliant?
    
6. Is the login geographically unusual?
    
7. Is the login outside normal working hours?
    
8. What happened immediately afterward?

# 6. The three big Intune attack surfaces

Memorize this:

```text
INTUNE ABUSE

1. WIPE
2. SCRIPT
3. APPLICATION
```

### ① Wipe

Attacker:

```text
Compromise admin
      ↓
Access Intune
      ↓
Select devices
      ↓
Wipe
      ↓
Factory reset
```

Impact:

**Very high.**

---

### ② Platform Script

Attacker:

```text
Compromise Intune admin
       ↓
Create PowerShell script
       ↓
Assign to devices
       ↓
Intune executes
       ↓
SYSTEM/user context
       ↓
Code execution at scale
```

This is particularly dangerous because Intune is a legitimate administrative mechanism.

Classic LOLBin-style problem:

> The attacker doesn't necessarily need malware when the management platform itself can execute commands.

---

### ③ Application deployment

Attacker can potentially abuse Intune to distribute a malicious application.

```text
Malicious package
       ↓
Intune
       ↓
Multiple endpoints
       ↓
High privilege execution
       ↓
Mass compromise
```

This turns a single compromised administrator into a potential **enterprise-wide deployment mechanism**.

# 7. Remote wipe detection

The relevant Intune audit activity is:

```text
wipe ManagedDevice
```

Splunk:

```spl
index=intune sourcetype="o365:graph:intune" wipe
| eval deviceid=mvindex('resources{}.modifiedProperties{}.newValue', 0)
| table _time activityType actor.userPrincipalName deviceid
```

### Important fields

```text
_time
activityType
actor.userPrincipalName
deviceid
```

The critical question:

> **Who issued the wipe against which device ID?**

Then correlate the device ID with Entra/device inventory information to determine:

```text
Device ID
   ↓
Hostname
   ↓
User
   ↓
Hardware
   ↓
OS
```

# 8. Don't make the rookie detection mistake

A tempting rule is:

```text
IF mass wipe occurs
THEN alert
```

That's useful for investigation, but it's **late detection**.

The wipe may already have happened.

Better detection strategy:

```text
              EARLY
                ↓
       Suspicious Intune login
                ↓
       Suspicious admin activity
                ↓
       Script creation/assignment
                ↓
       Wipe command
                ↓
              LATE
```

Your best opportunity is usually **before the destructive action**.

# 9. Platform Script detection

Search:

```spl
index=intune sourcetype="o365:graph:intune" activityType=*DeviceManagementScript*
| eval action=mvindex(split(activityType, " "), 0)
| eval script='resources{}.resourceId'
| eval target=mvindex('resources{}.modifiedProperties{}.newValue', 0)
| eval target=if(action="assignDeviceManagementScript", target, "N/A")
| table _time actor.userPrincipalName action script target
```

This gives you:

```text
Time
↓
Actor
↓
Action
↓
Script ID
↓
Target
```

# 10. Script lifecycle — memorize this

```text
CREATE
  ↓
ASSIGN
  ↓
EXECUTE
  ↓
DELETE
```

In SIEM:

```text
CreateDeviceManagementScript
        ↓
AssignDeviceManagementScript
        ↓
Endpoint execution
        ↓
DeleteDeviceManagementScript
```

### Investigation trick

If you see:

```text
CREATE
ASSIGN
DELETE
```

don't assume deletion means nothing happened.

The attacker may have:

```text
created script
→ assigned script
→ executed payload
→ deleted script
```

Deletion can actually be **anti-forensic behavior**.

```text
              ↓
          powershell.exe
```


Especially:


This can provide:

- Script duration
    
- Execution status
    
- Output
    
- Errors
    
- Metadata

# 12. SOC correlation

This is where L2 analysts should level up.

Don't just search:

```spl

```

Ask:

> **Why did PowerShell execute?**

Potentially legitimate:

```text

```

Suspicious Intune activity:

```text
Intune Agent
      ↓
AgentExecutor
      ↓
PowerShell
      ↓
Encoded command
      ↓
Network connection
      ↓
Credential access
```

Now you've got a much stronger investigation.

# 16. Stryker case — what you should remember

The case demonstrates a nasty truth:

> **Cloud management platforms are powerful enough to become enterprise-scale attack infrastructure when privileged credentials are compromised.**

The attacker doesn't necessarily need:

```text
ransomware
malware
exploit
worm
```

They may simply need:

```text
Valid admin credentials
        +
Intune privileges
        ↓
Legitimate administrative functionality
        ↓
Mass destruction
```

That's why **identity security is endpoint security** in modern Microsoft environments.

# 17. Defensive controls

### Privileged accounts

Use:

- Conditional Access
    
- MFA/passkeys
    
- Hardware-backed authentication
    
- Identity Protection
    
- Privileged Identity Management
    
- Minimal Global Administrators
    
- Separate admin accounts
    

### Intune

Use:

- Custom RBAC roles
    
- Scope Tags
    
- Multi-admin approval
    
- Least privilege
    
- Monitoring of scripts
    
- Monitoring of application deployments
    
- Monitoring of remote wipes

Instead of:

```text

   ↓

   ↓

```

Use:

```text
Security
   ↓

   ↓

Helpdesk Operator
   ↓

Helpdesk Admin
   ↓
Applications + policies
```

This is classic **least privilege**.

# 19. Scope Tags

Think:

```text
RBAC
+
Scope Tags
=
Who can do WHAT
+
WHERE they can do it
```

Example:

```text
EU Helpdesk
     ↓
EU Scope Tag
     ↓
EU Devices only
```

```text
US Helpdesk
     ↓
US Scope Tag
     ↓
US Devices only
```

Even if the account gets compromised, the blast radius is reduced.

# 20. Interview-ready answer

If an interviewer asks:

**"How would you investigate suspicious Intune activity?"**

A strong L2 answer is:

> "I'd first investigate the Entra sign-in that accessed the Intune portal, focusing on the privileged user's identity, source IP, location, authentication context, and whether the device was managed and compliant. I'd then correlate the login with Intune audit activity to identify actions such as device wipes, platform-script creation or assignment, and application deployment. For scripts, I'd correlate the Intune activity with endpoint telemetry such as Sysmon process creation and the Intune AgentExecutor log to determine what actually executed. Finally, I'd identify affected devices, determine scope and impact, validate whether the activity was authorized, and contain the compromised identity and endpoints."

That's the answer I'd memorize.
