
## 1. Sign-In Logs — "Who got in?"

```spl
index=* sourcetype="azure:aad:signin" appDisplayName="One Outlook Web"
| table _time userPrincipalName appDisplayName ipAddress location.city status.errorCode
| sort - _time
```

### What it does

Searches Microsoft Entra ID authentication events for Outlook/Exchange Online.

### Important fields

|Field|Meaning|
|---|---|
|`_time`|Time of login attempt|
|`userPrincipalName`|Account being accessed|
|`ipAddress`|Source IP|
|`location.city`|Approximate login location|
|`status.errorCode`|Authentication result|

### SOC question

> **"Was this login legitimate?"**

Look for:

```text
Known user
+
Unexpected IP
+
Unexpected location
+
Successful authentication
```

That becomes your **initial-access investigation point**.

# 2. Exchange Audit Logs — "What did they do?"

```spl
index=* sourcetype="o365:management:activity" Workload=Exchange
| table _time UserId Operation Workload
```

This is your **main Exchange investigation query**.

The key field is:

```text
Operation
```

It tells you what happened inside the mailbox.

For example:

```text
MailItemsAccessed
New-InboxRule
Set-InboxRule
Set-Mailbox
Add-MailboxPermission
Send
```

Think:

```text
Sign-in logs
     ↓
Who got in?

Audit logs
     ↓
What did they do?
```

---

# 3. `MailItemsAccessed` — "Did they read the mailbox?"

```spl
index=* Workload=Exchange Operation=MailItemsAccessed
| table _time UserId ClientIPAddress OperationCount
```

This looks for mailbox-content access.

### Why it matters

After compromising an account, an attacker often reads emails to understand:

- company structure
    
- financial activity
    
- ongoing conversations
    
- credentials/secrets
    
- potential phishing targets
    

### Important fields

```text
UserId
ClientIPAddress
OperationCount
```

### Example

```text
UserId: victim@company.com
ClientIPAddress: 185.x.x.x
OperationCount: 850
```

If the IP is unusual and hundreds of mailbox operations occur shortly after a suspicious login:

🚩 **Very interesting.**

---

# 4. `New-InboxRule` — "Did they create a hiding/persistence rule?"

```spl
index=* Workload=Exchange Operation=New-InboxRule
| table _time UserId Name DeleteMessage ForwardTo SubjectContainsWords
```

This detects creation of a new inbox rule.

Attackers can abuse rules to:

```text
Incoming email
      ↓
Check condition
      ↓
Delete / Forward
```

### Important fields

#### `DeleteMessage`

```text
DeleteMessage=True
```

Potentially very suspicious.

The attacker could delete replies to phishing emails.

---

#### `ForwardTo`

```text
ForwardTo=attacker@external-domain.com
```

Potentially indicates email exfiltration.

---

#### `SubjectContainsWords`

For example:

```text
SubjectContainsWords="invoice"
```

The attacker may only want emails related to invoices.

### Mental shortcut

```text
New-InboxRule
      ↓
Look at:
DeleteMessage
ForwardTo
SubjectContainsWords
```

---

# 5. `Set-InboxRule` — "Did they modify an existing rule?"

```spl
index=* Workload=Exchange Operation=Set-InboxRule
| table _time UserId Name DeleteMessage ForwardTo SubjectContainsWords
```

Very similar to `New-InboxRule`.

The difference:

```text
New-InboxRule
    ↓
Creates rule

Set-InboxRule
    ↓
Changes existing rule
```

### Important caveat

`Set-InboxRule` may only contain the fields that were **changed**.

So don't assume:

> "Field isn't present → feature isn't enabled."

That's a classic investigation trap.

---

# 6. `Set-Mailbox` — "Was mailbox-wide forwarding configured?"

```spl
index=* Workload=Exchange Operation=Set-Mailbox
| table _time UserId ForwardingSmtpAddress DeliverToMailboxAndForward
```

This is different from an inbox rule.

### Inbox rule

```text
IF condition
    ↓
Forward
```

### Mailbox forwarding

```text
EVERY incoming email
    ↓
Forward
```

### Important fields

#### `ForwardingSmtpAddress`

Example:

```text
ForwardingSmtpAddress=attacker@external.com
```

🚩 Investigate.

#### `DeliverToMailboxAndForward`

If:

```text
False
```

the victim may not retain the incoming emails in their mailbox.

That makes this especially suspicious.

---

# 7. `Add-MailboxPermission` — "Was someone given mailbox access?"

```spl
index=* Workload=Exchange Operation=Add-MailboxPermission
| table _time UserId Trustee
```

This detects mailbox permission changes.

The key field:

```text
Trustee
```

means the account that received the permission.

Example:

```text
UserId: victim@company.com
Trustee: attacker-account@company.com
```

Now you have to ask:

> Why did this account suddenly receive access to this mailbox?

This can provide **persistent access**.

---

# 8. `Send` — "Did the compromised account send phishing?"

```spl
index=* Workload=Exchange Operation=Send
| table _time UserId Item.Subject ClientIP SaveToSentItems
```

This is one of the most useful queries after you've established compromise.

### Important fields

#### `UserId`

Who sent the email?

#### `Item.Subject`

What was the email about?

Example:

```text
Urgent Invoice Update
Password Reset Required
Payment Confirmation
```

#### `ClientIP`

Where did the send originate?

Compare it with the normal user's activity.

#### `SaveToSentItems`

If:

```text
False
```

that's suspicious because the attacker may be trying to avoid leaving obvious evidence in Sent Items.

---

# 9. Message Trace — "Who received the phishing email?"

```spl
index=* sourcetype="o365:reporting:messagetrace"
| table Received SenderAddress RecipientAddress Subject Status FromIP
```

This is where you move from:

> **"The attacker sent an email."**

to:

> **"These 37 employees received it."**

### Important fields

|Field|Meaning|
|---|---|
|`Received`|Email timestamp|
|`SenderAddress`|Sender|
|`RecipientAddress`|Recipient|
|`Subject`|Email subject|
|`Status`|Delivery result|
|`FromIP`|Sending/source IP|

---

# 10. Filter Message Trace by Sender

```spl
index=* sourcetype="o365:reporting:messagetrace"
SenderAddress="user@company.com"
| table Received SenderAddress RecipientAddress Subject Status FromIP
```

Instead of looking at all messages, you're asking:

> **"What did this particular compromised account send?"**

Very useful after identifying a compromised mailbox.

---

# 11. Filter Message Trace by Subject

```spl
index=* sourcetype="o365:reporting:messagetrace"
Subject="Urgent Invoice Update"
| table Received SenderAddress RecipientAddress Subject Status FromIP
```

Now you're asking:

> **"Who received this specific suspicious email?"**

This is useful for phishing campaign scoping.

---

# 12. Find Deleted-Message Rules

```spl
index=* Workload=Exchange Operation=New-InboxRule DeleteMessage=True
| table _time UserId Name DeleteMessage ForwardTo SubjectContainsWords
```

This specifically hunts for:

```text
New-InboxRule
      +
DeleteMessage=True
```

### Why?

An attacker may send phishing emails and then create:

```text
IF subject contains "invoice"
THEN delete message
```

so replies don't reach the account owner.

This is a **high-value detection condition**.

---

# 13. Find Forwarding Inbox Rules

```spl
index=* Workload=Exchange (Operation=New-InboxRule OR Operation=Set-InboxRule)
| search ForwardTo=*
| table _time UserId Operation Name ForwardTo SubjectContainsWords DeleteMessage
```

This looks for rules involving forwarding.

The interesting part is:

```spl
ForwardTo=*
```

`*` means:

> There is some value in this field.

You're basically asking:

> **"Show me Exchange inbox-rule activity where forwarding is configured."**

---

# 14. Find Mailbox Forwarding

```spl
index=* Workload=Exchange Operation=Set-Mailbox ForwardingSmtpAddress=*
| table _time UserId ForwardingSmtpAddress DeliverToMailboxAndForward
```

This hunts for mailbox-level forwarding.

Think:

```text
Set-Mailbox
      +
ForwardingSmtpAddress exists
      ↓
Investigate
```

---

# 15. Find Silent Mailbox Forwarding

```spl
index=* Workload=Exchange Operation=Set-Mailbox DeliverToMailboxAndForward=False
| table _time UserId ForwardingSmtpAddress DeliverToMailboxAndForward
```

This is more specific.

You're hunting for:

```text
DeliverToMailboxAndForward=False
```

Potentially:

```text
Incoming email
      ↓
External attacker
```

while the legitimate user doesn't receive the message normally.

# 16. High Mailbox Access Volume

```spl
index=* Workload=Exchange Operation=MailItemsAccessed
| stats sum(OperationCount) as TotalAccesses by UserId ClientIPAddress
| sort - TotalAccesses
```

Now we're doing something more interesting with Splunk.

Instead of displaying individual events, we're aggregating them.

### `stats`

Performs calculations/grouping.

### `sum(OperationCount)`

Adds the operation counts.

### `by UserId ClientIPAddress`

Groups the results by:

```text
User
+
IP
```

Result conceptually:

```text
User             IP             TotalAccesses
alice@company    10.x.x.x       50
bob@company      10.x.x.x       71
alice@company    185.x.x.x      4,821   🚩
```

That last row deserves attention.

---

# 17. High-Volume Sending

```spl
index=* Workload=Exchange Operation=Send
| stats count as SendCount by UserId ClientIP
| sort - SendCount
```

This asks:

> **"Which accounts sent the most emails, and from which IPs?"**

Example:

```text
User                  IP             SendCount
alice@company.com     10.x.x.x       12
bob@company.com       10.x.x.x       19
charlie@company.com   185.x.x.x      347 🚩
```

That's a great hunting query.

---

# 18. The Big Investigation Query

```spl
index=* Workload=Exchange
| table _time UserId Operation ClientIP ClientIPAddress Item.Subject Name ForwardTo ForwardingSmtpAddress Trustee DeleteMessage SaveToSentItems
| sort _time
```

This gives you a broad Exchange activity timeline.

It's useful when you already know:

> **"Something happened to this mailbox, but I don't know what yet."**

You can then narrow down using:

```text
UserId
Operation
IP
time
```

# 🧠 The Cheat Code to Memorise

Don't memorise 20 queries separately.

Memorise these **8 operations**:

```text
┌─────────────────────────────────────────┐
│        EXCHANGE ONLINE INVESTIGATION     │
├─────────────────────────────────────────┤
│ SIGN-IN                                 │
│ sourcetype="azure:aad:signin"           │
│                                         │
│ READ MAIL                               │
│ Operation=MailItemsAccessed             │
│                                         │
│ SEND MAIL                               │
│ Operation=Send                          │
│                                         │
│ CREATE RULE                             │
│ Operation=New-InboxRule                 │
│                                         │
│ MODIFY RULE                             │
│ Operation=Set-InboxRule                 │
│                                         │
│ FORWARD MAILBOX                         │
│ Operation=Set-Mailbox                   │
│                                         │
│ ADD DELEGATE                            │
│ Operation=Add-MailboxPermission        │
│                                         │
│ TRACE EMAIL                             │
│ sourcetype="o365:reporting:messagetrace"│
└─────────────────────────────────────────┘
```

Then remember the **pivot fields**:

```text
MailItemsAccessed
    → ClientIPAddress
    → OperationCount

New-InboxRule
    → DeleteMessage
    → ForwardTo
    → SubjectContainsWords

Set-Mailbox
    → ForwardingSmtpAddress
    → DeliverToMailboxAndForward

Add-MailboxPermission
    → Trustee

Send
    → Item.Subject
    → ClientIP
    → SaveToSentItems

Message Trace
    → SenderAddress
    → RecipientAddress
    → Subject
    → Status
```

### The entire investigation in one line:

```text
LOGIN → READ → PERSIST → FORWARD → SEND → TRACE → SCOPE
```

That's the sequence I'd drill into your head for SOC interviews.
