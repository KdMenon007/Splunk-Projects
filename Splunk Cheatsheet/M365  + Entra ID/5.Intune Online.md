
The big idea is:

> **You are trying to answer: WHO accessed Intune → FROM WHERE → WHAT did they do → TO WHICH DEVICE → WHAT happened on that endpoint?**

---

# 1. First understand the architecture

Think of the environment like this:

```text
                    Microsoft Entra ID
                         │
                    Authentication
                         │
                         ▼
                  Microsoft Intune
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
            WIPE       SCRIPT       APP
             │           │           │
             ▼           ▼           ▼
          Device      Endpoint     Endpoint
             │           │           │
             └───────────┼───────────┘
                         ▼
                    EDR / Sysmon
                         │
                         ▼
                       Splunk
```

So there are **two major sides** of the investigation:

### Cloud side

```text
Entra ID
Intune
```

### Endpoint side

```text
Sysmon
EDR
Intune Management Extension logs
```

A good L2 analyst connects both.

---

# 2. Query #1 — Unmanaged Intune login

```spl
index=intune sourcetype=azure:aad:signin appDisplayName=*Intune* deviceDetail.displayName=""
| rename deviceDetail.* as dvc.*
| table _time appDisplayName ipAddress dvc.isManaged dvc.isCompliant dvc.displayName user
```

Let's dissect it.

### `index=intune`

```spl
index=intune
```

You're telling Splunk:

> Search the Intune-related index.

---

### `sourcetype=azure:aad:signin`

```spl
sourcetype=azure:aad:signin
```

This means:

> Only look at Microsoft Entra sign-in events.

So we're investigating **authentication**, not an endpoint event.

---

### `appDisplayName=*Intune*`

```spl
appDisplayName=*Intune*
```

This searches for applications whose name contains `Intune`.

For example:

```text
Microsoft Intune portal extension
```

So now we have:

```text
Entra sign-in
        +
Intune application
```

---

### `deviceDetail.displayName=""`

This is the interesting part.

```spl
deviceDetail.displayName=""
```

We're looking for an empty device display name.

Conceptually:

```text
Normal:

User
 ↓
Intune
 ↓
Corporate laptop
 ↓
deviceDetail.displayName = LAPTOP-001
```

Suspicious scenario:

```text
User
 ↓
Intune
 ↓
Unknown device
 ↓
deviceDetail.displayName = ""
```

That doesn't automatically mean attack.

But for a privileged Intune administrator:

> **Unmanaged/unknown device + privileged Intune access = investigate.**

---

# 3. Why rename the fields?

```spl
| rename deviceDetail.* as dvc.*
```

Suppose you have:

```text
deviceDetail.displayName
deviceDetail.isManaged
deviceDetail.isCompliant
deviceDetail.trustType
```

The query turns them into:

```text
dvc.displayName
dvc.isManaged
dvc.isCompliant
dvc.trustType
```

This simply makes the fields easier to work with.

---

# 4. Why `table`?

```spl
| table _time appDisplayName ipAddress dvc.isManaged dvc.isCompliant dvc.displayName user
```

You're saying:

> Show me only the fields I care about.

Result conceptually:

```text
TIME        USER          IP           MANAGED   COMPLIANT   DEVICE
10:20       admin@x.com   8.x.x.x      false     false       -
```

Now your analyst brain should go:

> "Why is an Intune admin accessing Intune from an unmanaged device?"

That's the point.

---

# 5. Query #2 — All Intune logins

```spl
index=intune sourcetype=azure:aad:signin appDisplayName=*Intune*
| rename deviceDetail.* as dvc.*
| table _time user appDisplayName ipAddress dvc.displayName dvc.isManaged dvc.isCompliant dvc.trustType
```

This one is less aggressive.

You're not filtering for suspicious devices.

You're saying:

> Show me **every Intune login**.

This is useful for establishing a baseline.

Example:

```text
admin1 → laptop-admin01 → managed → compliant
admin2 → laptop-admin02 → managed → compliant
admin3 → unknown       → unmanaged → non-compliant
```

The third one deserves attention.

---

# 6. Query #3 — Managed devices

```spl
index=intune sourcetype=azure:aad:signin appDisplayName=*Intune*
| rename deviceDetail.* as dvc.*
| search dvc.isManaged=true
| table _time user ipAddress dvc.displayName dvc.isManaged dvc.isCompliant dvc.trustType
```

Now we're filtering:

```text
isManaged = true
```

Meaning:

> The device is managed by the organization's device-management system.

This is generally a stronger trust signal.

But remember:

> **Managed does NOT mean safe.**

If an attacker compromises a corporate laptop, the laptop can still be managed.

---

# 7. Query #4 — Non-compliant devices

```spl
index=intune sourcetype=azure:aad:signin appDisplayName=*Intune*
| rename deviceDetail.* as dvc.*
| search dvc.isCompliant=false
| table _time user ipAddress dvc.displayName dvc.isManaged dvc.isCompliant dvc.trustType
```

Here we're looking for:

```text
isCompliant=false
```

Example:

```text
Admin
 ↓
Corporate laptop
 ↓
Intune managed
 ↓
NOT compliant
```

Why might it be non-compliant?

Potential reasons include:

```text
BitLocker disabled
Defender requirement failed
OS requirements failed
Password policy failed
Security configuration failed
```

Again:

> Non-compliant doesn't automatically mean compromised.

It's a **security signal**.

---

# 8. Now we move to the dangerous stuff

Once you've identified suspicious Intune access, ask:

> **What did the administrator actually do?**

There are three major categories:

```text
             INTUNE
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
      WIPE    SCRIPT     APP
```

---

# 9. Query #5 — Remote wipe

```spl
index=intune sourcetype="o365:graph:intune" wipe
| eval deviceid=mvindex('resources{}.modifiedProperties{}.newValue', 0)
| table _time activityType actor.userPrincipalName deviceid
```

This searches Intune Graph audit data.

The important field is:

```text
activityType
```

For a wipe:

```text
wipe ManagedDevice
```

---

# 10. What is `actor.userPrincipalName`?

Example:

```text
actor.userPrincipalName
=
john.smith@company.com
```

This tells you:

> **Who performed the action?**

That's critical.

You don't want to know merely:

```text
"A device was wiped."
```

You want:

```text
Who?
When?
Which device?
From where?
Was it authorized?
```

---

# 11. What is `deviceid`?

The wipe event may give you something like:

```text
deviceid =
a8f91c21-xxxx-xxxx-xxxx
```

That's not necessarily the friendly hostname.

So you correlate it with other device records.

Conceptually:

```text
Intune wipe
    ↓
Device ID
    ↓
Entra/device inventory
    ↓
Hostname
    ↓
User
```

That's correlation.

And correlation is basically the SOC analyst's favorite magic trick.

---

# 12. Why mass wipe is scary

Imagine:

```text
Compromised admin
      ↓
Intune
      ↓
500 devices
      ↓
Wipe
```

The attacker doesn't need malware on 500 computers.

They abuse **one administrative control plane**.

That's why cloud management systems are extremely valuable to attackers.

---

# 13. Query #9 — Platform scripts

```spl
index=intune sourcetype="o365:graph:intune" activityType=*DeviceManagementScript*
| table _time actor.userPrincipalName activityType resources{}.resourceId resources{}.modifiedProperties{}.newValue
```

This searches for Intune platform-script activity.

Think:

```text
Administrator
     ↓
Intune
     ↓
PowerShell script
     ↓
Many endpoints
```

That's powerful.

And therefore dangerous.

---

# 14. Why platform scripts are dangerous

Suppose an attacker controls an Intune administrator.

They can potentially abuse legitimate management functionality:

```text
Create script
     ↓
Assign script
     ↓
Intune delivers it
     ↓
Endpoint executes it
```

The endpoint may see something like:

```text
Intune Agent
      ↓
AgentExecutor
      ↓
PowerShell
```

From the endpoint's perspective, the command may originate from a legitimate enterprise management mechanism.

That's why this is difficult to distinguish from normal IT activity.

# 15. Query #10 — Parse script actions

```spl
index=intune sourcetype="o365:graph:intune" activityType=*DeviceManagementScript*
| eval action=mvindex(split(activityType, " "), 0)
| eval script='resources{}.resourceId'
| eval target=mvindex('resources{}.modifiedProperties{}.newValue', 0)
| eval target=if(action="assignDeviceManagementScript", target, "N/A")
| table _time actor.userPrincipalName action script target
```

This query is doing something more advanced.

It's **creating useful fields from messy audit data**.

---

# 16. `eval action=...`

```spl
| eval action=mvindex(split(activityType, " "), 0)
```

Suppose:

```text
activityType =
assignDeviceManagementScript something
```

`split()` breaks the string into pieces.

`mvindex(...,0)` takes the first piece.

So you get:

```text
action = assignDeviceManagementScript
```

Now it's easier to search and analyze.

---

# 17. Script ID

```spl
| eval script='resources{}.resourceId'
```

This extracts the resource ID.

Think:

```text
script ID
   ↓
Which script?
```

---

# 18. Target

```spl
| eval target=mvindex('resources{}.modifiedProperties{}.newValue', 0)
```

This tries to extract the target from the modified properties.

So now you can potentially determine:

```text
Actor
 ↓
Script
 ↓
Target
```

---

# 19. Why the `if()`?

```spl
| eval target=if(action="assignDeviceManagementScript", target, "N/A")
```

The target is particularly relevant when the action is:

```text
assignDeviceManagementScript
```

For other actions, it sets:

```text
N/A
```

This keeps the output cleaner.

---

# 20. Query #14 — Application activity

```spl
index=intune sourcetype="o365:graph:intune" activityType=*MobileApp*
| table _time actor.userPrincipalName activityType resources{}.resourceId resources{}.modifiedProperties{}.newValue
```

This looks for Intune application management activity.

Potential attack:

```text
Compromised Intune admin
        ↓
Malicious application
        ↓
Deploy
        ↓
1000 endpoints
```

So investigate:

```text
Who?
What application?
Which devices?
When?
Was it approved?
```

# 21. Endpoint side — Sysmon

Now we leave Intune's cloud logs.

We go to the endpoint.

Important Sysmon event:

```text
Event ID 1
=
Process Creation
```

So:

```spl
index=* sourcetype=*sysmon* EventCode=1
| search ParentImage="*IntuneWindowsAgent.exe"
| table _time host User ParentImage Image CommandLine ProcessId
```

This asks:

> Did the Intune Management Extension create a process?

---

# 22. The process tree

This is the key artifact:

```text
Microsoft.Management.Services.IntuneWindowsAgent.exe
                    │
                    ▼
             AgentExecutor.exe
                    │
                    ▼
               powershell.exe
                    │
                    ▼
                script.ps1
```

If you see this chain, don't immediately yell "MALWARE!"

It can be completely legitimate.

Instead ask:

```text
Who created the script?
What was the script?
Why was it deployed?
Which devices received it?
What did PowerShell execute?
```

Context wins.

---

# 23. Query #19 — Intune Agent → PowerShell

```spl
index=* sourcetype=*sysmon* EventCode=1
| search ParentImage="*AgentExecutor.exe" Image="*powershell.exe"
| table _time host User ParentImage Image CommandLine ProcessId
```

This is one of the most useful endpoint correlation queries.

You're specifically looking for:

```text
Parent =
AgentExecutor.exe

Child =
powershell.exe
```

Then inspect:

```text
CommandLine
```

That's where the juicy stuff often is.

---

# 24. What should you investigate in CommandLine?

For example:

```text
powershell.exe -ExecutionPolicy Bypass ...
```

or:

```text
powershell.exe -EncodedCommand ...
```

or:

```text
powershell.exe IEX(...)
```

These are **suspicious indicators**, not automatic proof of maliciousness.

You need context.

For example:

```text
Intune admin
 ↓
Approved script
 ↓
PowerShell
 ↓
Normal configuration change
```

Could be perfectly legitimate.

But:

```text
Unknown admin
 ↓
Unmanaged login
 ↓
Create Intune script
 ↓
Assign to All Devices
 ↓
PowerShell
 ↓
Encoded payload
```

That's a very different story.

---

# 25. The most important concept: `All Devices`

This is a huge investigation clue.

Imagine:

```text
Script assigned to:

All Devices
```

versus:

```text
Script assigned to:

10 specific test machines
```

The first has a dramatically larger potential blast radius.

So when investigating Intune scripts, always ask:

> **What was the assignment scope?**

# 27. The complete investigation

Suppose Splunk generates:

```text
10:01
admin@company.com
Intune login
IP = unfamiliar
Device = unknown
Managed = false
```

You investigate.

Then:

```text
10:08
createDeviceManagementScript
```

Then:

```text
10:10
assignDeviceManagementScript
Target = All Devices
```

Then endpoint telemetry:

```text
10:42
AgentExecutor.exe
      ↓
powershell.exe
```

Now your timeline is:

```text
10:01
   │
   ├── Suspicious Intune login
   │
10:08
   │
   ├── Script created
   │
10:10
   │
   ├── Script assigned
   │
10:42
   │
   ├── Endpoint execution
   │
   ▼
Potential enterprise-wide compromise
```

**That's an L2 investigation.**

# 28. Your mental cheat sheet

Don't memorize SPL blindly.

Memorize the questions:

```text
┌─────────────────────────────┐
│ 1. WHO?                     │
│    user / actor              │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 2. WHERE?                   │
│    IP / location / device    │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 3. DEVICE?                  │
│    managed / compliant       │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 4. WHAT?                    │
│    wipe / script / app      │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 5. TARGET?                  │
│    which device/group        │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 6. EXECUTION?               │
│    Sysmon / EDR / PowerShell │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ 7. IMPACT?                  │
│    what actually happened?   │
└─────────────────────────────┘
```

### The three SPL keywords to burn into your brain:

```text
DeviceManagementScript
wipe ManagedDevice
MobileApp
```

And the endpoint chain:

```text
IntuneWindowsAgent
        ↓
AgentExecutor
        ↓
PowerShell
```

If you understand **why** each query exists and what question it answers, rather than just memorizing the syntax, you'll be able to adapt the searches when the field names or data model change.
